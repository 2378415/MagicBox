# MAKCU V3.2 左片「未公开协议」清单

> 对象：`官方固件/V3.2_LEFT.bin`（sha256 `ca7a71b4…a3a580`）
> 目的：把命令跳表中**没有对应文本命令**的 13 个 opcode 处理函数全部导出、分类、标注证据与不确定项。
> 证据等级：**[观察]** 反汇编/数据直接可见；**[推断]** 由调用链与常量推得；**[待验证]** 需上机或进一步反编译。

---

## 1. 为什么会有「未公开」opcode

左片的分发是两级的：

```
文本帧 "km.left()\r"
   └─ 一级：43 条命令表（0x3C03DF74）前缀匹配
        └─ 取表项 +0x10 的 opcode
             └─ 二级：27 项跳表（0x3C03DF08）jx 到处理函数
```

命令表只用到 **13 个** opcode（0x00–0x07、0x09–0x0C、0x19、0x1A）。跳表另有 **13 个** opcode 指向真实处理函数，但没有任何文本命令能选中它们：

| 未使用 opcode | 0x08、0x0D、0x0E、0x0F、0x10、0x11、0x12、0x13、0x14、0x15、0x16、0x17、0x18 |
|---|---|

一级查表失败时（`0x4200EF18` 中 `beqz a10` 直接返回），**没有「按数字 opcode 兜底」的路径** [观察]。所以这些处理函数在 CH343 文本口上不可达，最可能的使用方是：

1. 右片（USB Host 侧）经两片之间的 UART1 直接按 opcode 调用 [推断]；

2. 产线/调试夹具的二进制帧 [推断]；
3. 历史遗留代码，现版本已无调用者 [待验证]。

## 3. 参数语法（共用解析器）

这些处理函数共用两套解析：

**单值 `FUN_4200E458`** [观察]

```c
if (s[0] == '\'' && len > 2 && s[len-1] == '\'')
    v = char_to_usage(s[1]);        // 单引号 → 字符
else
    v = atoi_skip_spaces(s, len);   // 允许前导空白、+/- 号，越界返回 0
```

**逗号列表 `FUN_4200E670`** [观察]

```c
n = 0;
while (有逗号 && n != 6) {
    段 = 到下一个 ',' 或 ')';
    v = parse_single(段);           // 同上，'c' 或十进制
    若 v != 0 → arr[n++] = (int16)v;
}
```
最多 **6 个**值，0 被视为「空位」不计数。

**区间 `FUN_4200E740`**：把 `a,b` 解析成两个端点（`start`、`end`），供 0x0F/0x14 的延时范围使用。

## 4. 逐条说明

### 4.1 0x08：空操作

```c
void handler(ctx, reply_arg) { reply(reply_arg, 0); }   // 7 条指令，无副作用
```

### 4.2 0x0D / 0x0E：单键按下 / 释放

```c
// 0x0D
v = parse_single(buf, len);          // 'A' 或 65 之类的十进制
if (v) { hid_key_down(ctx, v); reply(); }

// 0x0E
v = parse_single(buf, len);
if (v) { hid_key_up(ctx, v); reply(); }
```

`hid_key_down` = `FUN_42010E70`：把 usage 写进当前 HID 报告（字段表 `ctx+0x214`，report 缓冲 `ctx+0x219`），置 `dirty=1`，`xTaskGenericNotify` 唤醒提交任务。
`hid_key_up` = `FUN_42010F00`：按 usage 找到该字段并清零，同样置脏位并通知。

### 4.3 0x0F：点按（tap）

```c
v = parse_single(buf,len);
FUN_42010F8C(ctx, v, ms_min, ms_max);
// 内部：key_down(v); delay(随机或定值 ms); key_up(v);
```

### 4.4 0x10：按字符串逐字符输入

```c
if (len > 2 && buf[0]=='\'' && buf[len-1]=='\'') {
    n = min(len-2, 0x3F);
    memcpy(tmp, buf+1, n); tmp[n]=0;
    FUN_42010FDC(ctx, tmp, n);   // 每字符: key_down → 50ms → key_up
    reply();
}
```

### 4.5 0x11：键状态查询

```c
v = parse_single(buf,len);
ch = FUN_4201100C(ctx, v);          // 返回状态字符
snprintf(out, "%s\n", ch);
reply(out, strlen(out));
```
`FUN_4201100C` 撞 `excw`，内部大概率是「在报告里查该 usage 的按下位」[待验证]。

### 4.6 0x12 / 0x13 / 0x14：多键与组合键

```c
// 0x12 批量按下
n = parse_list(buf,len,arr);            // ≤6
if (n) { FUN_42011098(ctx, arr, n); reply(); }   // 逐个 key_down

// 0x13 批量释放
if (n) { FUN_420110B4(ctx, arr, n); reply(); }   // 逐个 key_up

// 0x14 组合键（按下→延时→释放）
n = parse_list(buf,len,arr);
FUN_4200E740(buf,len,&d1,&d2);          // 延时范围
if (n) FUN_420110D0(ctx, arr, n, d1, d2);
```

`FUN_420110D0` 的延时：`d1>0` 用 `d1` ms；`d1<=0 && d2>0` 用 `rand()%d2` ms；都为 0 则不延时。

### 4.7 0x15 / 0x16：写映射表

```c
// 0x16
idx = parse_single(buf,len);            // 0..255
val = parse_single(rest);               // 0..255
FUN_4202D4DC(ctx, idx, val);
// 内部: desc[idx+99] = (char)val;   // 描述符表后 256 字节 = 自定义映射

// 0x15
v1 = parse_single(buf,len);             // 16 位索引
v2 = parse_single(rest);                // 8 位值
FUN_4202D4A8(ctx, v1, v2);              // 同族写表（该函数撞 excw，未完全还原）
```

### 4.8 0x17：导出通道表

```c
for (i = 0; i < 256; i++) {
    base = ctx->tbl;                       // ctx+0x214
    if (base[i+0x269] && base[i+0x369] && ctx->flags[i+0x636]) {
        len = FUN_4202058C(buf, 16, fmt);  // 格式化 16 字节
        reply(buf, len);
        return;
    }
}
reply("0", 1);
```

用途推断：把当前「已启用通道」的索引/状态回给对端 [推断]。

### 4.9 0x18：通道开关

```c
// 反编译被 excw 截断，objdump 显示：
// 取索引 i（0..255）→ 检查 ctx->tbl[i+0x369] 非 0
// 解析随后的 ',' 分隔值 → 写 ctx->tbl[i+0x269] = (c=='1')
// 若 c=='1' → 清全局 0x3FC99FA3；否则置 1
```

置信度低，需要按 §6 的方法补完。

## 5. 与公开命令的对照

| 能力 | 公开文本命令 | 未公开 opcode |
|---|---|---|
| 鼠标移动/滚轮/按键 | `move(`、`wheel(`、`left(`… | — |
| 键盘按下/释放 | 无 | **0x0D / 0x0E** |
| 键盘点按 | 无 | **0x0F** |
| 字符串输入 | 无 | **0x10** |
| 多键组合 | 无 | **0x12 / 0x13 / 0x14** |
| 键状态查询 | 无 | **0x11** |
| 映射表写入 | 无 | **0x15 / 0x16** |
| 通道表导出/开关 | 无 | **0x17 / 0x18** |

即：**左片其实具备完整的键盘注入能力（单键、批量、组合、文本、状态查询），只是没有在文本协议里暴露**。这解释了为什么官方文档只写「支持 b pro 命令」；键盘能力留在 opcode 层。

## 9. 可达性修正（补充）

后续命名时定位到 `0x4200DB04`（`frame_router`）：UART0 的首字节路由器。它只把 `0x2E`(.) 转发给文本分发器，把 `0xA1/0xA2/0xA4/0xA5` 用于 ack、忽略、读配置、写序列号，其余字节交给 `frame_echo_hex` 回显 —— **不会**把首字节当 opcode 送进 §2 的跳表。

因此上表 13 个处理函数在 UART0 文本/二进制帧上仍然不可达；能触发它们的只可能是片间 UART1 的私有帧或代码内部直接调用。这一条把原先“可能有二进制兜底”的猜测收敛为“已确认没有”。


### 9.1 片间 UART1 也不是入口

右片 → 左片的 UART1 帧由 `hid_uart_task`（`0x4200FE68`）发出，长度取自头部 `+2` 的 16 位字段（总长 = 长度 + 4）；左片 `uart_events`（`0x42013884`）只把 `hdr[1] == 0xA0` 的帧交给 `FUN_42013734` 做 USB EP0 隧道（`usbd_ep0`），**不经过 `cmd_dispatch`**。

结论：UART0 与 UART1 两条链路都不分发这 13 个 opcode，它们目前只能视为遗留代码或为其他硬件变体保留。详见 `reversed/docs/uart1_link.md`。

## 10. 跳表专用入口（第 7 轮找回）

opcode 跳表有两项指向的地址从来没被 Ghidra 建成函数（无 `call8` 调用点、前后被
`ill` 填充隔开），因此旧版源码树里根本不存在这两个函数：

| opcode | 地址 | 名字 | 说明 |
|---|---|---|---|
| 0x16 | `0x4200E624` | `cmd_map_entry` | `"<idx>,<val>"` 写映射表项，两值非零才写 |
| 0x1A | `0x4200DC84` | `cmd_serial` | 序列号查询 / `serial(0)` 恢复原厂 / `serial("<串>")` 写伪装值 |

手工重建在 `reversed/manual/left/protocol/`，由 `build_project.py` 并入源码树；
`cmd_serial` 已用文本命令实测可达（`dynamic_tests.md` §11）。
