# 片间 UART1 链路（右片 → 左片）

两片之间不是普通串口透传，而是**带 4 字节头的私有帧**，左片收到后直接做 USB 控制传输。本文记录已确认的格式与仍未确认的字段。

---

## 1. 发送侧（右片）

`FUN_420100FC` 是右片的桥接初始化：

```c
led_init();
for (int i = 0; i < 8; i++)
    queue[i] = xQueueCreate(8, 4);          // 8 个队列，元素是缓冲区指针
for (int i = 0; i < 8; i++) {
    for (int j = 0; j < 8; j++) {
        buf[i][j] = heap_caps_malloc(size, 8);   // 每格 8 字节
        memset(buf[i][j], 0, size);
    }
}
for (int i = 0; i < 8; i++)
    xTaskCreate(hid_uart_task, "hid_uart", ..., i, 7, ...);   // 8 个同名任务
```

`FUN_4200FE68` 是 `hid_uart_task` 的主体：

```c
xQueueReceive(queue[id], &pkt, portMAX_DELAY);
FUN_4200F6B0(pkt, *(uint16_t *)(pkt + 2) + 4);   // 长度取自偏移 +2，再加 4 字节头
```

`FUN_4200F6B0(ptr, len)` → `FUN_42008F7C(1, ptr, len)` → `uart_write_bytes(UART_NUM_1, ...)`。

**结论（发送侧）**：帧 = 4 字节头 + 负载；**头的 `+2` 处是 16 位负载长度**，总长 = 长度 + 4。头部 `+0`、`+1`、`+4` 的语义见下。

---

## 2. 接收侧（左片）

`uart_event_task`（`0x420139E4`）安装 **UART1** 驱动并起三个任务：

```c
uart_driver_install(1, ...); uart_param_config(1, ...); uart_set_pin(1, ...);
xTaskCreate(uart_events,        "uart_events", ...);
xTaskCreate(hid_data_processing,"hid_data_processing", ...);
xTaskCreate(hid_parse_task,     "hid_parse_task", ...);
```

`uart_events`（`0x42013884`）读字节后交给 `FUN_42013734`，后者按头部字段分流：

```c
if (hdr[1] == 0xA0) {                 // 0xA0 = 控制传输帧
    if (*(uint16_t *)(hdr + 2) == 1) {
        if (hdr[4] == 0x00) {         // 方向/标志 = 0
            rc = usbd_ep0(0, data, ...);   // 在克隆设备上执行 EP0
            flag = (rc == 0);
            notify(...);
            return;
        }
        if (hdr[4] != 0xFF) return;   // 其他值忽略
    } else if (*(uint16_t *)(hdr + 2) != 0) {
        return;
    }
    ...
}
```

**结论（接收侧）**：`hdr[1] == 0xA0` 标记“USB 控制传输隧道”；`hdr+2` 的 16 位字段在接收侧被当作类型（0 或 1），在发送侧被当作长度 —— 同一字段的两种用法说明头部结构可能是 `[0]=? [1]=0xA0 [2..3]=长度/类型 [4]=方向`，但**具体语义仍需动态验证**。

---

## 3. 对“隐藏 opcode”的影响

左片的 `uart_events` 只调用 `FUN_42013734`（EP0 隧道）与 `uart_flush_input`，**没有**调用 `cmd_dispatch`（`0x4200EF18`）。因此：

| 链路 | 是否能把首字节当 opcode 分发 |
|---|---|
| UART0 文本/二进制帧 | ❌ 只认 `.`、`0xA1`、`0xA2`、`0xA4`、`0xA5`，其余回显 |
| UART1 片间帧 | ❌ 只认 `0xA0` 控制传输，其余忽略 |
| 内部直接调用 | 未发现调用点 |

**13 个隐藏 opcode（0x08、0x0D–0x18）在两条外部链路上都不可达**，目前只能判定为遗留代码或为其他硬件变体保留。要下定论需要上机：向 UART1 注入构造帧，或对 `0x4200E5xx`–`0x4200EDxx` 下断点。

## 5. 头部字段反推（逐字节）

左片 `FUN_42013734` 的完整分支显示，接收缓冲（`DAT_42001220`）按以下偏移取值：

| 偏移 | 发送侧（右片） | 接收侧（左片 `0x42013734`） | 置信度 |
|---|---|---|---|
| `+0` | 未观察到写入 | **未被读取** | 低（可能是填充/版本位） |
| `+1` | 未观察到写入 | **命令字节**：`0xA0` = EP0 隧道；`0xA2` = 数据/事件；其它 → 丢弃或仅给队列发信号 | 高 |
| `+2..3` | **u16 负载长度**，总长 = 长度 + 4 | `0xA0` 分支里当**类型**：`1` = 发起 EP0 IN，`0` = 另一方向，其它忽略 | 高（发送侧）/ 中（接收侧语义） |
| `+4` | 未观察到 | `0xA0` 分支的**方向/标志**：`0x00` 走 `usbd_ep0(0, …)`；`0xFF` 走另一支；其它忽略 | 中 |
| `+5` | 未观察到 | `0xA2` 分支：与全局 `DAT_42001208` 比较，像**会话/通道 id** | 中 |
| `+6` | 未观察到 | `0xA2` 分支：非零才继续，像**有效标志/长度** | 中 |
| `+8` | 未观察到 | `0xA2` 分支：与描述符 `+0x62` 或 `+0x1d5` 比较，像**端点地址或 report id** | 中 |

### 观察到的两处不一致

1. **头长 4 还是 9？** 右片按 `长度 + 4` 发送，左片却读到 `+8`。两种解释：右片的“长度”已经包含部分头部，或左片解析的是另一种（更长的）帧格式，`0xA0` 只是其中一类。
2. **`+2` 一字段两用**：发送侧把它当长度，接收侧在 `0xA0` 分支把它当类型（只接受 0/1）。更可能的结构是 `+2..3` 为长度、类型由 `+4` 区分，而 `0xA0` 分支里的 `==1` 实际是在比较**长度 = 1**（即 1 字节的 EP0 请求）。

### 下一步验证方法

- 静态：沿 `0x4200FF10`（队列生产者）回溯到 USB host 回调，看它如何填 `+0/+4/+5`；
- 动态：用逻辑分析仪抓 UART1，按 `0xA0/0xA2` 分类统计各偏移取值，可直接证实 `+2` 是长度还是类型。

现有结论足以支撑“UART1 是 USB 控制传输隧道”的判断，但字段级语义仍需上述验证。

## 6. 头部字段已定位（写入侧证据）

在右片找到三个**帧构造器**，头部写法完全一致：

```c
/* 0x420102A8：0xA0 控制传输请求 */
buf[0] = 0x5A;                    // 'Z' 魔数
buf[1] = 0xA0;                    // 命令
*(uint16_t *)(buf + 2) = 1;       // 负载长度 = 1
buf[4] = (param ? 0x00 : 0xFF);   // 负载第 0 字节 = 方向/标志
xQueueSend(queue[0], &buf, 0);
```

```c
/* 0x4200FAC0：0xA0 的填充助手 */
*(uint16_t *)(frame + 2) = 1;                  // 长度 1
frame[4] = (FUN_42010364() == 0) ? 0xFF : 0x00; // 方向
```

```c
/* 0x4200FAE0：0xA3 帧 */
*(uint16_t *)(frame + 2) = 1;
frame[4] = 0;
```

```c
/* 0x4200F6C4：通用转发，按源帧的 +1 命令字节分派 */
out[0] = 0x5A;
out[1] = src[1];
/* 0xA0 → 4200FAC0；0xA1 → 短帧置 len=1/flag=0xFF，长帧 → 4200FC74；0xA3 → 4200FAE0 */
```

### 修正后的头部布局

| 偏移 | 含义 | 证据 |
|---|---|---|
| `+0` | **魔数 `0x5A`（'Z'）** | 三个构造器一致 |
| `+1` | **命令字节**：`0xA0` EP0 隧道、`0xA1`、`0xA2` 数据/事件、`0xA3` | 构造器 + 左片 `42013734` 分支 |
| `+2..3` | **u16 负载长度**（不是类型） | 构造器统一写 `1`，发送侧按 `长度+4` 计算总长 |
| `+4` 起 | **负载**（不是头部第 5 字节） | 左片读到的 `+4/+5/+6/+8` 实际是 `payload[0..4]` |

由此推翻上一版的两处“不一致”：

1. 长度 `+2` 恒为长度；左片 `0xA0` 分支里的 `==1` 实际是**负载长度为 1**（1 字节的 EP0 请求），不是“类型=1”；
2. 右片按 `长度+4` 发送、左片读到 `+8`：因为 `+8` 是 `payload[4]`，属于负载，不是头部溢出。

### 各命令的负载语义

| 命令 | 负载长度 | 负载内容 |
|---|---|---|
| `0xA0` | 1 | `payload[0]` = 方向：`0x00` 发起 EP0 IN，`0xFF` 另一方向（`4200FAC0`） |
| `0xA3` | 1 | `payload[0]` = 0（`4200FAE0`） |
| `0xA1` | 1（短帧） | `payload[0]` = `0xFF` |
| `0xA2` | ≥5 | 左片按 `payload[1]`(会话 id)、`payload[2]`(有效位)、`payload[4]`(端点/report id) 做过滤 |

至此 UART1 的帧格式已完整：**`5A <cmd> <len:u16> <payload…>`**。

## 7. 0xA2 帧的写入侧证据（补上缺口）

`0x4200FF10`（USB 事件处理，无直接调用者，说明是回调注册）里找到 0xA2 构造：

```c
frame[0] = 0x5A;
frame[1] = 0xA2;
frame[4] = *(uint8_t *)((int)client + 0x8F);      /* payload[0] = 端点/接口号 */
frame[5] = id;                                     /* payload[1] = 会话/队列 id */
frame[6] = (uint8_t)len;                           /* payload[2] = 负载长度 */
frame[7] = 0;                                      /* payload[3] = 0 */
*(uint16_t *)(frame + 2) = ((uint16_t)len & 0xff) + 4;  /* 头部长度字段 */
queue_send(...);
```

与左片 `0x42013734` 的过滤条件一一对应：

| 偏移 | 写入值 | 左片用途 | 结论 |
|---|---|---|---|
| `+4` | `client+0x8F` 端点号 | 与描述符 `+0x62` / `+0x1d5` 比较 | **端点地址**（EP number） |
| `+5` | `id` | 与全局 `DAT_42001208` 比较 | **会话/队列 id** |
| `+6` | 负载长度 | 非零才继续 | **长度**（不是“有效位”） |
| `+7` | 0 | — | 填充 |

这样 UART1 的两种帧都有写入侧证据了：`0xA0`（EP0 隧道，1 字节方向）与 `0xA2`（HID 上报，端点号 + id + 长度）。

唯一仍需动态确认的是：`+2` 处的长度字段在 0xA2 分支写的是 `len+4`，而发送端又按 `该值+4` 计算总长 —— 说明这一字段可能包含 4 字节头，实际总长 = 字段值 + 4 仍需抓包核对。

## 8. 长度口径清算：`0x4200F6C4` 各分支写了多少字节

结论先给：**`+2` = 4 字节头之后的字节数；线上总长 = 字段 + 4。** 左右两侧
口径一致，0xA2 的“多算 4”也由此解释清楚。

### 8.1 接收侧状态机（右片 `0x4200F514`）复述口径

```c
/* 逐字节：0x5A → cmd → len_lo → len_hi → 收满 len 个字节 → frame_forward */
case 0:  if (b == 0x5A) { memset(frame, 0, size); frame[0] = b; st = 1; } break;
case 1:  frame[1] = b; st = 2; break;
case 2:  len = b; st = 3; break;
case 3:  len |= b << 8; frame[2..3] = len;
         if (len == 0) { frame_forward(frame); st = 0; }        /* 纯头帧 */
         else if (len > buf_size) st = 0;                       /* 超长丢弃 */
         else { payload_pos = 0; st = 4; } break;
case 4:  payload[payload_pos++] = b;
         if (payload_pos == len) { frame_forward(frame); st = 0; } break;
```

`len == 0` 也能成帧（只有 4 字节头），说明帧长完全由字段决定。

### 8.2 每个分支写入的字段与负载字节数

| `+1` 命令 | 处理函数 | 写入 `+2` | 实际写出负载 | 线上总长 |
|---|---|---:|---|---:|
| `0xA0` | `frame_ep0_dir`（`0x4200FAC0`） | `1` | 1（方向 `0x00`/`0xFF`） | 5 |
| `0xA3` | `frame_a3_flag`（`0x4200FAE0`） | `1` | 1（`0x00`） | 5 |
| `0x1A` | `0x4200F854`（键盘/鼠标快照） | `min(n,0x14)+1` | 1 状态 + n 字节快照 | 4+1+n |
| `0xA1`（`len<8`） | 早退分支 | `1` | 1（`0xFF`） | 5 |
| `0xA1`（`len>=8`） | `0x4200FC74` → 三个子分支 | 见 8.3 | 见 8.3 | — |
| `0xA4` | `0x4200FE44` → `0x4200F804`/`0x4200FD24`/`0x4200FD84` | `1` | 1（状态） | 5 |
| `0xB1` | 无处理分支 | **不写**（缓冲已清零） | 0 | 4（纯头） |
| 其它 | `0x420248E4` | `1` | 1（`0xFF`） | 5 |
| 字段 > 缓冲上限 | `0x4200F6C4` 入口早退 | `1` | 1（`0xFF`） | 5 |

### 8.3 `0xA1` 的三个子分支

| 子分支 | 条件 | 写入 `+2` | 负载 |
|---|---|---:|---|
| `0x4200F8E0` | 请求长度字段为 0 | `1` | 1（`0xFF`，表示失败） |
| `0x4200FC00` | 负长度 / 其他 | `读回字节数 - 8` | 读回的 HID 报告（去掉 8 字节前缀）；`<8` 时回落成 `1`/`0xFF` |
| `0x4200F90C` | 正常路径 | `(请求长度 == 读回长度) ? 0 : 1` | 0 表示“无负载”，1 时负载为 `0xFF` |

即：所有分支都是「先写负载、再把 `+2` 写成负载字节数」或「置 `1`/`0xFF`
错误帧」，没有一处让字段与实际字节数脱节。

### 8.4 0xA2 的“+4”由此闭合

`0x4200FF10` 里 0xA2 帧的负载布局是 `[ep, id, len, 0, data…]`，**头后
共 4 + len 字节**，所以字段写 `len + 4` 完全正确：

```
+0 5A | +1 A2 | +2..3 = len+4 | +4 ep | +5 id | +6 len | +7 0 | +8.. data[len]
                                 └────────── 头后 len+4 字节 ──────────┘
```

线上总长 = `len + 8`，与发送端 `字段 + 4` 一致。上一节标的“不一致”到此消除：
`+2` 从来都只是“头后字节数”。

## 9. 0xA2 为什么不在 `0x4200F6C4` 的分派表里

`frame_forward`（`0x4200F6C4`）只覆盖 `0xA0 / 0xA1 / 0xA3 / 0x1A / 0xA4 / 0xB1`，
收到 `0xA2` 会落到默认分支 `0x420248E4`，回一帧 `5A A2 01 FF`。原因不是漏写，
而是**方向不对称**：

| 方向 | 谁发 | 帧类型 |
|---|---|---|
| 右 → 左 | `hid_uart_task` / USB host 回调 | `0xA0`（EP0 隧道请求）、`0xA2`（HID 上报） |
| 左 → 右 | 左片 `uart_events` 回写 | `0xA0`/`0xA1`/`0xA3`/`0x1A`/`0xA4`/`0xB1` |

右片的接收状态机（`0x4200F514`）只在**左→右**方向收帧，这条链路上不会出现
`0xA2`；`0xA2` 由左片的 `0x42013734` 消费。因此分派表缺 `0xA2` 是设计使然，
不是未完成项（问题 #5 关闭）。
