# MAKCU 官方固件逆向分析报告（V3.2 LEFT / V3.7 RIGHT）

- 分析对象：`官方固件/V3.2_LEFT.bin`、`官方固件/V3.7_RIGHT.bin`
- 分析日期：2026-11-09
- 分析方式：静态分析（不改动样本，不连接硬件）
- 工具链：REA 6.7.0（CLI）＋ Rizin 0.9.1（Xtensa）＋ esptool 5.6.0 ＋ 自研 ESP32-S3 镜像解析/字面量池交叉引用脚本

---

## 0. 结论摘要

1. 两个 `.bin` 都是**从 0x0 起的整片烧录镜像**，不是单独的 app：`0x0` 引导加载器、`0x8000` 分区表、`0x10000` 应用；文件尾即应用结束（`0x62850` / `0x53740`），其后区域未包含。
2. 构建溯源明确：IDF **v5.4.1**（LEFT，2025-05-04 15:00:57）与 **v5.4.1-dirty**（RIGHT，2025-09-01 06:15:45）；RIGHT 的应用版本串是 git 描述 **`7d19c5c-dirty`**，LEFT 是默认值 **`1`**，两片工程名都还是 CMake 默认的 **`project-name`**——厂商没有在构建系统里写版本号。
3. 分区表为**单 app 槽**（factory 1MB）＋ nvs/phy_init/coredump/storage，**没有 OTA 槽**：现场升级只能走 USB 整片刷写，与官方 AIO 工具 `write_flash 0x0` 的行为一致。
4. 从 rodata 完整还原出**文本命令协议表**（`buttons()`、`buttons(`、`left()`、`right()`、`middle()`、`front()`、`wheel(`、`version`、`silent(`、`serial(`、`lock_mx()/(`、`lock_my()`、`lock_ml/mr/mm/ms1/ms2` 的 `()` 与 `(` 两种形式、`catch_*` 同名族），以及 `Original`/`Spoofed`、`Mouse does not have a serial number`、`%s Serial: %s` 等设备伪装/序列号相关文案。
5. 通过 Xtensa `l32r` 字面量池交叉引用，**恢复了厂商自带函数名到代码地址的映射**：LEFT 376 个标识符、RIGHT 244 个（含 IDF 符号）。厂商侧关键符号包括 `initialize_mouse_commit_task`、`MouseCommitTask`、`BezierTimer`、`bezier_timer`、`led_init`、`LedFlashTask`、`SERIAL_SETUP`、`UART0_Send_Task`、`UART0FrameConsumer`、`hid_parse_task`、`hid_data_processing`、`CommitFrame`、`EFUSE_BURN`、`crash_dump`、`BUTTON_LEFT/MIDDLE/RIGHT/SIDE1/SIDE2/BUTTON_6..16`。
6. 代码特征：IDF 默认 `-mlongcalls`，**所有调用都是 `l32r aN, .L` ＋ `callx8 aN` 的间接调用**；常规线性扫描得到的 CFG 很碎，必须做字面量池解析才能恢复函数边界（本报告已实现该解析器）。
7. 安全态势：镜像只有尾部 SHA-256 校验、**没有签名块**，也没有 flash 加密的标志；第三方固件可以刷进同一硬件，说明零售机**没有启用 Secure Boot 校验**。同时存在两处**不可逆 eFuse 写入**：`USB_PHY_SEL`（把内部 PHY 切到 OTG）与 `UART_PRINT_CONTROL`（V1.2 时代没有的第二处）。
8. 刷写副作用：整片镜像覆盖 `0x0–0x62850`，其中包含 `0x9000` 起的 NVS 区（镜像内该区为全 `0xFF`）——**整包刷写会清掉 NVS 里的配置（如 `baud_rate`）**，storage 区在 0x120000 之外不受影响。

## 1. 样本与哈希

| 文件 | 大小 | SHA-256 |
|---|---|---|
| `V3.2_LEFT.bin` | 403,536 | `ca7a71b40a7471bffabff86c6441fb05da1f07a8dbabae817d9bf5ab70a3a580` |
| `V3.7_RIGHT.bin` | 341,824 | `95940086eceda66d4259c27a81dd0153d559bcdee24613d4d877f5d37e0aa859` |

两片镜像结构一致（ESP32-S3，DIO，80MHz），但镜像头声明的 flash 容量不同：**LEFT 为 4MB，RIGHT 为 2MB**（bootloader 头 `flash_size` 字段分别为 `0x2` / `0x1`）。RIGHT 的分区最大到 `0x160000`（1.4MB），仍落在 2MB 之内，功能上不受影响，但说明两片的 bootloader 是分别用不同 flash 配置编译的：

| 段 | 文件区间 | 内容 |
|---|---|---|
| bootloader | `0x0` – `0x3A89` | ESP-IDF 二级引导，加载地址 `0x3FCE2810` 起 |
| 填充 | `0x3A90` – `0x7FFF` | `0xFF` |
| 分区表 | `0x8000` – `0x8FFF` | 5 条目（见 §4） |
| NVS | `0x9000` – `0xEFFF` | 镜像内为 `0xFF`（未预置数据） |
| phy_init | `0xF000` – `0xFFFF` | `0xFF` |
| app | `0x10000` – 文件尾 | 6 段镜像（DROM/DRAM/IRAM/IROM/IRAM/外设） |

应用镜像段布局（LEFT）：

| 段 | 加载地址 | 长度 | 区 |
|---|---|---|---|
| 0 | `0x3C030020` | `0x10B60` | DROM（字符串/常量） |
| 1 | `0x3FC93D00` | `0x3004` | DRAM（.data/.bss 初值） |
| 2 | `0x40374000` | `0xC484` | IRAM |
| 3 | `0x42000020` | `0x2F040` | IROM（代码） |
| 4 | `0x40380484` | `0x3794` | IRAM |
| 5 | `0x600FE100` | `0x1C` | 外设/RTC 段 |

RIGHT 的对应长度为 `0xA26C / 0x2C38 / 0x3144 / 0x26ACC / 0xCC00 / 0x1C`，代码量比 LEFT 少约 33KB。

## 2. 构建溯源

| 字段 | LEFT (V3.2) | RIGHT (V3.7) |
|---|---|---|
| app 版本串 | `1` | `7d19c5c-dirty` |
| 工程名 | `project-name`（默认值） | `project-name`（默认值） |
| 编译时间 | `May  4 2025 15:00:57` | `Sep  1 2025 06:15:45` |
| IDF 版本 | `v5.4.1` | `v5.4.1-dirty` |
| bootloader 编译时间 | `May  4 2025 15:00:59`（v5.4.1） | `Sep  1 2025 06:15:49`（v5.4.1-dirty） |
| app ELF SHA-256 | `7117afd8…ea24d967` | `a7b5aa28…9c9cafa592` |
| 镜像校验 | 尾部 SHA-256 合法 | 尾部 SHA-256 合法 |

要点：

- RIGHT 的 `7d19c5c-dirty` 是 `git describe` 风格的版本串，**说明右片在提交 `7d19c5c` 上带着未提交改动编译**；LEFT 仍是默认 `1`。
- 两片 bootloader 的编译时间不同（5 月 / 9 月），且 flash 容量配置不同（4MB / 2MB），**是两次独立构建，不是同一份产物**；LEFT 停在 2025-05，RIGHT 迭代到 2025-09。
- RIGHT 连 bootloader 都标 `v5.4.1-dirty`，说明右片是在**改过的 IDF 树**上构建的（或本地工具链配置被改动），与 `7d19c5c-dirty` 的脏版本串互相印证。
- `v5.4.1-dirty` 中的 `-dirty` 来自 IDF 自身的版本标记，通常表示构建时 IDF 树被改动过，或工具链配置被本地修改。

## 4. 分区表

两片一致，仅 storage 大小不同：

| 名称 | 类型 | 子类型 | 偏移 | 大小 | LEFT | RIGHT |
|---|---|---|---|---|---|---|
| nvs | data | nvs | `0x009000` | 24 KB | ✓ | ✓ |
| phy_init | data | phy | `0x00F000` | 4 KB | ✓ | ✓ |
| factory | app | factory | `0x010000` | 1 MB | ✓ | ✓ |
| coredump | data | coredump | `0x110000` | 64 KB | ✓ | ✓ |
| storage | data | nvs | `0x120000` | 128 KB / 256 KB | 128 KB | 256 KB |

由此可得：

- **没有 `otadata`、没有 `ota_0/ota_1`**：不支持 A/B 升级，升级＝整片重刷。
- app 分区 1MB，实际应用仅 330KB / 270KB，**剩余空间足够塞入自定义逻辑**。
- `coredump` 分区存在，配合 `crash_dump` 符号，说明崩溃会落盘，可用 `esptool read_flash 0x110000` 取回分析。

## 5. 协议与功能面（rodata 还原）

命令判定用的是**片段匹配**（`strncmp` 前缀比较，长度取自表项），所以表中同时存在 `xxx()` 与 `xxx(` 两种字面量：前者匹配无参调用，后者匹配带参调用。

> 第二轮已定位到真正的**表驱动分发器**：命令表 `0x3C03DF74`（43×20 字节）+ opcode 跳表 `0x3C03DF08`（27 项），完整协议见 [官方固件命令协议.md](官方固件命令协议.md)。

## 7. 代码特征与已定位逻辑

### 7.1 调用约定：全间接调用

```
0x40375510  entry a1, 0x70
0x40375513  l32r  a8, . 0x40374404     ; 取函数指针
0x40375516  wsr   a8, vecbase
0x4037551c  l32r  a8, . 0x403744c0
0x4037551f  callx8 a8                  ; 间接调用
```

IDF 默认 `-mlongcalls`，所有 `call` 都被编译成「字面量池取址 + `callx8`」。这带来两个后果：

- 反汇编器的线性扫描看不到直接调用目标，**函数发现率极低**（Rizin `aa` 在本样本上只识别出 1 个函数）；
- 必须解析 `l32r`（RI16 格式：`target = ((PC+3) & ~3) + (int16)imm << 2`）才能恢复调用图与数据引用。

本报告的实现：`tools/l32r_xref.py`，在 IROM/IRAM 上逐字节解码 `l32r`，把命中的字面量值映射回 rodata 字符串，得到 1361（LEFT）/ 1059（RIGHT）条引用、760 / 609 个被引用字符串。

### 7.2 已定位的函数体

`initialize_mouse_commit_task`（`0x4200F83C` 起）呈典型的「建队列 → 建定时器 → 建任务」序列：

```
0x4200F83C  entry a1, 0x30
0x4200F83F  l32r  a8, . 0x42000664
0x4200F842  l32r  a15, . 0x42000e08
0x4200F845  l32r  a12, . 0x42000988
0x4200F848  l32r  a11, . 0x42000e5c     ; ← "MouseCommitTask"
0x4200F84E  s32i  a8, a1, 0
0x4200F851  movi  a14, 8
0x4200F857  l32r  a8, . 0x420004b0
0x4200F85A  callx8 a8                   ; xTaskCreate(...)
0x4200F863  l32r  a8, . 0x42000e7c
0x4200F866  callx8 a8                   ; 队列/信号量
0x4200F87E  l32r  a8, . 0x42000e80
0x4200F881  callx8 a8                   ; xTimerCreate(...)
```

`EFUSE_BURN`（`0x42011188` 起）先读后写的顺序与 V1.2 的 `burn_usb_phy_sel_efuse()` 一致（先 `esp_efuse_read_field_bit` 判已烧，再 `esp_efuse_write_field_bit`），并额外出现 `UART_PRINT_CONTROL` 分支。

## 8. 安全与可改性

| 项 | 观察 | 影响 |
|---|---|---|
| 镜像签名 | 只有尾部 SHA-256，无签名块 | 自编译镜像可被引导器接受 |
| Secure Boot | 无相关分区/标志；第三方 Medius 固件可刷入同款硬件 | 引导器**未启用**签名校验 |
| Flash 加密 | 无迹象（AIO 工具直接写明文 bin） | 可用 `esptool read_flash` 读回整片 |
| eFuse | `USB_PHY_SEL`（不可逆）、`UART_PRINT_CONTROL`（不可逆） | 烧写后 PHY/打印通道固定，误烧影响 USB 枚举与日志 |
| OTA | 无 OTA 槽 | 升级必须 USB 整片刷写 |
| 调试口 | 外部 BOOT 按键 + ROM 下载模式 | 变砖可救，但 DTR/RTS 未接复位，需手动按住 BOOT |
| 整片刷写副作用 | 覆盖 `0x0–0x62850`，含 NVS | 会清空 `baud_rate` 等 NVS 配置 |

## 9. 逆向方案（分阶段，可复用）

### 阶段 0：环境（本机已就绪）

| 组件 | 状态 | 说明 |
|---|---|---|
| REA CLI 6.7.0 | ✅ 已装（`C:\Users\abao\AppData\Roaming\npm\rea.cmd`） | `rea doctor` 通过 Node/主机检查 |
| REA 原生分析引擎 | ⚠️ 未配置 | Windows 版 Ghidra P0 仅接受 x86/x64/ARM/6502；Xtensa 需另装引擎 |
| REA 固件分区检查 | ⚠️ 平台限制 | `inspect-firmware-regions` 返回 `capability_unavailable`，要求 Linux + binwalk |
| Rizin 0.9.1 | ✅ `tools/rizin/.../bin/rizin.exe` | 原生支持 `xtensa`，可反汇编并解析 `l32r` |
| Ghidra 12.2（独立） | ✅ `D:\Apply\Ghidra`（JDK 25：`D:\Apply\Java\jdk-25`） | 自带 `Xtensa:LE:32:default` 处理器模块；对 `work\*_app.elf` 自动分析出 1439 / 1630 个函数 |
| esptool 5.6.0 | ✅ `python -m esptool` | `image-info` 可直接读镜像头/段表 |

REA 可用路径：`rea execute-rizin-command <elf> '<rizin cmd>'`，返回带 `evidence_id` 的证据记录。已用其完成本节的一次反汇编取证（`ev_e8787689…c73bb`）。

### 阶段 1：结构提取（已交付脚本）

```powershell
python tools/report.py "官方固件\V3.2_LEFT.bin"      # 镜像/分区/字符串 + vaddr
python tools/esp_to_elf.py "官方固件\V3.2_LEFT.bin" work\V3.2_LEFT_app.elf 0x10000
python tools/l32r_xref.py "官方固件\V3.2_LEFT.bin" "官方固件\V3.2_LEFT.bin.strings.json"
python tools/names.py "官方固件\V3.2_LEFT.bin.xref.json" > work\names_left.txt
```

产物：`*.strings.json`（字符串＋虚拟地址）、`*.xref.json`（代码→字面量→字符串）、`work\*_app.elf`（六段 ELF，可直接喂 IDA/Ghidra/rizin）。

### 阶段 2：符号化（已交付）

1. 用 `names.py` 得到「名称 → 引用地址」表；
2. 用 `func.py <addr>` 回溯最近的 `entry a1, N` 序言，确定函数入口；
3. 在 IDA/Ghidra 里按表批量重命名，形成 `.idc`/`.py`/`.gzf` 符号脚本。

验收标准：厂商符号命中率 ≥ 90%，每个重命名都有 `rodata 字符串 → l32r → 代码地址` 的证据链。

### 阶段 3：函数级重建（需 Xtensa 反编译器）

推荐两条路线，任选其一：

- **IDA 9.x + Xtensa 处理器模块**：对 `-mlongcalls` 与 `l32r` 支持最好，能自动识别字面量池并恢复调用图；直接打开 `work\*_app.elf`，按段加载。
- **Ghidra 12.x + ghidra-xtensa 扩展**：免费路线；安装后在 Ghidra 中导入 ELF，语言选 `Xtensa:LE:32:default`，再跑 headless 脚本批量重命名。

优先级函数清单：

## 10. 风险与边界

- **eFuse 不可逆**：`USB_PHY_SEL` 与 `UART_PRINT_CONTROL` 一旦烧写不回退；刷任何自编译镜像前先确认这两位的现状。
- **整片刷写会清 NVS**：镜像覆盖 `0x0–0x62850`，NVS 区在镜像里是 `0xFF`；需要保留 `baud_rate` 等配置时，先单独 `read_flash 0x9000 0x6000` 备份。
- **双片不可混刷**：LEFT/RIGHT 段布局与功能不同（左片含命令表与 HID 设备侧，右片含 USB Host），刷反会失去枚举能力。
- **供电**：官方文档要求刷写时只插一根线（USB1/USB3 同时上电有倒灌风险）。
- **合规**：样本用于兼容性/互操作研究与自有设备维护；涉及规避检测、对抗反作弊的改造不在本报告范围。

### 12.11 片间链路与 C 级重写样板

**（1）UART1 片间帧解出**：

- 右片 `hid_uart_task`（`0x4200FE68`）从队列取包，按 `*(uint16_t*)(pkt+2) + 4` 计算总长，经 `uart_write_bytes(UART_NUM_1, ...)` 发出 → **帧 = 4 字节头 + 负载，头的 `+2` 是 16 位负载长度**；
- 左片 `uart_event_task`（`0x420139E4`）安装 UART1 并起 `uart_events` / `hid_data_processing` / `hid_parse_task`；
- 左片 `FUN_42013734` 只处理 `hdr[1] == 0xA0` 的帧，按 `hdr+2` 的类型位调用 `usbd_ep0` 完成 **USB 控制传输隧道**，其余忽略。

因此 UART1 也不分发隐藏 opcode：13 个隐藏处理函数在两条外部链路上都不可达，判定为遗留/变体保留（需上机断点才能最终确认）。

**（2）缺口函数 C 级重写样板**：`reversed/docs/reconstruction_patterns.md` 给出 `cmd_move` 的完整重写（解析 5 个 int16、`n==2` 走 `mouse_move`、`n==5` 走 `mouse_submit_ext` 且第 3 参限 1..1024、统一回执）与 `cmd_channel_toggle` 的部分重写（标出 3 处未确认字段）。

**（3）兜底块对齐修复**：此前 objdump 是整段线性反汇编，遇到数据字节会漂移，导致部分函数块起点错位。现在改为**按函数入口单独反汇编**（153 次 `--start-address`），`cmd_channel_toggle` 的首行已正确回到 `4200e56c: entry a1, 48`。


### 12.12 UART1 帧格式定版 + lock 族重写

**（1）片间帧格式已完整**：右片三个帧构造器（`0x420102A8`、`0x4200FAC0`、`0x4200FAE0`）写法一致：

```
5A <cmd> <len:u16> <payload…>
```

- `+0` 魔数 `0x5A`（'Z'）；
- `+1` 命令：`0xA0` EP0 隧道、`0xA1`、`0xA2` 数据/事件、`0xA3`；
- `+2..3` 负载长度（不是类型）；
- `+4` 起是负载，左片读到的 `+4/+5/+6/+8` 其实是 `payload[0..4]`。

这推翻了上一轮记录的两处“不一致”：`0xA0` 分支的 `==1` 是**负载长度为 1**；`+8` 属于负载而非头部溢出。

**（2）`lock_*` 四兄弟重写**：`cmd_lock_query` / `cmd_lock_axis` / `cmd_lock_param0` / `cmd_lock_param2` 分别对应「查询状态 / 查询轴向 / 设开关 / 设轴向参数」，且 `lock_m*(0)` 会连带 `catch_set(...,0)` 并清 dirty 标志。四者共用 `ctx+0x210` 的两张子表（`+0x54` 按键、`+0x9C` 轴向）。

### 12.14 0xA2 帧写入侧闭合

`0x4200FF10`（USB 事件回调）里找到 0xA2 构造，负载字段与左片过滤条件完全对应：`payload[0]=端点号`（`client+0x8F`，对应描述符 `+0x62/+0x1d5`）、`payload[1]=会话 id`、`payload[2]=长度`、`payload[3]=0`。至此 UART1 两种帧（0xA0 EP0 隧道、0xA2 HID 上报）都有写入侧与读取侧证据，仅剩长度字段的口径需要抓包核对。

## 13. 第 7 轮（2026-11-09）：`excw` 突破、隐藏 handler 补齐、长度口径闭合

### 13.1 153 个只有汇编的函数，压到 17 个

根因不是“Ghidra 不支持 Xtensa”，而是固件里 812 处三字节指令（binutils 译作
`excw`）被 Ghidra 当成控制流终止。做法：

1. `tools/patch_excw.py`：按**函数入口对齐**反汇编找出这些指令的真实地址，
   换成 `and aN, aN, aN`（同寄存器 no-op），写出 `work/*.nop.bin`；官方镜像
   一个字节都不动；
2. `tools/esp_to_elf.py` 重建 ELF，`analyzeHeadless` 重新反编译；
3. 结果：**LEFT 1440 个函数里 1428 个、RIGHT 1629 个里 1624 个**拿到真实 C，
   相当于把 136 个函数从“汇编兜底”升级为“可读 C”。

仍然保留汇编兜底的只剩两类（`docs/known_gaps.md`）：

- 10 + 5 个 Ghidra 仍报 pcode 错误的函数（body 太长 / 另有未译码指令）；
- `cmd_silent`、`cmd_channel_toggle` 两个——`excw` 落在前置校验里，补丁版会把

### 13.2 两个“只在跳表里”的 handler 被找回来

opcode 跳表 `0x3C03DF08` 有两项指向的地址，Ghidra 从未建成函数（没有 `call8`
调用点，前后还被 `ill` 填充隔开）：

| opcode | 地址 | 名字 | 语义 |
|---|---|---|---|
| 0x16 | `0x4200E624` | `cmd_map_entry` | `"<index>,<value>"` 写映射表项，两值非零才写，写后回显 |
| 0x1A | `0x4200DC84` | `cmd_serial` | 序列号接口：`serial()` 查询（`Original:`/`Spoofed:`）、`serial(0)` 恢复原厂、`serial("<串>")` 写伪装值 |

补法：`tools/ghidra_scripts/MakeFuncs.java` 在补丁版工程里按地址建函数、导出

3069 → **3071**。

同时反证了 `uart0_reply` 的封装是 `"km." + 内容 + "\r\n>>> "`。

### 13.3 UART1 长度口径闭合（问题 #3、#5）

`0x4200F6C4` 的每个分支都是「先写负载，再把 `+2` 写成负载字节数」，或写
`len=1 / payload=0xFF` 的错误帧：

| 命令 | 处理 | `+2` | 负载 | 总长 |
|---|---|---:|---|---:|
| 0xA0 | `frame_ep0_dir` | 1 | 方向字节 | 5 |
| 0xA3 | `frame_a3_flag` | 1 | 0x00 | 5 |
| 0x1A | `0x4200F854` | `min(n,0x14)+1` | 状态 + n 字节快照 | 4+1+n |
| 0xA1 | `0x4200FC74` 三子分支 | `读回-8` / 0 / 1 | 报告 / 无 / 0xFF | 见 `uart1_link.md` §8.3 |
| 0xA4 | `0x4200FE44` | 1 | 状态 | 5 |
| 0xB1 | 无 | 不写（缓冲已清零） | — | 4（纯头） |

0xA2 的“字段多 4”也解释清楚：它的负载是 `[ep, id, len, 0, data…]`，头后共
`4+len` 字节，所以字段写 `len+4` 是对的。**`+2` 恒等于“头后字节数”，总长 =
字段+4。**

分派表缺 0xA2 不是漏写：`0xA2` 只在右→左方向出现、由左片 `0x42013734` 消费；
右片接收状态机只处理左→右的帧。

### 13.4 `cmd_silent` 的真身：静默移动

硬件实测：`silent()`/`silent(0)`/`silent(1)` 零回包，`silent(0,0)` 回
`km.silent(0,0)\r\n>>> `。据此 + 汇编骨架，语义确定为：参数解析与 `cmd_move`
同构，`<2` 个参数静默返回，`n==2` 走 `pulse_move`（移动→等信号量→反向移动），
`n==5` 走扩展提交，3/4 参把第 3 个值当档位。这也修正了 `cmd_move` 的旧描述：
3/4 个参数**会移动**，不是不动作。

## 14. A 组待办执行结果（2026-11-09 第二轮）

### 14.1 A1：软浮点例程按 fdlibm 系数逐位定名（问题 #6 闭合）

方法：`tools/dump_consts.py` 把函数引用的字面量池当 double 读出来，与 fdlibm /
newlib 的已知系数做**位级比对**（不看形状猜，看常数）。

| 地址 | 判定 | 决定性常量 |
|---|---|---|
| `0x4201EBE8` | **`__kernel_cos`**（k_cos） | C1..C6 = `3FA555555555554C` / `BF56C16C16C15177` / `3EFA01A019CB1590` / `BE927E4F809C52AD` / `3E21EE9EBDB4B1C4` / `BDA8FAE9BE8838D4`，另有阈值 0.3 与 0.78125 |
| `0x4201ED60` | **`__kernel_sin`**（k_sin） | S1..S6 = `3FC5555555555549` / `3F8111111110F8A6` / `BF2A01A019C161D5` / `3EC71DE357B1FE7D` / `BE5AE5E68A2B9CEB` / `3DE5D93A5ACFD57C` |
| `0x4201EEcc` | **`__ieee754_rem_pio2`** | 2/π = `0.6366197723675814`、pio2 分段常量；返回象限 `n`，写 `y[0]/y[1]`（调用方都做 `n & 3`） |
| `0x4201F2D8` | **`__kernel_rem_pio2`** | 被 rem_pio2 在大参数分支调用，自带 2/π 长表 |
| `0x4201EA4C` | **`__ieee754_cos`** | 象限 1 → k_sin、0/2 → k_cos（cos 的符号表），后接符号异或 |
| `0x4201EAC8` | **`__ieee754_sin`** | 象限 1 → k_cos、0/2 → k_sin（sin 的符号表） |
| `0x4201FA38` | **`__ieee754_floor`** | 「已整数则原样返回」+ `0xfffff >> e` 尾数掩码 + 负数补 `0x100000 >> e` |
| `0x4201FB6C` | **`__ieee754_scalbn`** | 指数加 `n`、`0x7fe` 上溢、`-0x35` 下溢、`2^54`/`2^-54` 处理次正规 |
| `0x4201EB48` | **`__fixdfsi`** | 指数/尾数移位 + 符号乘法，越界转 ROM 辅助 |

`sin`/`cos` 的区分依据是**象限到核函数的映射表**，不是名字顺序：cos 的
`n&3==1` 走 k_sin，sin 的 `n&3==1` 走 k_cos。

顺带确认：`mouse_submit`（`0x4200EFEC`）确实调用 `cos`/`sin`/`__fixdfsi`，
即「Bezier/平滑」路径是在双精度里做三角运算再截断成整数坐标。

### 14.2 A2：`usb_event_handler`（`0x4200FF10`）的分派结构

事件的两种形态可以从代码直接读出（`param_2`）：

| `param_2` | 分支动作 |
|---|---|
| `>= 1` | 传输完成，长度 = `param_2`：填 0xA2 帧（`[4]=端点号`、`[5]=端点字节`、`[6]=长度`、`+2 = 长度+4`），投递到 UART1 队列，然后重挂传输 |
| `== -10` | 断连/复位类事件：重建传输描述符（`wMaxPacketSize`、包大小位、回调 `PTR_FUN_42000d74`、上下文）并 `usb_xfer_submit(0x4200D3E4)` |

端点解码是硬观察：`ep = bVar1 & 0xf`（端点号）、`bVar1 & 8` = IN 方向；每端点状态在
`DAT_42000D68 + ep*0x24`，环形缓冲下标 `+0x20` 用 `(i+1)&7` 轮转（8 格）。
`usb_xfer_submit`（新增命名）负责提交刚填好的传输，失败返回 `-2`（句柄/缓冲/回调为空）。

仍开放：事件码不是 tinyusb/ESP-IDF 的 `USBD_*` 枚举，而是这套自定义 host 驱动的
状态码（只有 `-10` 与「正数=长度」两种语义被证实）。要完全枚举需要该驱动的头文件。

### 14.3 A3：`cmd_channel_toggle` 的索引入口（问题关闭）

用**不同对齐起点**重新反汇编 `0x4200E56C` 段，在 `0x4200E59E` 找到了被错位的真代码：

```
4200e59e:  or    a10, a6, a6        ; a10 = arg
4200e5a1:  s32i  a11, a1, 0         ; 保存 arglen
4200e5a4:  call8 0x4200E458         ; parse_int_or_char(arg, arglen) -> a10
4200e5a7:  movi  a8, 255
4200e5aa:  bltu  a8, a10 -> reply   ; idx > 255 直接回执
4200e5ad:  l32i  a14, a4, 0x214     ; dev->tbl
4200e5b3:  add   a14, a14, a10      ; + idx
4200e5b8:  l8ui  a8, a14 + 0x369    ; 存在位
4200e5bb:  beqz  a8 -> reply        ; 通道不存在 → 只回执
```

所以 **`idx` 就是 `parse_int_or_char(arg, arglen)` 的返回值**，范围 0..255；
`+0x369` 是「存在位」、`+0x269` 是「启用位」，与 `cmd_dump_channels`（`0x4200DBB0`）
遍历同一对表一致。剩下的歧义只在入口那 3 字节未知指令，不影响语义。

**副产物（通用结论）**：GCC 会在函数内部插入 2/3 字节的**零填充**（循环/分支对齐），
两种反汇编器都会把这些字节当指令吃掉，导致后续整体错位 —— `0x4200E59C` 处的
`00 00` 就是这种情况。以后遇到「某函数中段突然变成乱码」，先按 ±1/±2 重对齐，
再去怀疑 `excw`。

### 14.4 A4：13 个 pcode 错误的函数（负结果）

把 Ghidra 报错地址前的零填充换成等长 no-op（`tools/patch_padding.py`）后重跑：
**失败数没有变化**（LEFT 仍 10 个）。说明这些函数的阻塞点不是填充错位，而是 Ghidra
的 Xtensa 模块缺少对应指令构造器（报错地址处 binutils 能正常译码，例如
`0x42020D8D` 的 `beqi`）。这些函数全是 IDF 内部（freertos/heap 的红黑树、分区表等），
对产品语义没有影响，**决定不为它们造补丁**：保持「17 个兜底块」的状态。

### 14.5 A5：源码树可编译化（不做，理由入档）

`src/*.c` 是反编译产物：没有原始头文件依赖、参数个数靠调用点恢复、跳表调用使原型
无法自洽。把它做成可编译需要重建整套 IDF 头文件与类型，工作量大且不产生新结论。
本轮只保证**头文件声明自洽**（26 个模块头 `-fsyntax-only` 全通过，见 `docs/headers.md`）。
