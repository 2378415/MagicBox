# 上机记录：2026-11-09 第二十批（真实两片流量打通，卡在“送入主机”这一公里）

> 这一轮把“两片真机联调”从不可能推到**真实 `0xA2` 帧每秒上千条进入左片**，
> 并定位到最后一个瓶颈：把 1 kHz 的报告流灌进 TinyUSB 的 IN 端点会被协议栈的 claim 机制吃掉。
> 过程中一度把板子烧进看门狗循环（已回退构建，待手动进下载模式重烧）。

## 1. 三个关键事实（都来自实测）

### 1.1 右片真的在转发，但需要左片先“宣告”

`0x4200FF10`（右片 USB 事件回调）里，`0xA2` 只有满足 `*DAT_42000d48 != 0` 才入队；而写这个
标志的唯一位置是 `frame_a3_flag`（`0x4200FAE0`）——**左片发一帧 `0xA3` 才会置位**，
设备掉线时 `frame_build_ep0(0)` 会把它清 0。

实测：`mx.ln a3 00` 之后，右片立刻开始转发：

```
21:48:41  frames 12085  hid 11818  injected 11818  rx_bytes 154968   delta 1025,0,0,0,1024,1,0,0,0,1024,0,13317
21:48:42  frames 13217  hid 12949  injected 12949  rx_bytes 169676   delta 1132,0,0,0,1131,1,0,0,0,1131,0,14708
```

`hid ≈ injected`、每秒约 1,100 帧，正是 1 kHz 鼠标。

### 1.2 真实 `0xA2` 的字节布局

`mx.lr`（最后一帧原始字节）+ `mx.ei`（注入体）：

```
lr -> cmd=a2 len=9 data=00 81 05 00 00 00 10 00 00
ei -> 00 00 10 00 00
```

即 `[ep=0x00, session=0x81, len=5, 0, data(5B)]`，与 `uart1_link.md` §8 的
`[ep, id, len, 0, data…]` 完全一致；数据体 5 字节（buttons / dx / dy / wheel / 第 5 字节）。

### 1.3 设备枚举是稳的（之前的 00↔ff 是插拔造成的）

停止插拔后连续 8 次采样 `mx.ln a0` 全为 `data=00`（`*DAT_42000d88` 非 0 = 有就绪设备），
`0xA1` 长帧也从“错误帧”变成 `len=0` 的纯头回包，说明右片确实进了 URB 路径。

## 2. 最后一个瓶颈：1 kHz 灌 HID 端点

新增 `mx.hv`（注入侧）与 `mx.hs`（所有 HID 发送侧）两组计数：

| 计数 | 读数 | 含义 |
|---|---|---|
| `mx.hv` | `attempts=1573 sent=12 not_ready=293 wake=0 no_mount=0 mnt=1` | 只有 **0.76%** 的报告真正发出 |
| `mx.hs` | `ok=7 busy=0 failed=93 no_mount=0 mnt=1` | 端点从不“忙”，但 `tud_hid_report()` 大量返回 false |

对照 TinyUSB 源码 `tud_hid_n_report()`：返回 false 只有两条路径——`usbd_edpt_claim()` 失败、
或 `usbd_edpt_xfer()` 失败；而 `tud_hid_ready()` 只看 `usbd_edpt_busy()`。两者不一致说明
**claim 被占用却没在传输**（一次被拒的 xfer 会把 claim 泄漏），于是后续几乎全部失败。

单帧测试（重启后只发一条）`mx.hv` 为 `1,1,...`，说明**低频下发送路径是好的**——问题在速率。

## 3. 一次失败的修复（已回退）

按“队列 + 排空任务”改造（`km_hid_tx`，通知驱动 + 每 2 ms 一条）后：

```
E (60100) task_wdt: Task watchdog got triggered. - IDLE0 (CPU 0)
E (60100) task_wdt: CPU 0: km_hid_tx
```

IDLE0 被饿死，控制台任务也停摆（`version` 无回包、`mx.dl` 收不到），板子只能手动进下载模式。
**已把 `makcu_hiddev_report_raw()` 回退成直发版本并重新构建**（`app_left/build/makcu_left.bin`，
301,136 B，21:58），源码里保留队列/排空代码与 TODO，等这次恢复后按下面的设计重做。

## 4. 下一步设计（明确的方向）

1. **不要从链路任务直接灌端点**：队列保留，但排空必须由 **HID 任务上下文**（或 `tud_task`
   的空闲回调）驱动，每次只在 `tud_hid_ready()` 为真时发一条，并且不在 `for(;;)` 里自旋；
2. **合并位移**：队列满时把丢弃的位移**累加**进下一条（相对位移可加），避免丢动作；
3. **上电自动宣告**：`makcu_link_bridge_init()` 里发一次 `0xA3`，并在设备掉线后重发
   （否则右片永远不转发——这是本轮最重要的发现）；
4. 5 字节报告与克隆描述符（4 字节）不匹配：要么把 fixture 换成 5 字节形状，要么按
   `report_len` 截断/映射，避免主机端解析错位。
