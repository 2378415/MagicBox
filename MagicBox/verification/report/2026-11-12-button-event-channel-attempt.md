# 2026-11-12 按键独立事件通道：两次上机尝试与回退

> 只记录事实与结论，供后续接手者避免重走。代码最终回到尝试前的状态（固件 347,936 B）。
> 未提交 git（按用户要求）。

## 1. 目标

持续 62.5 次/秒（600 点击 @8 ms，AIM 1 kHz 并发）下做到"边沿一条不多、一条不少"。
此前的观测：短时（150 点击 ≈2.4 s）5 轮 300/300 全 PASS；持续 10 s 出现 1164–1200/1200。

## 2. 设计（离线模型已验证）

`verification/model/test_button_event_channel.py`（5 例全绿，模型目录 46 passed）证明的契约：

1. 按键状态**只由事件队列改写**（`EventQueue`，深 128，满了计数不丢序）；
2. 运动报告**在发送时刻**取"最近一次真正上线"的按键字节（`Writer`）；
3. **唯一写者**：先清事件、再发运动；同值上线只算重复，不产生边沿。

模型结论：1200 次变化 → 1200 个边沿、0 重复、最坏延迟 ≤3 ms。

## 4. 上机结果：两次启动即挂

| 版本 | 任务栈 | 现象 |
|---|---|---|
| v1 | `km_btn` 栈 **3072** | 刷入后 USB 侧**完全不枚举**（只剩 CH343），控制台无输出 |
| v2 | `km_btn` 栈 **4096** | 同上 |

- 两次都是 `esptool` 写入 `Hash of data verified` 成功后，硬复位即失联；
- 说明是**启动阶段 panic**（且来不及输出日志 / USB 侧没起来）；
- 回退后（`git checkout` + 重新构建 347,936 B + 刷回）设备恢复正常：`km.MAKCU`、克隆 5 个 HID 集合、真机 9/9、模型 46 passed。

### 恢复（救砖）流程（已两次验证有效）

1. 拔线 → **按住 BOOT(IO0)** → 插线 → 松手 → 芯片进 ROM 下载器；
2. `esptool --chip esp32s3 --port COM8 --baud 115200 --before no_reset chip_id` 确认同步；
3. `write_flash 0x0 bootloader / 0x8000 partition-table / 0x10000 makcu_left.bin`；
4. 启动：优先 `COM9`（USB-JTAG）`--after hard_reset flash_id`（打印 "Hard resetting with a watchdog"）；
   若 COM9 被泄漏句柄占死（`PermissionError(13)`），**拔插电源**让应用启动。

## 5. 一处必须记住的推断纠错

之前把 `0x3E` 的 `pin` 少（667/1200）当作"引擎合并丢键"的证据 —— **错的**。
`pin` 只统计"进过 URG 队列"的按键报告；端点空闲时报告是**直发**的，不计数。
因此"持续 62.5 次/秒少 1.5–3%"的真因**仍未定位**，不能再用 `pin` 反推合并。

## 6. 下一步（拿到证据再改代码）

1. **JTAG 抓 panic**：用 openocd + xtensa gdb 连 MI_02，跑挂掉的版本读 backtrace（工具链已通，驱动缺口此前已修）；
2. **最小化新任务**：`km_btn` 只入队 + 计数、不调用 hook，先证明"新任务本身不犯规"，再逐项打开；
3. **补直发路径计数**：把"直发引入的按键变化数"与"队列引入的变化数"分开统计，
   才能把少掉的 1.5–3% 定位到直发还是队列；
4. 在 1–3 有结论前，**不再改发送路径、不再新增任务、不再盲刷**。

## 8. 追加：取证固件（只加计数，不改行为）

在回退版基础上只加两个计数器（`0x45` 扩到 50 B）：

| 偏移 | 字段 | 含义 |
|---|---|---|
| 42 | `direct_chg` | 直发路径上"引入按键变化"的报告数 |
| 46 | `queued_chg` | 队列（URG）路径上"引入按键变化"的报告数 |

实测（600 点击 @8 ms + SUMV@12 ms，连续 **5 轮**）：

```
direct_chg +694~722   queued_chg +497~514   两者之和 == 1200（每轮都精确）
wire_chg  +1200       PC 边沿 1200          5/5 PASS
```

结论修正（重要）：

1. **持续 62.5 次/秒在"干净队列"状态下是稳的**（本轮 5/5 1200/1200，每轮 ≈9.6 s）；
2. 之前那次 1164–1200 的失败，伴随 `wait_max ≈59 ms`、URG 有积压 —— 更可能是**前序压测留下的队列积压**造成的，
   不是稳态行为；后续压测前应先 `mx.rs` 重启或等队列排空；
3. `direct_chg + queued_chg` 恰好等于注入变化数，说明**每条变化都只被引入一次**，没有合并、没有多发；
   这条等式以后可以直接作为"零丢失/零多发"的固件侧判据。

## 9. 边界扫描（2026-11-12 13:5x，固件 348,144 B = 回退版 + 取证计数）

每档 2 轮，每轮 ≈10 s，二进制 `0x32` 注入 + SUMV@12 ms 并发：

| 速率 | 结果 | direct+queued / 期望 | 备注 |
|---|---|---|---|
| 55 次/秒（9091 µs，550 点击） | **2/2 PASS** | 1100/1100 | — |
| 60 次/秒（8333 µs，600 点击） | **2/2 PASS** | 1200/1200 | — |
| 65 次/秒（7692 µs，650 点击） | **0/2** | 1284/1300、1290/1300 | 每轮约 1.2% 变化**从未被引入**（不是队列丢） |
| 65 次/秒 + `mx.hk 0`（隔离真实鼠标透传） | **2/2 命中** | 1299/1300、1300/1300 | 隔离后基本无丢 |
| 70 次/秒 + `mx.hk 0` | **2/2 命中** | 1400/1400、1398/1400 | 隔离后仍然干净 |

附加取证：`0x45` 新增 `0x32` 帧计数（偏移 50）。65 次/秒时 **收到 1300/1300 帧**，
所以丢的不是传输层，而是"状态变化没被引入"。

### 结论（更新）

- **上限 ≈60 次/秒（真实设备在环）**：55/60 两档 2/2 PASS；
- 65 次/秒开始出现 ~1.2% 丢失，**隔离 `0xA2` 透传后消失**（65/70 都干净）→
  说明丢的原因是**真实鼠标的透传报告与注入按键状态互相覆盖**（同一根线上两个状态源），
  不是队列、不是注入传输、也不是引擎合并；
- 下一步若要继续提上限，方向应是"注入按键期间屏蔽透传按键位"（而不是改发送架构）：

  1. 注入模式（`0x32` 有活跃按键状态）时，透传报告按键位改用"注入状态"，而不是真实鼠标的字节；
  2. 或者给透传报告加同样的"状态戳印"，让两个源在线上收敛到同一个按键状态；
  3. 判据依旧是 `direct_chg + queued_chg == 注入变化数` 且 `wire_chg == 期望边沿`。

## 10. 按第 9 节方向落地：注入主持权窗口（2026-11-12 14:0x，固件 348,320 B）

实现（只改一处入口，不动发送架构）：

- `control_bin` 的 `0x32 BUTTON`：先 `makcu_hiddev_btn_hold_ms(200)`，再 `makcu_mouse_set_buttons()`；
- `app_main` 的透传转发改调 `makcu_hiddev_passthrough()`；
- `makcu_hiddev_passthrough()`：主持权窗口内，把透传报告的按键位对齐到 `s_wire_btn_last`
  （运动字节原样保留）；窗口外行为不变（物理点击照常生效）。

### 复测（真实设备在环，二进制注入 + SUMV@12 ms）

| 速率 | 结果 | wire_chg / 期望 |
|---|---|---|
| 55 次/秒 | **2/2 PASS** | 1100/1100 |
| 60 次/秒 | **2/2 PASS** | 1200/1200 |
| 65 次/秒 | 3 轮 **±1** | 1299/1300 ×3（测一次 1301） |
| 70 次/秒 | **2/2 PASS** | 1400/1400 |
| 75 次/秒 | **2/2 PASS** | 1500/1500 |
| 80 次/秒 | ±1 | 1599/1600 ×2 |

结论：

- 上限从"≈60 次/秒"提升到 **≥75 次/秒（严格 0 误差）**，65/80 档只差 1 个边沿（≈0.08%，方向不固定）；
- 剩余 ±1 属边界效应（注入事件与透传报告同一毫秒交错），不再是"整批 1.2% 丢"；
- 人手/连点宏（≤20 次/秒）完全无感；App 的注入场景（典型 ≤10 次/秒）余量 7 倍以上。

## 11. 追 80 次/秒的最后 1 个边沿（2026-11-12 14:1x，固件 348,512 B）

两次针对性修复：

1. **持权窗口内同步线上状态**：`app_main` 在 `makcu_hiddev_btn_hold_active()` 时用
   `makcu_hiddev_btn_wire_state()` 同步 `s_buttons`（原来同步真实鼠标字节，会把注入的按下改回 0，
   导致随后的"松开"被当成无变化）。
2. **注入事件强制立即上线**：新增 `makcu_mouse_emit_event()`（`0x32` 用它替代 `set_buttons + emit_now`），
   不再受 2 ms 让路窗口影响。

复测（800 点击 @6250 µs = 80 次/秒，AIM 并发）：

| 修复后 | 结果 |
|---|---|
| 80 次/秒 ×3 | 1599/1600、1599/1600、1600/1600（仍 ±1） |
| 70 次/秒 ×2 | 1400/1400 ×2 **PASS** |
| 75 次/秒 ×2 | 1500/1500 ×2 **PASS** |

取证（`0x45` 拆分计数）：

```
0x32 帧 +1600/1600（传输不丢）
direct +720 / queued +881 → 和 1601（多 1）
另一轮 direct +742 / queued +857 → 和 1599（少 1）
```

→ 80 次/秒下仍有 **±1**（0.06%），两轮方向不同，属"注入事件与运动/透传报告同一毫秒交错"的竞态；
`direct+queued` 与 `wire_chg` 始终相等，说明是"同一个变化被算多/算少一次"，而非整批丢失。

### 边界（最终）

| 速率 | 结论 |
|---|---|
| ≤75 次/秒 | **严格 0 误差**（多轮 PASS） |
| 80 次/秒 | ±1 边沿（0.06%），方向不固定 |

要彻底消掉 80 档的 ±1，只能回到"单写者事件通道"（push 只入队 + 完成回调/专用 drain 任务发送），
而这条路 2026-11-12 两次上机都启动即挂（原因未定，需 JTAG panic 日志），因此**暂不推进**。
