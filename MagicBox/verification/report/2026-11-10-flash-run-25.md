## 2. 修掉的真 bug：接口选错（这是 `FAILED_START` 的根因）

抓包显示：

- 帧 497/499/501：`GET_DESCRIPTOR(device)` / `(config 9B)` / `(config 41B)` 全部成功；
- 帧 504 `SET CONFIGURATION` **成功**、505 `SET_IDLE` 成功；
- 帧 507：`GET_DESCRIPTOR(Report, wDescriptorLength=222)`；
- 帧 508：我们回了 **158 字节**（内置描述符），而 HID 描述符里声明的是 93。

根因：自动克隆里找到 IF0 的鼠标报告描述符后**没有停止遍历**，共享变量 `iface_off`
继续被 IF1 覆盖，于是"配置取 IF1（41 字节/158 字节报告）、报告描述符存 IF0（93 字节）"，
长度自相矛盾 → Windows 取 93 字节内容 + 垃圾尾巴 → HID 驱动启动失败。

修法：命中的那一刻记住 `mouse_iface_off` 并 `break`；裁剪只针对这个接口。

同一轮还修掉：**直送写死 5 字节**（G3M 是 7 字节：5 键 + X16 + Y16 + 滚轮 + AC pan），
改为按实际长度直送。

修完后实测：

```
mx.dv   -> 配置 0x22(34B)、1 个端点、报告长度 0x5D(93)、rep93
PC 侧   -> USB\VID_320F&PID_706E\... + HID-compliant mouse，状态 OK
mx.ac   -> 1:320f:706e:93
```

## 3. 遗留问题：主机收下报告但不产生输入

关键判据（本轮新加的探针 `mx.hq`，统计 `tud_hid_report_complete_cb` 次数）：

```
注入 5 条 7 字节报告：mx.hs 0->5，mx.hq 0->5   ← 主机把 5 条全取走了
光标位移：Δx = 0（连"左键按下"都没有任何效果）
```

已排除：

| 假设 | 实验 | 结果 |
|---|---|---|
| 选择性挂起 | 设备级 `SelectiveSuspendEnabled=0` + 重启节点 | 无改善 |
| 描述符缓存 | 换序列号 `0000000000A7`，Windows 建新节点 | 无改善 |
| 缺 Feature 报告应答 | 实现 `tud_hid_get_report_cb` 回零 | 无改善 |
| 端点包长太小 | 裁剪时把 wMaxPacketSize 改成 64 | 无改善 |
| boot 子类 | 恢复 01/02（与可工作的 30FA 一致） | 无改善 |
| **配置模板** | 用"30FA 已验证可工作"的 34 字节模板 + G3M 的 93 字节报告描述符 | **仍无改善** → 问题不在配置，而在报告描述符/报告长度本身 |

我们服务出去的 93 字节与从设备读到的**逐字节一致**（`mx.rd` vs `mx.ln a1 8106…`）。

对照：同一固件、同一台 PC，**5 字节/12 位**的 30FA 克隆注入 `x=+16` → 光标 Δx=22 ✓。

## 4. 下一步（明确、可执行）

1. **把真 G3M PRO 直接插到这台 PC 上抓一次它的枚举**（USBPcap），看 Windows 对它做了什么
   我们没做的：是否 `SET_PROTOCOL(boot)`、轮询的端点/间隔、初始的 GET_REPORT 序列、
   以及它第一个输入报告的线上字节。**这是唯一还缺的对照**。
2. 用抓到的真实报告字节校验我们对 7 字节布局的理解（尤其 X/Y 的字节序与是否有 Report ID）。
3. 若确认是 16 位字段的问题，考虑**不改描述符、改数据**：把 16 位位移缩放成设备描述的
   12 位/8 位布局（我们已有 12→8 的残差机制可复用）。

## 5. 现场状态（收尾）

- 固件：`-DMB_CLONE_FIXTURE=3`（单接口、30FA 身份、12 位直送），`mnt=1`；
- 自检：5 字节直送 `x=+16` → 光标 Δx=**22** ✓（板子可正常控光标）；
- PC 侧：`USB\VID_30FA&PID_0302\000000000003` 状态 OK；
- 复合克隆（`MB_CLONE_FIXTURE=99`）代码保留，但**默认不启用**，避免把板子留在不可用状态。


## 6. 最终根因（补记）：`wants_raw_report()` 判据没改到

抓包里我们的克隆设备（地址 3）在发 **4 字节**报告（1300 帧），而描述符声明的是 **7 字节** ——
这就是"主机收下却不产生输入"的全部原因。

具体：`makcu_clone_wants_raw_report()` 仍是旧判据

```c
return s_clone.valid && s_clone.report_len == sizeof(k_report_12b);   /* 只认内置 12 位夹具 */
```

G3M 克隆的 `report_len = 93 ≠ 64` → 返回 false → 走 int8 解码路径 → 发 4 字节
`{buttons,dx,dy,wheel}` → 主机按 7 字节解析 → 直接丢弃。

之前那次"改成 from_device 判据"的补丁**实际没有落到源文件**（脚本 replace 目标不匹配但打印了成功），
所以后面所有实验（挂起、缓存、Feature、包长、boot 子类、配置模板）都建立在错误前提上——
这也解释了为什么它们全部"无改善"。

修法：

```c
return s_clone.valid && (s_clone.from_device || s_clone.report_len == sizeof(k_report_12b));
```

并在 `makcu_clone_adopt()` 里置 `from_device = true`。

修复后实测：

```
注入 7 字节报告 X=+100 -> 光标 Δx = 151     ✓ 主机按 16 位解析
ls  -> hid=10911  injected=9439
hs  -> 9617 ok / 0 failed
ei  -> 00 01 00 00 00 00 00                 （与真设备直插 PC 时的报告一致）
PC  -> USB\VID_320F&PID_706E + HID-compliant mouse，状态 OK
```

## 7. 教训（写给自己）

1. **补丁必须验证落盘**：本轮两次"replace 成功但实际没改"（`wants_raw_report`、
   `mx.rs`/`mx.hq` 探针），代价是整轮排障方向跑偏。改完要 `Select-String` 复核关键行。
2. **抓包优先**：`hs`（发送被接受）与"主机是否真的按这个格式解析"是两件事，
   只有线上字节（或 `hq` 完成计数 + 数据长度）能分辨。


## 8. 双接口克隆的第一次尝试（失败，已回退）

目标：让 MI_01（键盘/厂商接口）也生效，使侧键与宏可用。

抓包确认真 G3M PRO 的侧键/宏**不在** 7 字节鼠标报告里：

| 端点/长度 | 样本 | 含义 |
|---|---|---|
| `0x81` 7 B | `00 01 00 00 00 00 00` | 位移/左右中键（已克隆） |
| `0x82` 8 B | `01 00 20 00 …` → `01 00 20 1e …` | **键盘报告**：`20`='3'、`1e`='1' → 用户那条 `31` 宏 |
| `0x81` 37 B | `01 00 00 2a …` | MI_00 上的第二条输入报告（厂商集合） |
| `0x82` 64 B | `04 aa 00 aa …` | 厂商数据（DPI/灯效） |

按计划做了：`CFG_TUD_HID=2`、原样服务 66 字节配置、按 `0xA2` 的 `ep` 路由
（`0x81`→实例 0，`0x82`→实例 1，`tud_hid_n_report`）。

**枚举成功**且和真设备一致（`MI_00 → HID-compliant mouse`、`MI_01 → HID Keyboard Device`
+ 系统控制/用户控制/供应商/厂商 4 个集合，共 5 个），但：

```
ls  -> hid=15380  injected=15258
hq  -> 86            ← 只有 86 条被主机取走
```

即 **`tud_hid_n_ready(0)` 几乎恒为假**：实例与端点的绑定不是"按描述符顺序"那么简单
（TinyUSB 在 `hidd_init` 里自己分配），我们按 `ep` 猜的实例号与实际不符，结果鼠标报告被送进
一个没人轮询的端点 → 鼠标不动。

随后整体回退（`CFG_TUD_HID=1` + 裁剪配置 + 实例 0 直送），但**枚举持续失败**
（`mnt=0`、`CM_PROB_FAILED_START`，即使换序列号）——说明同一 VID/PID/序列号族在反复
枚举不同配置后，主机侧留下了失败态，且回退不彻底（克隆结构与描述符回调仍带双接口痕迹）。

最终用**夹具 1**（`046D:C077`，全新 VID/PID 族）恢复可用：`mnt=1`、注入 `Δx=301`。

## 9. 双接口下一步的正确做法（避免再踩）

1. **先量后改**：加探针打印 `hidd_init` 之后每个实例实际绑定的端点（或用抓包看
   `SET_CONFIGURATION` 后主机轮询哪个 EP），确认实例↔EP 映射，再写路由；
2. **用独立 VID/PID/序列号做实验**（例如 `046D:C077` + 新序列号），不要污染真鼠标身份族；
3. **一次只加一个变量**：先只把配置换成 66 字节（仍是单实例，第二接口不注册），验证不破坏鼠标；
   再开 `CFG_TUD_HID=2`；
4. 失败时**完整回退**（clone 结构、描述符回调、sink 签名一起回），并保留一份可烧的已知good 构建。


## 10. 恢复"G3M 正常移动"的做法：夹具 4（已实测 + 已入回归）

双接口实验把**自动克隆**那条路弄坏了（`mnt=0`、`CM_PROB_FAILED_START`，同一份描述符在
09:35 还能枚举；换序列号、换 VID 族都不解）。为了先恢复可用，改用**夹具**绕开自动克隆：

`MAKCU_CLONE_FIXTURE_G3M`（`mx.cl 4`）：

| 项 | 值 |
|---|---|
| 身份 | `046D:C077`（在这台 PC 上枚举稳定的族） |
| 报告描述符 | **G3M PRO 原生 93 字节**（5 键 + X16 + Y16 + 滚轮 + AC pan） |
| 配置 | 34 字节单接口、boot 鼠标、EP `0x81` MPS 64、bInterval 1 |
| 转发 | `from_device = true` → **7 字节原字节直送**（不做 12→8 转换） |

实测：

```
dv  -> 046d:c077  rep93    mnt=1
PC  -> USB\VID_046D&PID_C077 + HID-compliant mouse  OK
注入 X=+100 -> Δx = 110     hs 2750 ok / 0 failed    hq 2750
```

用户实测：**速度正常**。回归新增 `test_fixture_g3m_report_layout`：**99 passed / 0 failed**。

结论：**"报告格式"与"身份"可以解耦** —— 用枚举稳定的身份承载任意鼠标的报告描述符，
就能在不碰自动克隆的前提下得到正确的位移/按键/滚轮。侧键/宏仍需 MI_01（键盘接口），
即 D38 的双接口工作。

## 11. 本轮两条教训补充

1. 自动克隆（运行时读描述符）代码路径**脆弱且难回退**；夹具路径简单、可复现。
   排障与交付应优先用夹具锁定"报告格式正确"，再把自动克隆作为增强项单独推进。
2. 同一 VID/PID 族在反复枚举不同配置后会被主机挂死；**实验要用独立身份**（D38 第 2 条）。


## 12. 路线 B 成功：侧键改用标准鼠标键，单接口即可透传（2026-11-10）

### 发现（不抓包就能拿到）
HECATE Connect 的按键映射表在 `DefaultData\Mouse_3395.json` 的 `KeyList`，赋值码是
`组<<16 | 子掩码`：

| 码 | 十六进制 | 含义 |
|---|---|---|
| 1048832/1049088/1049600 | `0x100100/0x100200/0x100400` | 左/右/中键 |
| **1050624** | **`0x100800`** | **鼠标4（后退）** |
| **1052672** | **`0x101000`** | **鼠标5（前进）** |
| 1245440… | `0x13xxxx` | 键盘按键族 |
| 10485760/10492672 | `0xA00000/0xA01B00` | 宏/多媒体族（用户的 `31` 宏在其内） |

### 实测（抓包 + 盒子）
用户在 HECATE Connect 里把两只侧键改成"默认键（前进/后退）"后，鼠标直插 PC 抓包：

| byte0 | 帧数 | 含义 |
|---|---|---|
| `0x08` | 22 | 键 4（后退） |
| `0x10` | 44 | 键 5（前进） |
| `0x01`/`0x04` | 11/9 | 左键/中键 |

→ 侧键已成为 **MI_00 7 字节鼠标报告里的标准按键位**。插回盒子后：

```
mx.bo -> 0x1B      （左/右 + 键4 + 键5 全部到达）
mx.ls -> injected 8150 / hid 8176
mx.hs -> 全部 ok，0 failed
用户实测：侧键有响应，正常
```

### 结论
**"完全透传"不需要多接口克隆就能达成大部分目标**：把侧键映射成标准鼠标键后，
位移（16 位精度、正确速度）+ 左右中键 + 滚轮 + 两只侧键**全部可用**。
代价是那只键上的宏 `31` 不再输出（宏走 MI_01 键盘报告）；要恢复宏才需要 MI_01（D38）。
