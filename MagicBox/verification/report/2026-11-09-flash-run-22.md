# 上机记录：2026-11-09 第二十二批（12 位打包报告 + 速度对齐）

> 接第二十一批（端到端打通）之后，用户反馈"位移偏快、y 轴快得离谱、x 轴偏慢"。
> 根因是**这颗鼠标发的是 12 位打包报告**，我们按 8 位读了。

## 1. 症状与证据

用户描述：y 轴非常快，x 轴偏慢。

用 `mx.ei`（最后一帧注入体）连续采样 100 秒，让用户先左右移动、再上下移动，按停顿切段：

| 原始数据 | 旧读法（8 位） | 真实含义（12 位） |
|---|---|---|
| `00 01 10 00 00` | x=1, y=**16** | x=1, y=**1** |
| `00 00 f0 ff 00` | x=0, y=**-16** | x=0, y=**-1** |
| `00 ff 0f 00 00` | x=-1, y=**15** | x=-1, y=**0** |
| `00 00 30 00 00` | x=0, y=**48** | x=0, y=**3** |
| `00 00 c0 ff 00` | x=0, y=**-64** | x=0, y=**-4** |

特征非常干净：`b2` 恒为 16 的倍数（±16/±32/±48/±64），`b3` 恒为 `00`/`ff`（符号扩展）。
这就是"低 4 位被左移 4 位"的痕迹。

## 2. 真实布局

```
byte0 = buttons
byte1 = x[7:0]
byte2 = x[11:8] | (y[3:0] << 4)      ← 关键
byte3 = y[11:4]
byte4 = wheel
```

解码：

```c
x12 = sign_extend_12(data[1] | ((data[2] & 0x0F) << 8));
y12 = sign_extend_12((data[2] >> 4) | (data[3] << 4));
wheel = data[4];
```

旧实现把 `data[2]` 当 8 位 y 直接发 → **y 恰好放大 16 倍**（因为那是 y 的低 4 位左移 4 位），
x 只用了低字节 → 偏慢。两条现象被同一条证据同时解释。

## 3. 另两处配套修正

1. **12 位 → 8 位要带余量**：快速甩动时 12 位值可能超出 int8（±127），超出部分进 `s_res_x/s_res_y`
   顺延到下一条报告，避免"甩快了丢距离"。
2. **必须逐条转发，禁止攒包**：Windows 指针加速按"单条报告的位移量"决定档位，
   把 1 位移攒成 20 位移会直接跳到高加速档 → 手感变快。`makcu_mouse_forward()` 现在
   逐条原样发，只有端点忙时才落到累加器。

## 5. 台架开关一览（本轮新增）

| 探针 | 作用 |
|---|---|
| `mx.du <hex>` | 用注入路径的解码函数解一条原始报告，回 `dx,dy,wheel` |
| `mx.fs <n>` | 转发分频（1=全转），用于标定速度或验证是否重复投递 |
| `mx.ss <hex>` | 钉住 0xA2 会话 id（`00` 回自动），让用例与现场真实流量解耦 |
| `mx.hk <0\|1>` | 注入钩子开关，测试期间隔离真实鼠标流量 |
| `tools\set_fs.ps1 -N n` | 一键切换 `mx.fs` |

## 8. 又一个探针级 bug（本轮最后修的）

`mx.fs` 无论传什么值都回 `8`：探针的数字解析用的是 `while (*arg >= '0' ...)`，
而命令缓冲区**不保证在 `len` 处 NUL 结尾**，残留字节被一起吃进数字，`n` 变成了大数
再被 `if (n > 8) n = 8;` 截断。

修法：`mx.fs` / `mx.ss` / `mx.du` 三处解析全部改成**以 `len` 为界**
（`while (i < len && line[i] >= '0' ...)`）。修完：

```
mx.fs 1 -> 1     mx.fs 3 -> 3     mx.fs 1 -> 1
mx.du 0001100000 -> 1,1,0        mx.bw -> 0,0,0,0
```

教训：**自研文本协议里所有参数解析都必须带长度边界**，不能指望字符串终止符。
