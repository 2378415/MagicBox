# 性能评审与整改方案（自编固件，2026-11-10）

> 目标：以「极致速度」为准绳，找出关键路径上的瓶颈与不合理实现。
> 本文只给方案，**未修改任何代码、未提交**。

---

## 0. 评审范围与方法

| 层 | 文件 |
|---|---|
| 右片 app | `app_right/main/app_main.c`（16676 B） |
| USB host（右片核心） | `components/makcu_hidhost/src/makcu_hidhost.c`、`include/makcu_hidhost.h` |
| 链路（双片共用） | `components/makcu_link/src/makcu_link.c`、`src/makcu_link_bridge.c`、两个头文件 |
| USB device（左片） | `components/makcu_hiddev/src/makcu_hiddev.c` |
| 左片 app | `app_left/main/app_main.c` |

判据不是"代码是否漂亮"，而是**每一条报告从 USB 到 USB 要付出多少固定开销**：
系统调用次数、堆栈拷贝次数、互斥锁次数、任务唤醒次数、以及**优先级是否让关键任务被抢占**。

---

## 1. 现状基线（实测）

| 指标 | 值 | 来源 |
|---|---|---|
| 报告吞吐 | **≈900 帧/秒**，35 s 内 31,555 帧 **0 失败** | `mx.ds` 压测 |
| 链路带宽占用 | 1 kHz × 15 B = **15 KB/s**，5 Mbaud ≈ 500 KB/s → **约 3%** | 计算 |
| 单帧开销 | 4 B 头 + 4 B（ep/session/len/flag）+ 7 B 报告 = 15 B，**协议开销 53%** | 计算 |
| 厂商通道 | `out=169, ok=169, in82=169`（100%） | `mx.ox` |

**结论先行：带宽不是瓶颈（只用了 3%）。真正的瓶颈是"每包固定开销"和"任务优先级/耦合"。**
所以优化方向是**减少每报告的调用/拷贝/加锁次数**，而不是提高波特率或改协议批量。

---

## 2. 关键路径成本分解（每条报告）

```
[右片]
DWC2 ISR
  └─ in_xfer_cb            (usb_cli 任务，prio 6)
       └─ report_sink      ← 1 KB 栈数组；mutex(session)；memcpy；mutex(tx)；uart ring 拷贝
            └─ uart_write_bytes
  └─ usb_host_transfer_submit（重新武装）

[左片]
uart_read_bytes × N 字节   (km_link 任务，prio 9；**每字节一次系统调用**)
  └─ makcu_link_parser_feed × N
       └─ handle_hid       ← s_chunk 重组 memcpy（每报告）；session 比较；memcpy 到 s_last_injected
            └─ link_report_to_mouse → makcu_hiddev_report_verbatim_ep
                 └─ tud_hid_n_report   ← TinyUSB 内部锁 + FIFO 拷贝
                      └─ km_hid 任务（prio 11）下发到主机
```

| 跳 | 固定开销 | 备注 |
|---|---|---|
| 右 `report_sink` | **1 KB 栈 + 2 次互斥 + 2 次拷贝** | 见 §3 P0-3 |
| 右 链路读 | **每字节 1 次 `uart_read_bytes`** | 见 §3 P0-1 |
| 左 链路读 | **每字节 1 次 `uart_read_bytes`** | 同上 |
| 左 `handle_hid` | **每报告 1 次多余 memcpy** | 见 §3 P0-4 |
| 左 HID 提交 | TinyUSB 锁 + FIFO 拷贝，失败**直接丢** | 见 §3 P1-5 |

合计：一条 7 字节报告要经历 **5 次数据拷贝**（栈×3 + 环形×1 + FIFO×1）、**3 次加锁**、
**约 15 次系统调用**（两侧逐字节读）。对 1 kHz 这就是每秒 15,000 次系统调用 —— 这才是要削的东西。

## 3. 问题清单

### P0-1 两颗芯片都「逐字节」读链路 UART

| | |
|---|---|
| 证据 | `components/makcu_link/src/makcu_link_bridge.c:420`、`app_right/main/app_main.c:395` |
| 代码 | `uart_read_bytes(LINK_UART, &byte, 1, pdMS_TO_TICKS(20))` |
| 影响 | 1 kHz × 15 B = **15,000 次/秒** 的 `uart_read_bytes`；每次含环形缓冲访问、tick 换算、可能阻塞唤醒 → 估算 **5–10% CPU + 明显抖动**；右片还会因此抢占 USB 任务（见 P0-2） |
| 改法 | 一次读一块：`uint8_t buf[256]; n = uart_read_bytes(LINK_UART, buf, sizeof buf, pdMS_TO_TICKS(20));` 然后 `for (i<n) parser_feed(...)`；空闲分支（`n==0`）只做心跳/日志刷新 |
| 预期 | 系统调用与任务唤醒降低 **~15×**；链路抖动显著下降 |
| 风险 | 极低（纯读法改动，解析器逐字节接口不变） |

### P0-2 右片任务优先级倒置（关键任务被低价值任务抢占）

| | |
|---|---|
| 证据 | `app_right/main/app_main.c:437`（`link_task` prio **10**）vs `components/makcu_hidhost/src/makcu_hidhost.c:453,457`（`usb_lib`/`usb_cli` prio **6**） |
| 影响 | 报告源（`usb_cli` 里跑 `in_xfer_cb`→`report_sink`）优先级最低，且逐字节读任务更高 → **IN 完成被延迟**、FIFO 拥塞、极端情况下丢包。这是右片最严重的结构性问题 |
| 改法 | `usb_lib` → **12**、`usb_cli` → **11**；`link_task` → **8**；`rearm_task` 保持 5。若担心 UART 丢字节，用 **4 KB RX 环**（现在 1024）吸收突发 |
| 预期 | 报告延迟 P99 大幅下降；高负载下不再丢帧 |
| 风险 | 中：需回归 + 压测；若 `usb_lib` 过高可能饿死链路读（可用 4 KB 环缓解） |

### P0-3 右片 `report_sink`：1 KB 栈 + 两把锁 + 两次拷贝（**每报告**）

| | |
|---|---|
| 证据 | `app_right/main/app_main.c:145`（`uint8_t payload[MAKCU_LINK_MAX_FIELD]` = 1024 B）、`:147`（`makcu_hidhost_session()` 内部 `s_lock`，见 `makcu_hidhost.c:478-487`）、`:155-161`（`s_tx_lock`）、`:150-151`（memcpy + `makcu_link_build` 再拷） |
| 影响 | 每报告 1 KB 栈（`usb_cli` 栈仅 4096）、2 次互斥（含优先级继承逻辑）、2 次拷贝；`uart_write_bytes` 在 TX 环满时会**阻塞 USB 任务** |
| 改法 | ① 0xA2 用固定 **≤64 B** 栈缓冲（`len` 最大 64，实际 7）；② session 改为**无锁读**（缓存在一个 `volatile uint8_t s_session_cache`，由 attach/detach 更新）；③ 取消中间的 `s_tx` 拷贝：直接两次 `uart_write_bytes`（先 4 B 头，再载荷）或写进一个**无锁 SPSC 环**由专用发送任务排空；④ 若保留 `s_tx`，只在真并发时加锁（单写者场景可去掉锁） |
| 预期 | 每报告去掉 **2 次互斥 + 1 次 1 KB 栈分配 + 1 次拷贝**；抖动下降、CPU 下降 |
| 风险 | 中（涉及发送路径重构）；建议与 P1-6（TX 环加大）一起做 |

### P0-4 左片 `handle_hid` 里的 `s_chunk` 重组在热路径上

| | |
|---|---|
| 证据 | `components/makcu_link/src/makcu_link_bridge.c:307-321`（`s_chunk[8][256]` 静态 2 KB，每报告 `memcpy`） |
| 影响 | 纯为 `mx.dc` 台架探针服务的**额外一次 memcpy**，1 kHz 下毫无意义 |
| 改法 | 用 `#if defined(MB_DEBUG_OPCODE)` 或一个 `s_chunk_track` 开关门控（默认关） |
| 预期 | 每报告省一次 memcpy 与 2 KB 静态占用 |
| 风险 | 无 |

### P1-5 左片报告直送与 TinyUSB 同步耦合，失败即丢

| | |
|---|---|
| 证据 | `components/makcu_hiddev/src/makcu_hiddev.c:214-221`（`if (!tud_hid_n_report(...)) { s_raw_not_ready++; return; }`） |
| 影响 | `km_link`(9) 直接调用 TinyUSB；端点忙时**报告被丢弃**（历史记录：1 kHz 洪泛时成功率曾掉到 0.8%）。当前压测 0 失败，但边界情况仍会丢 |
| 改法 | 加**报告小环（深度 8~16）**+ 由 `km_hid` 在 `tud_hid_report_complete_cb` 后主动排空（这正是 run-20 留下的 TODO）；环满才丢，且计入丢弃计数 |
| 预期 | 高频突发下零丢帧；链路任务与 TinyUSB 解耦 |
| 风险 | 中（需保证顺序与不合并报告——1 kHz 下**绝不能合并**） |

### P1-6 右片 TX 环形缓冲偏小

| | |
|---|---|
| 证据 | `app_right/main/app_main.c:50`（`LINK_TX_BUF 1024`） |
| 影响 | 5 Mbaud 下仅 **≈1.6 ms** 的缓冲；一旦 `link_task` 或 `usb_cli` 停顿超过 1.6 ms，`uart_write_bytes` 就阻塞调用者（可能就是 USB 任务） |
| 改法 | 提到 **4096**（≈6.5 ms），与左片 RX（4096）对称 |
| 预期 | 消除 TX 阻塞与由此产生的报告延迟尖峰 |
| 风险 | 低（+3 KB RAM） |

### P1-7 右片 `log_flush_one()` 按**字节**调用

| | |
|---|---|
| 证据 | `app_right/main/app_main.c:402`（循环体内，每字节一次） |
| 影响 | 15,000 次/秒调用，每次比两个全局变量；本身很便宜，但属明显冗余 |
| 改法 | 改为每完成一帧调用一次，或在 `n==0`（空闲）时调用 |
| 预期 | 微小但白捡 |
| 风险 | 无（日志最多延迟一帧） |

### P1-8 解析器没有批量接口，逐字节统计

| | |
|---|---|
| 证据 | `components/makcu_link/src/makcu_link.c`（`makcu_link_parser_feed` 单字节）；`makcu_link_bridge.c:430`（`s_stats.rx_bytes++` 每字节） |
| 改法 | 增加 `makcu_link_parser_feed_block(p, buf, n, on_frame, ctx)`：循环内部不返回，直接把完成的帧回调出去；统计按块累加 |
| 预期 | 与 P0-1 配合，进一步减少函数调用与逐字节判断 |
| 风险 | 低 |

### P2-9 观测计数的饱和精度问题

| | |
|---|---|
| 证据 | `components/makcu_hidhost/src/makcu_hidhost.c:503`（`sat8()`，>255 一律 255） |
| 影响 | 长跑压测时 `submit_ok/complete/forward` 全部显示 `ff`，**无法判断是否真的持续增长**（今天排障时就吃过这个亏） |
| 改法 | 16 位计数 + 显式截断（帧里多带 2 字节），或提供"取快照并清零"的探针 |
| 预期 | 观测能力提升（不是速度，但直接影响后续所有性能工作的可信度） |
| 风险 | 无 |

### P2-10 `uart_write_bytes` 缺少"非阻塞"保护

| | |
|---|---|
| 证据 | `app_right/main/app_main.c:158`、`components/makcu_link/src/makcu_link_bridge.c` 多处 |
| 改法 | 写前 `uart_wait_tx_done(LINK_UART, 0) == ESP_OK` 才写；否则入队/丢弃并计数（配合 P1-6 后基本不会触发） |
| 风险 | 低 |

### P2-11 UART 时钟源未显式指定 APB

| | |
|---|---|
| 证据 | `.source_clk = UART_SCLK_DEFAULT`（`app_right/main/app_main.c:426`、`makcu_link_bridge.c:448`） |
| 影响 | 5 Mbaud 的分频精度取决于时钟源；APB 80 MHz 时 5 Mbaud 误差 <0.1% |
| 改法 | 显式 `UART_SCLK_APB`，并核算实际波特率误差 |
| 风险 | 低（两片必须一致，否则误码） |

### P2-12 代码结构重复（可维护性，非直接性能）

| 问题 | 证据 | 改法 |
|---|---|---|
| `s_tx` + `s_tx_lock` + `makcu_link_build` + `uart_write_bytes` 的模式在 4 处重复 | `app_right/main/app_main.c:151-161, 188-198, 218-228, 307-320` | 抽一个 `link_send(cmd, payload, len)` 单点，未来做无锁发送只需改一处 |
| 各 handler 各自申请 1 KB 栈缓冲 | `app_main.c:145, 281, 307` | 统一到一个按需大小的暂存（0xA2 用 64 B，配置描述符用 256 B） |
| 任务优先级、缓冲大小散落各处 | 多处 `#define` | 收敛到一个 `board_config.h` |

## 4. 不建议做的事（避免走弯路）

| 想法 | 为什么不做 |
|---|---|
| **提高链路波特率** | 现在只用了 3% 带宽，提高波特率不解决任何问题，反而增加误码风险 |
| **把多条报告打包进一帧**（改协议） | 带宽不是瓶颈；而 1 kHz 下**合并报告会破坏时间精度**（历史教训：批量/合并会导致手感异常）。若将来要 4 kHz 或多设备，再以新 opcode（如 `0xA6`）**可选**引入 |
| **把 `MAKCU_LINK_MAX_FIELD` 全局调小** | 隧道/配置描述符路径确实需要 1 KB；正确做法是**按用途分开**（P0-3、P2-12），不是砍全局上限 |
| **给每报告加日志/时间戳** | 会把日志 `vsnprintf` 拖进热路径；度量要用采样计数，不要用日志 |

## 5. 度量方法（怎么证明"更快了"）

现有探针只给吞吐，不给延迟。建议加**最小侵入**的延迟采样：

1. 右片：`in_xfer_cb` 进入时记 `esp_timer_get_time()`，写进帧头保留字节（或用 1/64 采样计数器累加）；
2. 左片：`handle_hid` 里取当前时间，计算 `now - ts` 得单跳延迟，进一个 256 桶直方图；
3. 新探针 `mx.lat` 输出 `P50 / P99 / max / 样本数`；
4. 压测口径固定为：**1 kHz 连续 60 s**，验收线 = `0 丢帧` 且 `端到端 P99 < 500 µs`。

> 采样率建议 1/16（避免测量本身影响结果），并且**只在 `MB_DEBUG_OPCODE` 构建里启用**。

## 6. 整改路线图

### 批 1：低风险、立竿见影（预计 2~3 h，仅需刷左片 + 少量右片改动）

| 项 | 预期 |
|---|---|
| P0-1 逐字节读 → 块读（两侧） | 系统调用/唤醒 ↓15×，抖动 ↓ |
| P0-4 `s_chunk` 门控 | 每报告省一次 memcpy |
| P1-7 `log_flush_one` 改按帧 | 白捡 |

验收：`mx.ds` 压测 0 失败；主观手感无变化；回归 100 passed。

### 批 2：右片热路径重构（预计 3~4 h，必须刷右片并压测）

验收：1 kHz 60 s，0 丢帧、P99 < 500 µs（配合 §5 的 `mx.lat`）。

### 批 3：解耦与整洁（预计 3~4 h）

| 项 | 预期 |
|---|---|
| P1-5 左片报告环 + 由 `km_hid` 排空 | 高频突发零丢帧 |
| P1-8 解析器块接口 | 进一步降调用 |
| P2-9 计数 16 位 | 观测可信 |
| P2-11 时钟源、P2-12 发送单点化 | 可维护性 |

---

## 7. 一句话结论

**当前固件"能用且在 1 kHz 下 0 失败"，但它是"按调用开销付费"的实现**：
每报告 15 次系统调用、5 次拷贝、3 次加锁，且右片存在优先级倒置。
按上面的批 1 就能拿掉大部分固定开销（不动协议、不动时序），批 2 解决优先级倒置与锁开销，
批 3 才谈得上"极致"。**不要动波特率和帧格式——那不是瓶颈。**

## 关键发现 1：`tud_hid_n_ready()` 前置检查直接丢报告

`makcu_hiddev_report_verbatim_ep()` 原本：

```c
if (!tud_hid_n_ready(inst)) { s_raw_not_ready++; return; }   /* ← 报告在这里就没了 */
```

1 kHz 下"端点忙"是**常态**，所以每条被拒的报告连同它承载的相对位移被永久丢弃。
相对位移是累加的 → 丢 N% 的报告 = 手感慢 N%。这正是"鼠标偏慢"的真正原因（与带宽/波特率无关）。

修复：端点忙 / 挂起时都 `rep_push()` 入队，由完成回调排空。实测：

| 阶段 | 注入 200 条的发送成功数 |
|---|---|
| 修复前 | 70 |
| 只兜住 `tud_hid_n_report` 失败 | 122 |
| 兜住前置检查（最终） | **200（0 丢弃）** |

用户实测确认：**跟手**。

## 关键发现 2：两个台架工具 bug（曾把排查带偏很久）

1. **`MB_DEBUG_OPCODE` 没有转发给组件** —— `add_compile_definitions()` 是目录级的，`makcu_link` 看不到它，
   于是 `mx.dc` 的重组探针在台架构建里也被裁掉（回归 `test_chunk_is_reassembled` 因此失败）。
   已在 `app_left/main/CMakeLists.txt` 里对 `makcu_link` 显式 `target_compile_definitions()`。
2. **`mx.lfx` 用的是普通发送而不是回环** —— 帧被发给了右片，右片不认识 `0xA2` 就回错误帧，
   于是"注入全被丢弃"的假象出现。已改为 `makcu_link_send_loopback()`。

> 教训：台架探针本身也要有回归覆盖，否则它会用假数据误导排障。

## 关键发现 3：自愈逻辑不能在链路任务里调隧道

`handle_presence()` 在链路任务上下文里被调用，而它内部调 `tunnel_get(0xA1)` → `makcu_link_request()`
**等待回执**，但回执只能由同一个链路任务解析 → **自锁 400 ms**，期间 RX 环溢出、大批报告丢失。
已改为置标志、由独立的 `km_heal` 任务执行检查与重克隆。

### 尚未做（按收益排序）

1. **队列深度 16 → 32**（+128 B RAM）即可消掉开机突发的那 1.7% 丢弃；
2. **P2-9 计数 16 位**：`sat8()` 饱和到 255，长跑压测无法判断是否持续增长；
3. **§5 延迟度量 `mx.lat`**：目前只有吞吐指标，没有 P50/P99，无法量化"更顺"；
4. P1-8 解析器块接口、P2-10 写前非阻塞、P2-11 显式 APB 时钟源、P2-12 发送路径单点化。

### 结论

"鼠标偏慢"根因是**报告在 `tud_hid_n_ready()` 前置检查处被丢弃**（相对位移累加，丢多少就慢多少），
与链路带宽（仅 3% 占用）、波特率、帧格式**无关**。修复后注入 200/200 全部送达，用户实测跟手。


## 收尾四项（2026-11-10 完成）

| 项 | 状态 | 说明 |
|---|---|---|
| **1. 报告队列 16 → 32** | ✅ 已刷左片 | 开机/重枚举突发导致的丢弃从 1.7% 降到 **0** |
| **2. 计数改 16 位** | ✅ 已刷右片 | `0x1C` 的 submit/complete/forward 改为 u16（payload 16→20 字节），不再 255 饱和 |
| **3. `mx.lat` 延迟探针** | ✅ 已刷双片 | 左片测"报告间隔 + 每条处理耗时"，并通过新 opcode `0x21` 向**右片**查询其每条转发耗时（两片时钟不同步，故不做绝对端到端） |
| **4a. P2-11 显式 APB 时钟源** | ❌ 不做 | APB 80 MHz 与 XTAL 40 MHz 对 5 Mbaud 都是整数分频（误差同为 0），改了没有收益，反而引入"两片时钟源不一致→误码"的风险 |
| **4b. P2-10 写前非阻塞检查** | ❌ 不做 | 对**报告路径**，`uart_write_bytes` 阻塞是"慢一点但一定送达"，改成非阻塞就是"可能丢一帧=丢一段位移"。TX 环已 4 KB（≈6.5 ms），阻塞概率极低 |
| **4c. P1-8 解析器块接口** | ❌ 不做 | 块读已消除了逐字节系统调用（P0-1），剩下的逐字节状态机是 ns 级，收益小于改动风险 |
| **4d. P2-12 发送路径单点化** | ⏸ 延后 | 纯重构，会动 4 处已验证正常的热路径，等真有第二个发送者时再做 |

## 最终量化（2026-11-10，`mx.lat` 实测）

```
mx.lat -> int=7900/25600us  proc=10/30us  n=905
          r=60/60/67us      n8=243
mx.ds  -> 3,885 已发出 / 0 队列丢弃
```

| 指标 | 值 | 说明 |
|---|---|---|
| 左片每条报告耗时 | **p50 10 µs / p99 30 µs** | ≈0.5% CPU @500/s |
| 右片每条转发耗时 | **p50 60 µs / p99 60 µs / max 67 µs** | ≈3% CPU @500/s |
| 报告到达间隔 | ≈2 ms（≈500 条/秒） | 由**鼠标回报率**决定，不是盒子限制 |
| 队列丢弃 | **0** | |

**结论：当前实现远未饱和（两片合计约 70 µs/条）。"偏慢"的根因是丢报告，不是处理慢。**

### 如果将来还要更快（当前无必要）

唯一有意义的下一步是 **P0-3**：把右片那条 60 µs 的转发路径里的 1 KB 栈数组、两把互斥锁和一次中间拷贝去掉
（预计降到 10–15 µs）。但那要把 200 条/秒的余量从 30× 提到 150×，对 1 kHz 鼠标没有实际意义。
