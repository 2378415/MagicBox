# 上机记录：2026-11-09 第五批（键盘组 8 支 + 隐藏 opcode 测试夹具）

## 1. 本轮移植（8 支）

| handler | opcode | 原地址 | 语义（协议面） |
|---|---|---|---|
| `cmd_key_down` | 0x0D | `0x4200EC48` | 解析 usage（`'c'` 或单个十进制数字）→ `hid_key_down` → 回显；usage 为 0 静默 |
| `cmd_key_up` | 0x0E | `0x4200EB1C` | 同上，换 `hid_key_up` |
| `cmd_key_tap` | 0x0F | `0x4200E9D0` | usage + 延时窗口（`parse_range`）→ `hid_key_tap` → 回显 |
| `cmd_set_string` | 0x10 | `0x4200DE80` | 只接受 `'…'`，≤0x3F 字节 → `hid_type_string` → 回显 |
| `cmd_key_state` | 0x11 | `0x4200ED74` | 读按键状态 → 回 `<name>\n<digit>` |
| `cmd_keys_down` | 0x12 | `0x4200E6F0` | `parse_list6`（≤6 个，逗号/右括号分隔）→ 批量按下 → 回显 |
| `cmd_keys_up` | 0x13 | `0x4200E718` | 同上，批量释放 |
| `cmd_keys_combo` | 0x14 | `0x4200E998` | 列表 + 延时 → `hid_keys_combo` → 回显 |

配套实现：

- `makcu_parse_int_or_char / parse_list6 / parse_range`：三个解析器的等价实现。
  **注意**：`parse_int_or_char` 原样只吃**一位十进制**（反编译里读一个字符后就 clamp 返回），
  所以 `"42"` 得到 `4` —— 这是复现原行为，不是修 bug；
- `makcu_char_to_usage`：标准 HID usage 表（与反编译里采样到的手臂一致：`g`→0x0A、
  `p`→0x13、`u`→0x18、`z`→0x1D，字母大小写不敏感）；
- `makcu_kbd_hooks`：八个 HID 写入函数的位置，等 `makcu_keyboard` 移植后接入。

累计已移植 **22 / 27**。

## 2. 新增：隐藏 opcode 的台架夹具

0x0D–0x18 没有文本命令，外部不可达，光靠文本协议测不到。因此在 `app_left` 加了一条
**只用于台架**的入口（`-DMB_DEBUG_OPCODE=ON`，默认 OFF）：

```
mx.<两位十六进制 opcode> <参数>
```

例如 `mx.0d 'a'` 会直接调用 `cmd_key_down`，参数即该 handler 的“整行”。这样隐藏 opcode
的回包也能上机断言了。发布固件必须保持该选项为 OFF（决策 D17）。

## 3. 回归（38 例，含 10 例隐藏 opcode）

| 端口 | 结果 |
|---|---|
| `COM11`（原生 USB-Serial-JTAG） | **37 passed, 1 xpassed, 0 failed** |
| `COM8`（CH343 / UART0） | **37 passed, 1 xpassed, 0 failed** |

隐藏 opcode 用例（逐字节）：

| 发送 | 收到 |
|---|---|
| `mx.0d 'a'` / `mx.0d 4` | `km.'a'` / `km.4` + 后缀 |
| `mx.0e 'a'` | `km.'a'` |
| `mx.0f 4,1,5` | `km.4,1,5` |
| `mx.10 'hi'` | `km.'hi'` |
| `mx.11 'a'` | `km.mx\n0` |
| `mx.12` / `mx.13` `'a','b'` | `km.'a','b'` |
| `mx.14 'a',1,2` | `km.'a',1,2` |
| `mx.0d`、`mx.10` 无参 | 无回包 |

**一个发现**：`mx.0f 'a',1,5` 无回包 —— 因为 `parse_int_or_char` 的 `'c'` 形式要求
**整个参数**以引号结尾，带延时窗口时只能用十进制 usage（`4,1,5`）。这与原实现的解析器
一致，已写进测试注释。

## 4. T3（指令相似度）读数

`tools/t3_report.py` 把这 8 支编译结果与原始地址逐条比对（归一化指令序列）：

| handler | 相似度 | 说明 |
|---|---:|---|
| `cmd_set_string` | 0.603 | 最接近：解析结构简单 |
| `cmd_keys_up` / `cmd_keys_down` | 0.560 | 原实现把 list 解析器内联了 |
| `cmd_key_tap` | 0.520 | |
| `cmd_keys_combo` | 0.500 | |
| `cmd_key_state` | 0.083 | 原实现内联了整个 usage 解析（119 条 vs 我们 25 条） |
| `cmd_key_down` / `cmd_key_up` | 0.070 | 原实现内联 106 条解析器，我们只留 9 条 + 调用 |

结论：**T3 对“手写重实现”不是有效门槛**，它衡量的是“同一份源码重新编译”的保真度
（对 P0 的库代码有意义）。手写 handler 的判据应是 T2（协议逐字节）＋结构审查，
T3 只作为“跑偏得离谱”的告警。该结论已写进 `docs/00-plan.md` 与决策 D18。
