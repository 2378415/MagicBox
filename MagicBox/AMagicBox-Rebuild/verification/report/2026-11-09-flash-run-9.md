# 上机记录：2026-11-09 第九批（分步提交引擎）

## 1. 本轮实现（`0x4200EFEC` 的提交骨架）

| 项 | 内容 |
|---|---|
| 拆分 | HID 报告只能带 int8，按 `127` 上限分步：`steps = ceil(max(\|dx\|,\|dy\|)/127)` |
| 分配 | **最大余数法**，步进之和严格等于请求值（不多不少） |
| 节拍 | 步间 `vTaskDelay(1)`（与原厂等提交信号量的节拍一致） |
| 可观测 | 16 条报告环形 trace，`mx.rq` 一次读回（hex，每 3 字节一份） |
| 未移植 | 原函数的**随机角度旋转 + 双精度缓动**（`cos/sin/__fixdfsi` + PRNG），现在步进是直线等分 |

## 2. 抓到的 bug：trace 打印顺序

第一次上机 60 例里挂了 1 条（`test_two_axis_split_sums`）。现场探针（`tools/trace_probe.py`）显示：

```
.km.move(-260,130) → trace 里实际发出 (-87,44) (-87,43) (-86,43)
```

三步、分量都 ≤127、两轴之和正好 -260 / +130 —— **引擎是对的**，错在 `mx.rq`：16 条环形缓冲写满后会回卷，而打印从 index 0 开始，于是“最后 N 条”取到的是错位条目。

修法：`makcu_mouse_trace()` 先按时间顺序拷进一份静态数组再返回。重烧后 **61 例全绿**。
