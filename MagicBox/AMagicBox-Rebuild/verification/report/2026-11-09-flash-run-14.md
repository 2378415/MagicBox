## 1. 本轮环境（这台机器原来没有 IDF）

交接文档 §5 写的 `D:\esp-idf`、`D:\esp-tools`、`D:\Apply\toolchains` 在本机**都不存在**，
`tools\build_app.ps1` 直接报 `python.exe not recognized`。本轮按下面的方式重建，全部写进
`tools\setup_idf_local.ps1`（可重跑）：

| 项 | 做法 |
|---|---|
| IDF 源码 | `github.com:443` 不可用 → gitee 镜像 `gitee.com/EspressifSystems/esp-idf` 的 `v5.4.1` |
| 子模块 | `git submodule update` 在 gitee 上会要凭据 → 改用 codeload 按 `git submodule status` 的 pin sha 逐个取 tar.gz（16 个 + 先取的 7 个，脚本内可复用） |
| 工具链 | `xtensa-esp-elf 14.2.0_20241119`（386 MB）来自 `dl.espressif.com/github_assets`，解到 `D:\esp-tools\tools\xtensa-esp-elf\esp-14.2.0_20241119` |
| Python 环境 | `D:\esp-tools\python_env\idf5.4_py3.11_env`（venv + `requirements.core.txt`） |
| **坑 1** | IDF 5.4.1 需要 `D:\esp-tools\espidf.constraints.v5.4.txt`，venv 手工建时不会生成 → 先建空文件，否则 `cmake` 直接报 “forgotten to run the install scripts” |
| **坑 2** | `idf-component-manager` 装到 3.x 后 IDF 传 `--interface_version 3` 被拒（3.x 只认 4/5/6）→ 必须 `pip install "idf-component-manager<3"`（实测 2.5.2） |
| **坑 3** | IDF 的 `git_submodules.cmake` 会强行 init 子模块并 FATAL → 构建时置 `IDF_SKIP_CHECK_SUBMODULES=1` |
| **坑 4** | `makcu_board` / `makcu_hidhost` 声明了 `INCLUDE_DIRS "include"` 但目录不存在，CMake 直接报 “not a directory” → 各补一个占位头（无导出符号） |

构建命令（本轮两次都用这个包装）：

```powershell
$env:IDF_SKIP_CHECK_SUBMODULES='1'
powershell -NoProfile -ExecutionPolicy Bypass -File tools\build_app.ps1 -App app_left -Clean `
    -Define "-DMB_DEBUG_OPCODE=ON,-DMB_HID_DEVICE=ON,-DMB_CLONE_FIXTURE=1"
```

## 2. 根因：克隆的配置描述符多了一个字节

**症状**（交接文档 §10.2）：`mx.dv` 自洽（VID 046D:C077、总长 34、HID 声明 52=报告长度），
但 `mnt=0`；主机侧 `USB\VID_046D&PID_C077\000000000001` 状态 `Error`，`Problem 10 / CM_PROB_FAILED_START`，
`ProblemStatus 0xC0000001`。

**取证**（不依赖新固件，用宿主侧 USB ETW）：

```powershell
logman create trace usbhub2 -p Microsoft-Windows-USB-USBHUB3 0xffff 4 -o hub2 -ets
pnputil /restart-device "USB\VID_046D&PID_C077\000000000001"
logman stop usbhub2 -ets          # 然后 tracerpt 转 XML
```

USBHUB3 事件 43 打出主机真正收到的配置描述符（34 字节）：

```
09 02 22 00 01 01 00 A0 32 | 09 04 00 00 01 03 01 02 00 |
09 21 11 01 00 00 01 22 34 00 | 07 05 81 03 40 00
```

按 `bLength` 走链：`0 → 9(配置) → 9(接口) → 9(HID) → 27`，偏移 27 处是 **`bLength = 0`**，
端点描述符被截成 6 字节（丢了 `bInterval`）。紧接着：

```
事件 93: URB_FUNCTION = 0x0 (SELECT_CONFIGURATION), UsbdStatus = 0x80000300 (INVALID_PARAMETER)
事件 91: IoctlCode   = 0x220003 (SUBMIT_URB),        NtStatus   = 0xC0000001 (UNSUCCESSFUL)
```

**原因**：`makcu_clone.c: build_config()` 里 HID 描述符写成了 **10 字节**（`bcdHID 11 01` 之后多了
一个 `*p++ = 0;`），但 `wTotalLength` 仍按 `9+9+9+7 = 34` 填。设备发 34 字节（TinyUSB 按
`wTotalLength` 截断），于是端点描述符被切掉最后一个字节、链在 27 处断掉 → 主机找不到端点 →
`SET_CONFIGURATION` 被 USBPORT 判 `INVALID_PARAMETER` → HidUsb 启动失败 → `Problem 10`，
设备侧 `tud_mount_cb` 从未触发（`mnt=0`，且驱动失败后端口挂起会再被 `tud_suspend_cb` 清零）。

**修复**：删掉那个多余的 `0x00`，HID 描述符回到 9 字节。
`verification/model/test_clone_descriptor.py` 用 Python 镜像 `build_config()` 走链，并专门复现
“多一个字节 → 偏移 27 出现 `bLength=0`”，防止回归。

## 3. 顺带修的两处数据面问题

| 问题 | 现象 | 处理 |
|---|---|---|
| 克隆后报告仍带 Report ID 1 | 克隆描述符（`k_report_4b`/`k_report_5b`）没有 Report ID 项，主机按 4/5 字节解析，多出的 ID 字节会把每个字段挪一位 | `makcu_clone_t` 增加 `report_id`（0 = 无 ID）；`makcu_hiddev_report()` 在克隆激活且 `report_id==0` 时 `tud_hid_report(0, raw, len)`，并按 `report_len` 补 AC-pan 字节；克隆激活时不再发键盘 ID2 |
| `MB_TUSB_DEBUG` 根本传不到 TinyUSB | 该宏只在 `app_left/main` 目录作用域生效，tusb 库仍 `CFG_TUSB_DEBUG=0`，日志永远是空的 | `app_left/main/CMakeLists.txt` 对 `espressif__tinyusb` 与 `makcu_hiddev` 两个目标补 `target_compile_definitions` |

另外两处与交接文档描述不符的代码问题：

| 问题 | 处理 |
|---|---|
| `run_move()` 把步数上限卡在 `MAKCU_REPORT_TRACE`（16）→ 单次移动超过 16×127 = **2032 计数就被截断**，`fold_residue` 也挤不回来；交接文档“步进之和 == 请求值”只在 ≤2032 时成立 | 步数改为 `ceil(span/127)`，缓冲按 `STEP_MAX = 259` 静态分配；曲线控制点改为每次移动取一次（原来每个采样点都重新随机，实际是抖动而不是弯曲） |
| 没有硬件可断言的守恒证据 | `makcu_mouse` 增加累计计数器 + `mx.rt`（`dx,dy,wheel`），测试可断言“进 5000 出 5000”，不受 16 条轨迹环限制 |

## 4. 上机结果

### 4.1 枚举（本轮的核心证据）

烧录后串口日志（`tools/flash_capture.ps1` 抓的 TinyUSB 调试流）：

```
USBD Setup Received 00 09 01 00 00 00 00 00
  Set Configuration
  Open EP 81 with Size = 64
  HID opened
  Bind EP 81 to driver id 0
USBD Xfer Complete on EP 80 with 0 bytes
```

设备侧：

```
mx.dv -> init=1 mnt=1
         dev 12 01 00 02 00 00 00 40 6d 04 77 c0 00 01 01 02 03 01
         cfg 09 02 22 00 01 01 00 a0 32 | 09 04 00 00 01 03 01 02 00 |
             09 21 11 01 00 01 22 34 00 | 07 05 81 03 40 00 01     ← 9 字节 HID，端点完整
         rep52:05
```

主机侧：

```
USB 输入设备        USB\VID_046D&PID_C077\000000000001     OK
HID-compliant mouse HID\VID_046D&PID_C077\8&1E1472C&0&0000 OK
```

即“仓库 → 回调 → 主机 → 驱动启动 → 鼠标设备节点”全链路通过，交接文档 §10.2 的第 1 条闭环。
`mx.cc` 清掉克隆后设备回到内置身份 `303A:4004`，同样 `mnt=1`、枚举正常（两条路径都验过）。

### 4.2 协议 / 运动回归

| 项 | 结果 |
|---|---|
| 上机回归 `python -m pytest verification\regress` | **75 passed + 1 xpassed**（清洁构建，COM3） |
| 离线模型 `verification\model` | **16 passed**（新增克隆描述符模型 7 例 + 分步守恒 1 例） |
| 单次移动守恒 | `mx.rt` 前后差：`.km.move(10,0)` → `+10`；`.km.move(-3,7)` → `-3,+7` |
| 全量程移动 | `.km.move(-30000,20000)` → 累计差 `-30000/+20000`（259 步） |

> **坑 5（重要）**：`MB_TUSB_DEBUG=1..3` 的构建不能跑回归——TinyUSB 会把每个控制/中断传输打在
> UART0 上，回包里混进 `Queue EP 81 with 5 bytes ...`，`km.` 前缀断言全崩（本轮先踩到 13 例失败，
> 换清洁构建后全绿）。调试构建只用于“看枚举到底哪一步失败”。
