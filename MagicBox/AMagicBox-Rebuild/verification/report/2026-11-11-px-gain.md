# 光标增益标定（只测量）

> 2026-11-11 10:20。工具 `tools/px_cal.py`。**没有改固件、没有改系统设置。**

## 1. 方法

- 用 `mode.bit7`（极速）让 `T = ceil(D / max_report)`，于是**每条报告正好带 `max_report` counts**，
  可以干净地把"每报告 counts"当自变量扫；
- 每次测量前 `SetCursorPos` 归位到 (200, 屏幕中)，`GetCursorPos` 读终值（进程按 per-monitor DPI aware）；
- 每档重复 3 次取中位数；同时从 `mx.mt` 读回**实际发出的 counts**（不是请求值）做分母；
- 贴边（坐标到 0 或 screen-1）的样本判为 invalid。

## 4. 那"速度越大偏移越大"是哪来的？——屏幕边界钳位

从 x=200 起跑，`sumv` 一次走完：

| 请求 counts | 线性预期位移 | 实测位移 | 结果 |
|---|---|---|---|
| 400 | 500 px | 500 | ✓ linear |
| 800 | 1000 px | 1000 | ✓ linear |
| 1500 | 1875 px | 1875 | ✓ linear |
| 1900 | 2375 px | **2359** | ✗ CLAMPED（停在 x=2559） |
| 2200 | 2750 px | **2359** | ✗ CLAMPED |
| 3000 | 3750 px | **2359** | ✗ CLAMPED |

**撞边之后多发的 counts 被 OS 吃掉，永不回补**。所以：

- 位移越大 / 速度越快 → 越容易顶到屏幕边 → "少走的像素"越多 → 看起来"坐标偏得越厉害"；
- 而且它和"每报告多大"完全无关（增益恒定）——之前的推测（Windows 加速曲线）在本机**不成立**。

## 5. 结论（修正之前的方案）

| 原方案 | 本机实测结论 |
|---|---|
| **S1 改系统设置**（关 EPP） | **不需要**：`MouseSpeed=0`，EPP 本来就是关的。**打开 EPP 才会引入非线性**，千万别改 |
| **S2 瞄准档 `max_report=12`** | 对**落点精度没有帮助**（增益与 per-report 无关，9 与 103 都是 1.25）。它只影响观感：每报告小时轨迹更"碎"，每报告大时更"跳"。要视觉锯齿小可以留 12，但别指望它治偏移 |
| **S3 固件增益表** | **不需要查表**：增益是**常数 1.25 px/count**（= 1.0 logical × 125% 缩放）。客户端乘一个常数即可；换机器/换缩放要重标 |
| **新增 S4′ 防撞边** | **真正该做的**：撞边是不可逆的信息丢失，只能在**下发前**避免 |

## 6. 建议的整改（下一步，待拍板）

1. **客户端换算**：`px = counts × 1.25`（本机）；若上位机要"按像素说话"，下发改成 `counts = px / 1.25`。
2. **防撞边**：PC 侧下发前读 `GetCursorPos`，把 `dx` clamp 到"到边的剩余空间 / 1.25"；
   要点式到位就分 2–3 段（每段读一次光标再修正），撞边立刻停。
3. **工具并排显示**：boxbench 轨迹页同时显示"Σ counts / 实际像素位移 / 撞边标记"，一眼看出是精度问题还是钳位问题。
4. **`max_report` 定为 12（观感）**：可以照你说的做，但记住它不是精度手段；真正决定观感的是"每报告跳多少像素"（12 counts ≈ 15 px/报告）。
5. 若将来要做"1 count = 1 px"，只能改系统指针速度（Sensitivity 从 10 往 6 调）或改 Windows 缩放，属于**系统设置**范畴，需你确认后再动。

```powershell
python tools\px_cal.py --mr 12,60,120 --dx 800        # 指定档位
```

`aim_move.py` 的做法（也是"到位"的正确姿势）：

```
读光标 → counts = px / gain → 把目标夹到屏幕内、把这一发夹到不越界
      → 发一段 sumv → 等它走完 → 再读光标 → 残差超容差就再来一段（通常 1–2 轮）
```
