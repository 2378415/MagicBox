# 控制口 921600 + 二进制快速通道（P1 + P2）

> 2026-11-10 18:00 实施并上机验证。目标来自用户决策：**盒子算轨迹 / 直接 921600 / 交互路径允许丢包**。

## 1. P1：921600 与控制口 RX/TX 整改

| 改动 | 位置 | 原因 |
|---|---|---|
| `CONTROL_BAUD 115200 → 921600`，`CONFIG_ESP_CONSOLE_UART_BAUDRATE` 同步 | `app_left/main/app_main.c`、`app_left/sdkconfig` | 115200 下一条 16 字节文本命令光上线就要 1.39 ms；控制台与协议同线，波特率必须一致，否则日志变乱码 |
| RX：逐字节读 → **事件队列 + 按 `ev.size` 零超时读** | `control_port_task` | 见 §4 坑 1 |
| TX：`tx_buffer_size 0 → 1024` | `uart_driver_install` | 阻塞写会让回包期间不解析下一条命令 |
| 工具默认值全同步 | `conftest.py`、`trace_motion.py`、`trace_opcodes.py`、`flash_capture.ps1`、`clone_check/cursor_test/hid_isolation/watch_link/watch_session/set_fs/flash_when_ready/reflash` | 否则刷写、回归、台架脚本全部失效 |

`flash_capture.ps1` 现在以 921600 发 `mx.dl`；ROM 下载器仍以 115200 打印开机横幅，
用 921600 去读它是乱码，属正常，esptool 自己会同步到 115200 再提速。

## 2. P2：二进制快速通道（`app_left/main/control_bin.c`）

```
5A <cmd> <seq> <len u16 LE> <payload> <crc8>       crc8 poly 0x07 覆盖 cmd..payload
```

| cmd | 名称 | payload | 字节 | 回包 |
|---|---|---|---|---|
| 0x31 | MOTION_PLAN | dx i16, dy i16, dur_ms u16, mode u8, flags u8 | 14 | 无 |
| 0x32 | BUTTON | mask u8 | 9 | 无 |
| 0x33 | WHEEL | delta i8 | 9 | 无 |
| 0x34 | QUERY | what u8（0 计数 / 1 能力 / 2 上条计划） | 9 | 有 |
| 0x35 | PING | counter u32 | 12 | 有 |

- 交互命令**零回执**；`QUERY 0` 给出 `pkts / crc_err / len_err / seq_gaps / last_seq`，
  `QUERY 2` 给出上一条计划的 `recv_us / submit_us`；
- `0x5A` 只有在"文本行首"才会开帧，所以文本命令里的 `Z` 不会被误判；
- 与文本协议共存：同一根线、同一个 `makcu_mouse` 动作层；
- `QUERY 1` 的 `plan_engine` 目前是 **0**（走旧的 127 分块引擎），1000 Hz 计划执行器落地后改 1。

## 3. 实测

```
text .km.version()   -> km.MAKCU                     （921600 下逐次可用）
PING x200            -> lost 0  p50 1.10 ms  p99 1.18 ms  max 1.49 ms
PING x100（复测）     -> lost 0  p50 1.11 ms  p99 1.27 ms
MOTION_PLAN dx=200   -> mx.rt 精确 +200 / QUERY2 submit_us=330
BUTTON 1/0           -> mx.bo 0x01 → 0
WHEEL +1             -> mx.rt wheel=1
CRC / 长度错误        -> 0 / 0
回归                  -> 100 passed（125.7 s）
```

对照整改前后（同一台 PC、同一条 CH343）：

| 指标 | 整改前 | 整改后 |
|---|---|---|
| 单条命令 RTT | 20 ms | **1.1 ms** p50 |
| 命令侧线上时间（16 B 文本） | 1.39 ms | 0.17 ms |
| 回包阻塞 | 2.08 ms/条 | 0 |
| 二进制帧（14 B 计划） | — | 0.15 ms |

1.1 ms ≈ 一个 USB FS bulk 帧 → **已经贴到这条链路的下界**（再快只能改 USB 拓扑）。

## 4. 两个坑（已修，值得记住）

1. **`uart_read_bytes(buf, 1024, 20 ms)` 会等满长度或超时**。12 字节的回包永远填不满
   1024，于是每条回复被硬生生拖到 20 ms —— 这正是整改前 RTT 恒定 20 ms 的原因
   （文本命令与二进制 PING 完全一样，说明与解析器无关）。
   改用事件队列：`ev.size` 告诉这次来了多少，按该长度用 0 超时读。
2. **`CONFIG_FREERTOS_HZ=100`，所以 `pdMS_TO_TICKS(5) == 0`**。用它等队列等于忙等：
   `km_uart0` 变成自旋任务、IDLE0 被饿死、任务看门狗每 5 s 打印一次；更糟的是日志
   与协议同线，回归里"逐字节比对"的用例全被打翻（表现为 12 failed / 13 skipped）。
   改用 `portMAX_DELAY` 阻塞在事件队列上（带 JTAG 回退时才用 1 tick）。

## 5. 顺带修的测试脆弱点

`test_zero_move_emits_nothing` 在 921600 后偶发失败：前一个用例的多步移动还在按 tick
排空，`before` 取到的"最后一条报告"随后被它改掉。采样前多等一拍（0.5 s + 0.2 s），
并在注释里写明原因。
