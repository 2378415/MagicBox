# 上机记录：2026-11-09 第四批（锁 / 抓取查询 / 按下）

## 1. 本轮移植（6 支）

| handler | opcode | 原地址 | 语义 |
|---|---|---|---|
| `cmd_lock_param0` | 0x00 | `0x4200DECC` | `lock_m*(1)` 写通道槽 `+0x54`；参数不是 `'1'` 时连带 `catch_set(0)` 与 `dirty=0`；回显 |
| `cmd_lock_query` | 0x01 | `0x4200DE40` | `lock_m*()` 回 `<name>\n<digit>`，`digit = (通道槽 +0x54 != 0)` |
| `cmd_lock_param2` | 0x02 | `0x4200DF08` | `lock_mx(` / `lock_my(` 写**字节** `+0x9C` / `+0x9D`（`FUN_42010C08 → F9F8/FA24`）；回显 |
| `cmd_lock_axis` | 0x03 | `0x4200DE60` | `lock_mx()` / `lock_my()` 读同一字节回状态 |
| `cmd_catch_query` | 0x0B | `0x4200DFF0` | 通道槽 `+0x54`、抓取槽 `+0x168`、armed 槽 `+0x124` 三者同时非零才回 1 |
| `cmd_button_press` | 0x04 | `0x4200DF30` | `left(1)` 按下 / `left(0)` 释放 → `lock_axis_set` → `axis_slot_set`（写 `+0x9C+4*target`，并置提交请求）；回显 |

要点：`0x01`/`0x03` 的查询与 `0x00`/`0x02` 的写入**严格互补**，这也是命令表里
`lock_mx()`（查询）排在 `lock_mx(`（写入）之前的原因（前缀匹配取首个命中）。

累计已移植 **14 支 / 27 个 opcode**。

## 2. 一个新的测试环境坑（已修）

CH343 只把 DTR/RTS 接到 CH343 自己，**没有接 ESP32-S3 的 EN/IO0**：
- 无法用它进下载模式（`esptool` 报 `Failed to connect`，实测）；
- 也**不能靠 DTR/RTS 脉冲复位应用**，所以 RAM 里的状态会跨测试轮次保留。

现象：第一轮在原生 USB 上跑完后，第二轮换 CH343 跑，`.km.lock_mx()` 返回 `1`
（上一轮 `lock_mx(1)` 留下的轴字节），两条断言失败。

修法：`conftest.py` 在 `device_ready` 里先发一组清零命令（`lock_m*(0)`、`lock_mx(0)`、
`lock_my(0)`、`buttons(0)`、`left(0)`…`ms2(0)`），再开始断言。修完后两条通路都全绿。
