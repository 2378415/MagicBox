# 方案：让 HECATE Connect 能在"鼠标插在盒子上"时正常识别与设置

> 目标（用户最终诉求）：G3M PRO 接在盒子右侧 host 口时，PC 上的 HECATE Connect
> 仍能识别这颗鼠标，并能读取/写入它的配置（DPI、按键映射、宏、灯效等）。
>
> 本文是**方案**，不含执行步骤的落地代码。基于 2026-11-10 run-25 的实测结果制定。

## 1. 现状与目标的差距

已知（实测）：

| 通道 | 端点 | 方向/长度 | 用途 | 盒子现状 |
|---|---|---|---|---|
| 鼠标 | `0x81` | IN 7B | 位移 / 按键 / 滚轮 | **已透传**（夹具 4，7 字节原字节直送） |
| 键盘 | `0x82` | IN 8B | 宏 / 键盘输出 | 未转发（单接口） |
| 厂商 | `0x82` | IN 64B | 状态读取（`04 aa 00 aa …`，约 1.2 s 一次） | 未转发 |
| 厂商 | **`0x05`** | **OUT 64B** | **写配置**（DPI/宏/灯效/按键映射） | **完全没有通路** |

PC 侧（管理程序）需要的是 **双向代理**：它既读（厂商 IN），也写（厂商 OUT）。

身份方面：当前夹具用 `046D:C077`（因为 `320F:706E` 这一族在本机反复枚举不同配置后整族
挂死 `CM_PROB_FAILED_START`）；管理程序识别目标鼠标大概率按 VID/PID + 产品串 `G3M PRO`。

| 需求 | 现状 | 差距 |
|---|---|---|
| PC 认成 G3M PRO | `046D:C077` | 改回 `320F:706E` + 产品串，并清理挂死的设备节点 |
| 复合拓扑（MI_00 + MI_01） | 单接口 `CFG_TUD_HID=1` | D38 双实例（前置：量清实例↔端点绑定） |
| 厂商 IN 回传 | 链路 `0xA2` 帧**带 `ep` 字段**（设计支持多端点） | 按 `ep` 路由到第 2 个 HID 实例 |
| 厂商 OUT 下行 | 无 | **硬门槛**：右片需能向鼠标 OUT 端点提交传输 |
| 身份稳定性 | 320F 族曾挂死 | 清节点 + 每次实验用独立序列号 |

## 2. 已掌握的事实（可直接引用，不需重做）

1. 真鼠标描述符与端点：MI_00 = `0x81`(IN) 93 字节报告描述符；MI_01 = `0x82`(IN) + `0x05`(OUT)，
   报告描述符 158 字节，配置 66 字节（完整原文见 run-25 与 `mx.dv`/`mx.if`）。
2. `mx.if` 已能读到 `2 93:81:0 158:82:1`（两个接口的描述符/端点/Report ID 都已入库）。
3. `0xA2` 帧的 payload[0] 就是端点号 → 链路层面**天生支持多端点分发**。
4. 侧键/宏的通信性质：侧键映射为鼠标键时走 MI_00 的按键位（已实测 `0x08`/`0x10`）；
   宏与厂商数据走 MI_01。
5. 管理程序的按键映射码表（`DefaultData\Mouse_3395.json` 的 `KeyList`）：
   `0x100800`=鼠标4、`0x101000`=鼠标5、`0x13xxxx`=键盘族、`0xA0xxxx`=宏/多媒体族。
6. 右片（原厂 V3.7）`frame_forward` 的 opcode：`0xA0`（EP0 方向）、`0xA1`（EP0 隧道）、
   `0x1A`（快照）、`0xA4`（克隆上下文写）、`0xA3`（A3 门闸）——**没有数据端点 OUT 提交**。

## 3. 方案路线

### Phase 0 可行性侦察（0.5–1 h，必须先做）

目的：确定管理程序"只用读"还是"必须写"，从而决定 Phase 2 的投入规模。

1. 清理本机 `320F:706E` 的失败节点（设备管理器显示隐藏设备后删除），并换一个全新序列号；
2. 克隆改为：`320F:706E` + **G3M 的 66 字节复合配置** + 两份报告描述符（93/158）+ 产品串
   `G3M PRO` + 厂商串（从设备读回，见 `mx.dv` 的 strings 部分）；
3. USBPcap 抓 **HECATE Connect 启动与进入"按键设定/其他设定"页**的完整动作；
4. 观察：`GET_REPORT`/`SET_REPORT` 序列、是否轮询 `0x82`、是否对 `0x05` 写入、写入的包形态。

**判定点（写进报告的结论）**

- 只读 → Phase 1 完成后管理程序即可"看待状态"，价值高、成本低；
- 必须写 → Phase 2 是硬门槛，进入"opcode 对照"研究。

### Phase 1 复合拓扑 + IN 转发（1–2 h）

1. **先量后改**：加探针打印 `hidd_init` 之后每个 HID 实例实际绑定的端点（上次失败根因就是按
   描述符顺序猜实例号，`tud_hid_n_ready(0)` 恒假、`hq 86 / 15238`）；
2. `CFG_TUD_HID=2`，配置描述符**原样服务 66 字节**；
3. `0xA2` 按 `ep` 分发：`0x81`→实例 0（鼠标 7B）、`0x82`→实例 1（键盘 8B / 厂商 64B）；
4. 独立身份做实验（`046D:C077` + 新序列号）验证不破坏鼠标，再切 `320F:706E`；
5. **验收**：PC 出现与真鼠标一致的 5 个集合；管理程序能识别设备并显示当前配置（读通）；
   鼠标位移/按键/滚轮/侧键仍全部正常。

### Phase 2 厂商 OUT 下行（2–4 h 研究 + 实现；或数天）

核心问题：**右片固件能否向鼠标的 OUT 端点提交一次 64 字节传输？**

1. 先在**官方 LEFT 固件**里对照已知隐藏 opcode 清单（`0x08`、`0x0D–0x18`），找"提交 OUT 传输"
   类命令；同时在右片镜像里搜 `usb_xfer_submit` 的调用点，看是否有非 EP0 的路径；
2. 分支：
   - **存在** → 用它实现双向代理（LEFT 新增帧类型：OUT 提交；右片回执；盒子上验证
     "改 DPI → 鼠标灯/手感立刻变化"）；
   - **不存在** → 两条落地路径：
     - A（立即可用）：管理程序只在**鼠标直插 PC** 时用于配置，盒子负责使用；
     - B（长期）：自研右片 host 栈（backlog 的 right-chip host-stack port），获得完整双向代理。

### Phase 3 稳定性与回归（1 h）

- 身份/序列号策略：每次实验独立序列号，失败即换，不污染整个 VID 族；
- 回归补充：复合枚举（5 个集合）、`0x82` IN 转发、`0x05` OUT 下行（若实现）；
- 验收清单（写进 HANDOVER）：能识别 / 能读 / 能写 / 写后生效 / 鼠标功能不受影响。

## 4. 推荐顺序与工作量

| 步骤 | 内容 | 工作量 | 收益 |
|---|---|---|---|
| 1 | Phase 0 侦察 | 0.5–1 h | 决定后续投入，且能立刻知道"读"是否足够 |
| 2 | Phase 1 复合 + IN 转发 | 1–2 h | PC 认成真 G3M PRO；宏（MI_01）可用；管理程序可读 |
| 3 | Phase 2 opcode 对照研究 | 0.5 h（只研究） | 判定双向代理是否可行 |
| 4 | Phase 2 实现（若可行） | 2–4 h | 管理程序可写配置 |
| 5 | Phase 3 回归与文档 | 1 h | 稳定性 |

## 5. 风险与前提

1. **320F 族挂死**：Phase 0 必须先清节点，否则一上来就 `CM_PROB_FAILED_START`；
2. **别让管理程序升级鼠标固件**：固件一变，已采集的端点/描述符/厂商特征全部失效；
3. **不要解析 64 字节配置语义**：做**纯透传**最稳；解析属于 Route C 深水区，且对目标没必要；
4. **失败要完整回退**：保留一份可烧的"夹具 4 构建"作为退路（当前稳定态：`mnt=1`、
   7 字节直送、侧键可用、回归 100 passed）；
5. 一次只加一个变量；每个阶段都要有"没破坏鼠标基本功能"的验证。

# 执行记录（2026-11-10）：Phase 0 完成 + Phase 2 结构定位

## Phase 0 判定结论：**必须写，且不能走 EP0 绕开**

抓包（`work/usbpcap/cfg2.pcap`，G3M PRO 直插 PC，HECATE Connect 启动 + 改按键 + 改 DPI）：

| 观察项 | 结果 |
|---|---|
| 厂商 **OUT** `0x05`，64 B 写包 | **216 帧** |
| 厂商 **IN** `0x82`，64 B 回包 | **216 帧**（严格 1:1 请求/应答） |
| 类接口控制传输 | 只有 `SET_IDLE`（wIndex=0 与 1）+ `GET_DESCRIPTOR` |
| `SET_REPORT` / `GET_REPORT` | **完全没有** |
| 鼠标 `0x81` 7 B | 24307 帧（正常） |
| 命令帧形态 | OUT/IN 均以 `04 aa 00 aa …` 开头，应答尾部带 `ff` |

**结论**：配置读写**全部**走厂商数据端点，不走 EP0 ⇒ 无法用现有的 `0xA1`（EP0 隧道）代理，
**Phase 2 的 OUT 下行是硬门槛**。

## Phase 2 静态定位（右片 `官方固件\V3.7_RIGHT.bin`）

镜像结构（app 在文件偏移 `0x10000`，6 段）：

| 段 | load | 长度 | 说明 |
|---|---|---|---|
| 0 | `0x3C030020` | `0xA26C` | DROM（常量/字符串） |
| 1 | `0x3FC93E00` | `0x2C38` | DRAM 数据 |
| 2 | `0x40374000` | `0x3144` | 代码/数据 |
| 3 | **`0x42000020`** | **`0x26ACC`** | **IROM（应用代码）** |
| 4 | `0x40377144` | `0xCC00` | DRAM |
| 5 | `0x600FE100` | `0x1C` | 外设寄存器初值 |

`usb_xfer_submit`（`0x4200d3e4`）的 5 个调用点：

| 调用点 | 归属 |
|---|---|
| `0x4200DFEB` | EP0 隧道路径（`0xA1` 用） |
| `0x4200EA45` | 另一处武装路径 |
| `0x42010081` / `0x420100F6` / `0x4201023D` | 事件处理器内的**重挂**路径 |

**关键发现**：`0x420101A6` 起是一段**通用武装例程** —— 取端点号（`extui a8,a9,0,4`）→ 按方向判断
→ 填 URB（pipe/buffer/callback，`s32i` 到 a2+12..72）→ `call8 usb_xfer_submit`。
旁边 `0x420100FC` 是**按描述符遍历接口/端点并武装**的循环（8×8 双层）。

⇒ **"给任意端点提交一次传输"的能力右片本来就有**，只是没有从链路协议暴露
（`frame_forward` 仅认 `0xA0/0xA1/0x1A/0xA4/0xA3`）。

## Phase 2 落地需要的两件事（及其门槛）

1. **补一个链路 opcode**（如 `0xA5` = "OUT 提交"：`<ep> <len> <data…>`）→ 填 URB 后调用
   `0x42010197` 这条武装例程；回执用现有错误帧或新帧类型；
2. **能刷写右片**：目前只验证过刷 LEFT（CH343/COM3）；右片的烧写接口**尚未确认**
   —— 这是 Phase 2 的**唯一硬门槛**。已有回滚素材：`官方固件\V3.7_RIGHT.bin`（341,824 B，
   含 bootloader@0 + app@0x10000）与出厂 `烧录工具1_7.exe`。

## 下一步（按顺序，不并行）

1. **确认右片可刷**：查 `烧录工具1_7.exe` 如何选择芯片（字符串/资源），或用万用表/逻辑分析仪
   找右片的 UART/USB 下载口；确认后再动代码；
2. 在右片镜像里找 `frame_forward`（`0x4200F6C4`）的分派表，确认是否有**空闲 opcode** 与可用空洞；
3. 写 `0xA5` 处理：解析 `<ep><len><data>` → 定位武装例程 → 提交；
4. LEFT 侧：把 PC 下发到 MI_01 OUT `0x05` 的 64 字节数据（`SET_REPORT`/HID OUT）转成 `0xA5` 帧；
5. 验证：管理程序改 DPI → 鼠标手感/灯效立即变化；断线可回滚。

> 在此之前，HECATE Connect 只能"直插鼠标时配置"，盒子上使用（当前稳定态）。

# 执行记录（2026-11-10 三）：右片刷写路径确认（门槛解除）

## 出厂工具的刷写逻辑（从 `flasher.pyc` 直接读出的结论）

`官方固件\烧录工具1_7.exe` 是 PyInstaller 包，`modules\flasher.pyc`（Python 3.12）里
的 esptool 调用参数序列**逐字**如下：

```
--chip esp32s3   --port <com_port>   --baud 921600   write_flash 0x0 <bin_path>
```

- 固件来源：`https://github.com/terrafirma2021/MAKCM_v2_files/raw/main/MAKCU_LEFT.bin`
  与 `.../MAKCU_RIGHT.bin`（即我们手里的 `V3.2_LEFT.bin` / `V3.7_RIGHT.bin`）；
- 成功判据：输出里出现 `Hash of data verified.`；异常判据：出现 `WARNING: ESP32-S3`；
- 串口是**按 VID/PID 自动枚举**（`serial_handler.find_com_port`），并非写死 COM 号；
- 工具还带一个设备命令层（`GET_BAUD_RATE` / `SET_BAUD_RATE`（LSB 格式）/ 设备日志级别 /
  `reset_mcu`），走的是盒子控制口的命令行协议——与我们已还原的 `.km.` 协议同族。

**⇒ 两片都是"单条 esptool 写 0x0"，镜像里自带 bootloader(@0) + app(@0x10000)。**

## 右片刷写流程（已确认，硬件侧由用户提供）

1. **按住 BOOT，把数据线接到右侧 USB 口** → 右片进入 ROM 下载口（串口出现）；
2. 执行：

```
D:\esp-tools\python_env\idf5.4_py3.11_env\Scripts\esptool.exe ^
  --chip esp32s3 --port COMx --baud 921600 write_flash 0x0 D:\JinPeng\MagicBox\官方固件\V3.7_RIGHT.bin
```

3. 看到 `Hash of data verified.` 即成功；拔掉数据线、正常上电（不按 BOOT）；
4. **回滚**：同一命令写回原厂 `V3.7_RIGHT.bin` 即可（本机 `tools\reflash.ps1` 已是同一波特率套路，
   可扩展一个 `-Right` 分支复用）。

## 操作要点（后续每次改右片都照这个来）

1. 右片原生 USB 接电脑（`VID_303A&PID_1001`，COM 号可能变化，用 `esptool --port` 指过去）；
2. 刷写前**先全片回读备份**（28 s，4 MB）；
3. `write_flash 0x0 <image>`，看 `Hash of data verified.`；
4. 刷后**回读前 64 KB 比对**（快速确认）；
5. 回滚 = 用备份或出厂镜像同命令写回。

## 副作用与注意事项

- 刷右片会复位右片 ⇒ 它会把已枚举的鼠标丢掉；需要重新 `mx.ac`（自动克隆）+ `mx.rs`（重启枚举），
  或直接拔插鼠标；
- 实测发现刷完后**左片控制口 COM3 掉线**（插右片数据线时挤掉/左片复位），需确认左侧数据线在位；
  这是台架接线问题，不是固件问题。

# 执行记录（2026-11-10 五）：补丁方案定稿（可执行）

## 1. 分派表实测（`frame_forward` @ `0x4200F6C4`）

```
cmd==0xA3 -> 0x4200FAE0  (A3 门闸)
cmd==0xA0 -> 0x4200FAC0  (EP0 方向)
cmd==0xA1 -> 0x4200FC74  (EP0 隧道)
cmd==0x1A -> 0x4200F854  (快照)
cmd==0xA4 -> 0x4200FE44  (克隆上下文写)
cmd==0xB1 -> 0x4200F795  ← 只回 ACK，无任何动作（空闲）
其他      -> 0x420248E4  (错误帧)
```

**补丁点**：`0x4200F732` 的 `movi a9, 177` + `0x4200F735` 的 `beq a8, a9, 0x4200F795`
—— 把这条 `beq` 的目标改成新例程地址，即一条指令的补丁。

## 2. 镜像校验结构（实测）

| 项 | 值 |
|---|---|
| app 镜像 | 276,288 B（文件偏移 `0x10000` 起），6 段 |
| 段表结束 | app 内偏移 `0x43718` |
| 附加摘要 | `hash_appended = 1`，尾部 32 B 为 SHA-256 |
| **摘要覆盖范围（实测匹配）** | `app[0 : 0x43720]`（即末 32 B 之前全部） |
| 当前摘要 | `e6dbce9c…6439c6a2` |

⇒ 补丁后**重算这 32 字节**即可通过 bootloader 校验。

## 3. 新代码放哪：追加一个段（没有代码洞）

IROM 段（`0x42000020` + `0x26ACC`）内**没有 ≥60 字节的连续空洞**，所以新例程用
**追加段**的方式：在 `0x42026AEC` 之后（例如 `0x42027000`）新增一段，把 blob 放在那里，
同时改 `app[1]` 段数、补段头、重算摘要。

## 4. blob 要做什么（`0xA5` 或复用 `0xB1`）

入参：`a10` = 帧指针（payload 在帧内），格式约定 `<ep:u8> <len:u16> <data…>`：

```
1) 校验 len <= 64、ep 合法；
2) 在 DRAM 里准备 64 字节缓冲 + 一个 URB 结构（pipe/endpoint/长度/回调 = 现有 0x4200FF10）；
3) 调用武装例程（0x42010197 那条路径）或直接 usb_xfer_submit(0x4200D3E4)；
4) 回 ACK 帧。
```

## 5. 五个执行步骤（顺序固定）

| # | 内容 | 依赖硬件 |
|---|---|---|
| 1 | 用 IDF 工具链编一个 `blob.c`（链接地址钉在 `0x42027000`），抽出机器码 | 无 |
| 2 | Python 脚本：改 app 段（新增段 + 改 `0xB1` 分支）→ 重算摘要 → 产出 `V3.7_RIGHT_patched.bin` | 无 |
| 3 | 右片数据线接电脑（`VID_303A&PID_1001`），全片回读备份 | 右线 |
| 4 | `esptool write_flash 0x0 V3.7_RIGHT_patched.bin` + 回读比对 | 右线 |
| 5 | LEFT 侧把 MI_01 的 OUT `0x05` 数据转成 `0xB1` 帧；管理程序改 DPI 验证 | 中线 + 鼠标 |

**风险控制**：第 2 步产出后先在 PC 上做"静态自检"（段表/摘要/分支目标全对），
再刷；任何时候可用 `V3.7_RIGHT.bin` 或 `hw_right_full_before_patch.bin` 回滚。

# 执行记录（2026-11-10 六）：URB / pipe 结构解出（补丁所需的最后一块知识）

## `usb_xfer_submit(0x4200D3E4)` 的入参与内部字段

调用约定：`urb = 参数`（重挂路径传的是 `struct+12`）。

```
urb+8    pipe        ← **驱动分配的 pipe 句柄（不是编码值）**，内部用 pipe+0xA00 取 pipe 结构，
                        *(pipeStruct+100) 取 pipe context，*(pipe+0) 校验有效
urb+12   desc        ← **端点描述符指针**：提交时读 *(desc+2)=bEndpointAddress（bit7=IN）、
                        *(desc+3)&3、*(desc+4/5)&0x7FF=wMaxPacketSize（IN>0x140 / OUT>0xF0 报错）
urb+20   标志        ← 必须 (值 & 3)==0
urb+24   数据缓冲    ← 必须 4 字节对齐（(值 & 3)==0）
urb+28   长度
urb+44   状态        ← == -6 时走特殊分支
urb+56   完成回调    ← 0x4200FF10（事件处理器）
urb+60   自身指针
urb+17   方向/状态标志（重挂时 = 0 或 1<<(n-1)）
```

## pipe 表（关键发现）

- `0x3FC9FD64` = **pipe 指针数组**（按端点号 0..7 索引）；
  武装循环里 `callx8 [0x4037B294]`（分配 8 字节）后 `addx4 a8, a7, a8; s32i a10, a8, 0` 写入该数组
  ⇒ **8 个端点的 pipe 都会被创建**，包括 OUT 的 EP5；
- `0x3FC9FC14` = 另一张按端点索引的句柄表；`0x3FC9FD34` = 每端点 armed 标志；`0x3FC9FD3C`/`0x3FC9FD5C` 为状态字。

## blob 设计（据此定稿）

```c
/* 入参 a10 = 帧指针；payload = <ep:u8><len:u16><data…> */
ep   = payload[0] & 0x0F;
len  = payload[1] | payload[2] << 8;      /* <= 64 */
pipe = *(uint32_t *)(0x3FC9FD64 + 4 * ep); /* 直接复用已存在的 pipe */
desc = &static_ep_desc;                    /* 07 05 05 03 40 00 01 自造 */
memcpy(buf, payload + 3, len);             /* buf 复用帧的 DRAM 缓冲（4 字节对齐） */
fill_urb(pipe, desc, buf, len, cb = 0x4200FF10, self = &urb);
usb_xfer_submit(&urb);
ack(frame);
```

## 剩余未知（很小）

1. `urb+17` 的确切语义（重挂时 `bgeui epByte,3` 分支决定 0 或 `1<<(n-1)`）——需要再读几行；
2. OUT 端点是否需要在提交前把 armed 标志（`0x3FC9FD34`）也置位；
3. pipe 表里 EP5 的指针是否非零（若为 0 说明 OUT 端点未被创建，需另想办法）。

## 工作量与节奏（诚实评估）

| 任务 | 估时 | 需要硬件 |
|---|---|---|
| 补完上述 3 个未知（静态） | 0.5–1 h | 无 |
| 写 blob + 补丁脚本 + 静态自检 | 1–1.5 h | 无 |
| 刷写与调通（每轮约 2–3 分钟：换线→刷→换回→`mx.ac`/`mx.rs`→验证） | 1–2 h，约 5–10 轮 | 右线+中线 |
| LEFT 侧转发 `0x05` → `0xB1` | 0.5 h | 中线 |

**总计约 3–5 小时**。当前已交付的鼠标功能（移动/左右中键/滚轮/侧键）不受影响，
补丁失败可用 `V3.7_RIGHT.bin` 或 `hw_right_full_before_patch.bin` 完整回滚。

# 执行记录（2026-11-10 七）：右片补丁链路打通 + 内存读探针

## 已彻底解决（本轮硬成果）

### 1. ESP app 镜像的完整改造流程（可复用）

| 项 | 结论（实测） |
|---|---|
| 段表 | app 在文件 `0x10000`，6 段；IROM `0x42000020` 长 `0x26ACC` |
| **校验和** | `XOR(0xEF, 所有段数据)`，放在段后 16 字节对齐块的**最后一字节** |
| **附加摘要** | SHA-256 覆盖 `[0, 摘要偏移)`，即包含校验和字节 |
| 新代码位置 | **不加新段**，把 blob 接在 IROM 段末尾并**扩展该段长度**（加新段会导致 bootloader 不加载） |
| 校验工具 | `esptool --chip esp32s3 image_info <app>` 必须报 `Checksum … (valid)` 与 `Validation hash … (valid)` |

### 2. 分派器补丁点

`0x4200F738` 的 3 字节 `j 0x4200F78C`（未识别命令 → 错误帧）改为 `j 0x42026AEC`（blob 蹦床）。
`0xB1` 的 ACK 分支保持原样 → 我们的入口就是**任何未识别 opcode**，实际用 `0xA5`。

### 3. blob 必须用"汇编蹦床 + call0 C 体"

被 `j` 跳入（不是 `call8`）⇒ **不能用 `entry a1,N`**（寄存器窗口旋转会把 `a2` 指到别处，
实测读到垃圾、回执 `01 00 00 00`）。正确做法：

```
patch_entry:            ; 0x42026AEC
    addi a1,a1,-64
    s32i a0..a11 (a1+0..40)
    call0 patch_body    ; call0 ABI：a2 原样作为参数，C 体自己平衡 a1
    l32i 恢复 a0..a11
    addi a1,a1,64
    j 0x4200F795        ; 回到分派器的发送路径
```

### 4. 右片内存读探针（新能力，已上机可用）

`0xA5` 的 `op=0xEE`：payload `<EE><len16><addr:u32 LE><count:u8>`，回传 `count` 字节原始内存。
工具：`tools/rd_right.ps1`（`Read-RightBytes -Addr … -Count …`，按 8 字节分块，
回包超过 ~8 字节会撑爆右片 TX 缓冲）。

实测：`0x3FC9FD64` 读出 `0x3FCA7214`（有效 DRAM 指针），但再次读取变 0 —— 该地址疑似临时变量，
不是稳定的 pipe 表；`0x3FC9FC00..FE00` 整簇 dump 中大量为 0 或读超时。

## 未解决（下一轮的明确目标）

1. **定位驱动的"端点 → pipe + 端点描述符"结构**：`0x3FC9FD64` 不是它。
   建议路径：从 `usb_xfer_submit` 里调用的 `0x4200C920`（通道分配）反查其调用者与入参结构，
   或在枚举回调里找写入描述符指针的 store；
2. **LEFT 侧双接口（D38）**：PC 的 OUT 写要先进到左片（MI_01 的 OUT 端点），才谈得上转成 `0xA5`；
3. 二者都完成后，HECATE Connect 才能经盒子改写鼠标配置。

## 当前设备状态

- 右片：跑**带补丁的固件**（`work\V3.7_RIGHT_patchedB.bin`），鼠标功能完全正常
  （`state=00`、`mx.ac` 成功、frames/rx 持续增长）；
- 补丁只增加了一条未识别 opcode 的入口（`0xA5`），已被实测不会影响正常通路；
- 回滚：`tools/flash_right.ps1`（默认刷出厂镜像）或 `hw_right_full_before_patch.bin`。

# 稳定性收尾（2026-11-10）：身份固定 + 异步 OUT 转发

## 问题 1：克隆身份会漂移

实测盒子后的鼠标在不同时刻上报过 `0E8C:F0DB`、`0ECC:F0DF`（不是 `320F:706E`）——
PC 侧没有对应 INF，管理程序就不认。原因有两层：

1. `mx.vp` 的运行时覆盖存在 **RTC**，**刷写会清 RTC**，覆盖丢失；
2. 更隐蔽：RTC 里**旧固件布局的残留值**会被当成 `vid_ovr`，在 `makcu_clone_adopt()`
   里**覆盖掉编译期强制值**（`mx.fv` 探针实测：`force=320f:706e` 但 `ovr=0ecc:f0df`）。

修法：新增构建选项 `-DMB_FORCE_VIDPID=320f706e`（转发给 `makcu_clone` 组件），
并且**放在覆盖块之后**、同时把 `vid_ovr/pid_ovr` 写回强制值。实测：

```
mx.fv -> force=320f:706e  ovr=320f:706e  dev=0f326e70
mx.ac -> 1:320f:706e:93      mx.if -> 2 93:81:0 158:82:1
PC    -> 复合设备 + MI_00/MI_01 + 5 个集合，全部 OK
```

## 问题 2：OUT 写入回执率只有 66/184

`out_to_right()` 原先在 **TinyUSB 回调里同步等待** `makcu_link_request`（≤300 ms），
阻塞导致后续主机写入无法武装、回执大量超时。

修法：改为 **队列 + 独立工作任务**（`km_outq`，深度 6，优先级 8），回调只入队立即返回；
`mx.ox` 增加 `dropped` 字段观察队列溢出。

# 最后一修（2026-11-10）：回执竞态 → **100% 成功率**

## 现象

应用的配置写入虽然都能到达鼠标（`in82 == out`），但**右片的 0xA5 回执**只有零星命中：
台架空闲时 5/5，实机 1 kHz 报文流下 1/17。

## 根因

`makcu_link_request()` 等的是**共享的 `s_last_rx_cmd`/`s_last_rx`**，而 A2 报告流每秒上千帧，
我们的 `0xA5` 回执在 1 ms 轮询窗口内就被下一条报告覆盖掉了。

## 修复

在帧处理里增加**按命令匹配的专用待收缓冲**：

```c
if (s_req_cmd != 0 && f->cmd == s_req_cmd && !s_req_got) {
    s_req_len = min(f->len, sizeof s_req_buf);
    memcpy(s_req_buf, f->payload, s_req_len);
    s_req_got = true;         /* request() 只等这个标志 */
}
```

## 实测（修复后）

```
基线: out=32 ok=32 in82=32 dropped=0
结束: out=51 ok=51 in82=51 ack=00
增量: out=19 ok=19   → 成功率 100%
```

## 顺带修的另一个坑（右片）

异步 OUT 原先在 transfer 的完成回调里 `usb_host_transfer_free()` 它自己 —— USB 栈仍在引用，
导致堆损坏、**整片失联**（`mx.ln 1c` 无回执）．改为**预分配 3 个 transfer 的池**（回调只置空闲标志）。
