# Android 采集卡 + 手机 YOLO 低延迟方案（当前版）

> 目标设备：iQOO 15 + 海备思 CA1331（UHC10 / MS2130）+ 联想拯救者 R9000P
>
> 目标：手机端运行 YOLO 检测 PC 画面，结果叠加显示；玻璃到玻璃尽量 ≤100ms。
>
> 当前策略：**先跑通，最后做性能优化**；回控 PC 暂不处理。

---

## 1. 结论摘要

| 决策 | 当前结论 |
|---|---|
| 采集卡 | **不换**。MS2130 在 100ms 目标下够用；换卡通常只省 10–20ms |
| 首版形态 | 通用 UVC + LiteRT/TFLite GPU + COCO 模型 + Canvas 画框 |
| 采集格式 | **1080p60 YUY2**，不要 MJPEG；PC 固定 1080p60 |
| 推理帧率 | MVP 可先 30fps；采集端尽量保持 60fps |
| 延迟预期 | 30fps MVP 约 90–110ms；优化后 65–85ms；60fps 优化 55–75ms |
| 性能优化 | 放到最后：60fps、GPU 预处理、QNN INT8、SurfaceView/GLES、144Hz、零拷贝 |
| 回控 | 只预留接口，不影响当前渲染链路 |

**一句话：这张卡不是 50ms 级的卡，但在“尽量 100ms”目标下够用；先把链路跑通，再决定是否值得优化。**

---

## 2. 目标与边界

### 2.1 当前目标

- PC 画面经 HDMI 采集卡进入 iQOO 15；
- 手机端运行 YOLO，检测特定物体；
- 手机屏幕显示原始画面 + 检测框；
- 玻璃到玻璃延迟尽量 ≤100ms；
- 先验证全链路可运行，再做性能优化。

### 2.2 当前不做

- 不追 50ms 硬指标；
- 不做 4K 采集；
- 不做回控 PC（只预留 `DetectionSink`）；
- 不做 iOS；
- 不先写自定义 libusb/UVC 驱动；
- 不先做零拷贝、QNN、60fps 多线程管线。

---

## 3. 硬件链路

### 3.1 连接图

```text
R9000P HDMI 输出（1920×1080 60Hz，RGB Full，HDR off）
  → 海备思 CA1331 / UHC10（MS2130）
       HDMI IN：4K60 兼容，但只采集 1080p60
       USB OUT：USB 3.0 5Gbps，UVC 免驱
       PD IN：100W 直通，边采集边给手机充电
  → iQOO 15 USB-C（USB 3.2 Gen1，5Gbps）
```

- 优先 **USB-C 直连 + PD 充电器**，少一个 Hub 就少一个降速变量；
- 如果 PD 直通导致 USB 降到 2.0，再换 USB 3.0 + PD Hub；
- 如果卡没有 HDMI 环出、又需要接显示器，加一个 HDMI 1×2 分配器（带 EDID）。

### 3.2 设备规格

| 设备 | 关键规格 | 对方案的影响 |
|---|---|---|
| iQOO 15 | 骁龙 8 Elite Gen 5，USB 3.2 Gen1 5Gbps，3168×1440 144Hz，Android 16 / OriginOS 6，7000mAh | 带宽够 1080p60 YUY2；144Hz 有利于显示延迟；注意 16KB page size 和后台限制 |
| R9000P | 内屏 2560×1600，HDMI 输出 | 内屏和 HDMI 只能复制/扩展；要低延迟需 1080p60 复制或外接显示器 |
| CA1331 / UHC10 | MS2130，4K60 输入，1080p60 采集，YUY2/MJPEG，USB 3.0，PD100W | 卡内缓冲约 30–40ms；必须强制 YUY2；避免 4K 输入缩放 |

### 3.3 物料清单

- 海备思 CA1331 采集卡；
- USB-C 5Gbps 全功能线（不要用充电线）；
- 65W/100W PD 充电器；
- HDMI 2.1 线；
- 可选：HDMI 1×2 分配器（需要外接显示器时）；
- 可选：磁吸散热背夹（60fps 持续推理时建议）。

## 4. 软件架构

### 4.1 MVP 架构（先跑通）

```text
UVC 采集（Camera2 外接 或 AndroidUSBCamera / libuvccamera）
  → NV21/YUV 帧（1080p30/60，带时间戳）
  → CPU/libyuv 转 640×640 RGB
  → LiteRT/TFLite GPU delegate
  → YOLO 模型（先用 COCO 预训练验证）
  → Kotlin/C++ NMS
  → 自定义 View Canvas 画框
  → TextureView 显示
```

**MVP 原则：能用现成库就用现成库，不碰热路径优化。**

| 模块 | MVP 选择 | 后续替换 |
|---|---|---|
| 采集 | Camera2 外接（若系统识别）；否则 AndroidUSBCamera / libuvccamera | 自写 libusb/UVC |
| 预览 | TextureView | SurfaceView + GLES |
| 帧转换 | libyuv JNI，NV21→640 RGB | GPU shader 直接转换 |
| 推理 | LiteRT/TFLite GPU delegate，FP16 | QNN INT8 |
| 模型 | YOLOv8n / YOLO11n COCO 640 | 自定义 YOLO26n 单类 |
| 后处理 | Kotlin/C++ NMS | NMS-free + GPU |
| 画框 | 自定义 View Canvas | GL 同一 pass |
| 线程 | 单推理线程，忙则丢帧 | 采集/推理/渲染三线程 |
| 延迟统计 | 帧时间戳 + 绘制时间戳 | Perfetto 分段 |

### 4.2 目标态架构（最后优化）

```text
UVC  native（libusb）
  → YUY2 帧
  → GPU 纹理（PBO / AHardwareBuffer）
  → shader：YUYV→RGB + letterbox 640×640
  → QNN INT8 YOLO26n（NMS-free）
  → GL 叠加框
  → SurfaceView，144Hz 面板
```

优化顺序按收益排序：

1. 60fps 采集 + 推理；
2. 干掉 CPU YUV 转换（GPU 预处理）；
3. QNN INT8；
4. SurfaceView + GLES 画框；
5. 144Hz 帧调度；
6. 线程优先级、热控、零拷贝。

## 5. 延迟预算

按 MS2130 卡内 30–40ms 估算（以实测为准）：

| 阶段 | 30fps MVP | 30fps 优化后 | 60fps 优化后 |
|---|---:|---:|---:|
| PC 采样/合成 | 16.7ms | 16.7ms | 8.3ms |
| 采集卡 | 30–40ms | 30–40ms | 30–40ms |
| USB 组帧/传输 | 5–10ms | 3ms | 3ms |
| 预处理 | 8–15ms | 2ms | 2ms |
| 推理 | 12–20ms | 5–8ms | 5–8ms |
| 后处理 | 3–5ms | 1ms | 1ms |
| 渲染/显示 | 3–7ms | 3–5ms | 3–5ms |
| **估算 P50** | **90–110ms** | **65–85ms** | **55–75ms** |
| **估算 P95** | **110–130ms** | **85–100ms** | **75–90ms** |

### 5.1 30fps 与 60fps 的区别

- 30fps 的帧间隔是 33.3ms，采样和卡内缓冲的帧时间都会变长；
- 30fps 不会降低延迟，反而可能增加 10–30ms；
- 建议：**采集端保持 1080p60**，推理可以先 30fps（隔帧跑），显示用最新帧；
- 如果模型能跑 60fps，直接 60fps，100ms 余量最大。

### 5.2 测量方法

- 应用内打点：帧到达时间、预处理完成、推理完成、绘制提交；
- 玻璃到玻璃：PC 显示毫秒计时器/白闪，手机 240fps 慢动作同时拍两块屏幕；
- 记录 P50/P95/P99，不要只看平均值；
- 每次优化前后用同一方法复测。

## 6. 采集卡与 PC 设置

### 6.1 采集卡设置

| 项目 | 设置 | 原因 |
|---|---|---|
| 分辨率 | 1920×1080 | 避免 4K→1080p 卡内缩放 |
| 帧率 | 60fps | 降低采样/缓冲的帧时间 |
| 格式 | **YUY2** | 无编码压缩；MJPEG 多 8–12ms 解码 |
| USB | 5Gbps | 1080p60 YUY2 约 2Gbps；USB 2.0 会强制 MJPEG |
| PD | 100W 直通 | 边采集边充电；需确认不降速到 USB 2.0 |

**关于“压缩”：**

- 1080p 进、1080p 采：没有分辨率缩放；
- 选 YUY2：没有编码压缩；
- 但仍有 4:2:2 色度抽样和卡内 30–40ms 缓冲；
- 所以“不压缩”不等于“零延迟”。

### 6.2 PC 设置

- 分辨率：1920×1080，刷新率 60Hz；
- 关闭 HDR / Auto HDR；
- 输出 RGB Full 0–255；
- NVIDIA 控制面板：缩放选“无缩放/显示器缩放”；
- 游戏内垂直同步按可接受度关闭，减少 1 帧延迟；
- 内屏 2.5K 镜像会导致卡缩放：要么内屏也 1080p60 复制，要么外接 1080p60 显示器。

## 7. 模型与数据

### 7.1 MVP

- 先用 COCO 预训练的 YOLOv8n / YOLO11n，验证“采集→推理→画框”链路；
- 输入 640×640，FP16/FP32，LiteRT GPU delegate；
- 不急着做 INT8、不急着换 YOLO26。

### 7.2 特定物体

- 自建数据集：3–5k 帧，来自采集卡实拍，不用 PC 截图代替；
- 标注后训练 YOLO26n / YOLO11n，单类或少量类；
- 导出 640，QNN INT8；校准集用采集卡实拍帧；
- 目标小于约 20px 时，640 可能不够：
  - 优先 ROI 裁剪；
  - 其次 768/960 输入（30fps）；
  - 2×2 分块精度最好，但 60fps 基本不可能。

## 8. 分阶段计划

| 阶段 | 周期 | 任务 | 退出标准 |
|---|---|---|---|
| **P0 硬件验证** | 2–3 天 | 通用 UVC App 验证 1080p60 YUY2；`dumpsys usb` 看 5Gbps；检查 Camera2 是否识别外接摄像头；粗测延迟 | 1080p 稳定 10 分钟；5Gbps；延迟有基线 |

| **P2 自定义模型** | 1–2 周 | 采集数据、标注、训练、导出、替换模型 | 目标可检出；精度可接受；≥20fps |
| **P3 稳定性** | 1 周 | 重连、权限、热、30/60fps、异常恢复 | 1 小时稳定；≤110ms |
| **P4 性能优化** | 2–3 周 | 只在 P3 不达标时做：60fps、GPU 预处理、QNN、SurfaceView、144Hz、零拷贝 | P95 ≤100ms；热稳定 |

**总周期：6–9 周**，取决于数据集。P4 不是必做项；如果 P3 已经“尽量 100ms 以内”，可以先交付。

## 10. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| MS2130 卡内 30–40ms | 端到端 90–110ms | 100ms 目标下可接受；实测 >50ms 再考虑换 Elgato/Magewell |
| 默认走 MJPEG | +8–12ms 解码 | 显式选 YUY2 1080p60 |
| 4K 输入触发卡内缩放 | +10–20ms、画面软 | PC 固定 1080p60 |
| PD 直通降速到 USB 2.0 | 1080p60 YUY2 带宽不够 | `dumpsys usb` 验证；换线/换 Hub |
| 卡无环出 | 没法接显示器 | HDMI 分配器，或内屏 1080p 复制 |
| Camera2 不识别外接摄像头 | 只能用 libuvccamera | P0 先检查；没有就走 AndroidUSBCamera |
| Android 16 / 16KB page size | native 库崩溃 | NDK r28+，16KB 对齐重编 |
| OriginOS 后台限制 | USB 断/服务被杀 | 前台服务、电池白名单、自启动 |
| 手机热降频 | 30 分钟后掉帧 | 散热背夹、PD 旁路充电、30fps 降级 |
| 特定物体数据不足 | 模型精度差 | 采集卡实拍数据、负样本、ROI、768/960 |
| 回控后加 | 闭环延迟超预期 | 预留 `DetectionSink`；闭环按 70–100ms 预估 |

## 11. 回控预留（当前不做）

```text
DetectionFrame {
  frameId,
  captureTimestampNs,
  boxes: [{x, y, w, h, score, classId}]
}
```

- 推理线程只产出 `DetectionFrame`；
- 控制线程独立消费，深度 1，丢旧不排队；
- 未来无论走网络、ADB 还是 HID，都从 `DetectionSink` 接；
- 现在不让控制逻辑影响渲染/推理延迟；
- 闭环预算：检测 70–90ms + 控制 10–30ms = 80–120ms。如果最终闭环也要 ≤100ms，检测端需要压到 70–80ms。
