# 瞄准模块（App 端闭环瞄准，AIM 版）

> 面向：`com.magicbullet.capture` 的「瞄准」Tab。
> 控制口协议：子项目 `AMagicBox-Rebuild/docs/API-control-port.md`（2026-11-11 版）。
> 本版对应固件 2026-11-11 12:40（`0x3C AIM` / `0x3D AIM_STATE`）。

---

## 1. 职责划分

| 层 | 干什么 | 不干什么 |
|---|---|---|
| `YoloDetector` + `Postprocess` | 出检测框（归一化到采集帧） | 不管瞄准 |
| `TargetTracker` | head↔body 聚类、逐帧跟踪、速度估计（最小二乘 + EMA） | 不管发什么命令 |
| `AimController` | 选目标、算 Δpx、前馈、clamp、发 `0x3C AIM` / `0x37 STOP`、轮询 `0x3D` | 不碰像素与 USB |
| `ControlPort` | CH343 二进制收发、AIM/AIM_STATE、`0x39/0x3B/0xE1` 事件通道 | 不懂"瞄准"语义 |
| `HotkeyWatcher` | 侧键订阅（consume=1）、1 Hz 心跳、学习按键 | 不决定瞄谁 |
| `AimRectView` | 矩形范围编辑（拖 / 8 向拉伸 / 准心十字） | 不保存配置 |

`AimController`、`ControlPort` 都是进程单例：预览页喂检测，瞄准页只读状态。

---

## 2. 坐标系与准心

- 检测框归一化到采集帧；换算回像素即 PC 像素（同分辨率时 1:1）。
- `AimRect` 存归一化 `x,y,w,h`，采集模式变化不影响。
- **准心 = 矩形中心**（`anchorX/Y`）——把矩形摆到游戏准心处即完成校准。
- 目标必须落在矩形内才参与瞄准。

---

## 3. 控制律（AIM）

每帧（有新检测结果时）：

```
Δpx     = aimPoint(target) + aimOffset − anchor
前馈     Δpx += v × leadMs/1000            仅当 frames ≥ 3 且 |v| ≥ 30 px/s
counts  = Δpx × (1 / pxPerCount) × gain    pxPerCount = 1.25（本机实测常数）
clamp   |counts| ≤ maxStepCounts           默认 400
下发    0x3C AIM(dx counts, dy counts, max_ms, flags, dead_min)
           max_ms   = 10（每发时长预算 4–40 ms）
           flags    = bit0 会话钳位(4000 counts) 默认开 | bit1 极速 默认关
           dead_min = round(deadzonePx / 1.25)，默认 3 counts
死区     |Δ| < deadzonePx → 不发任何运动帧
松手/丢目标 → 0x37 SUMV_STOP（AIM(0,0) 不打断轨迹）
状态     每 500 ms 发 0x3D，读 last_result/rounds/dead_hits/aborted/gen
```

为什么用 AIM 而不是 `0x36 SUMV`：AIM 收"时长预算"而不是"速度"，固件内部按恒速剖面走完（无加减速段），单发 10 ms 就够用；同时自带死区与会话钳位，并且 `AIM_STATE` 能回答"这一发到底成没成"，不必靠猜。

### 参数含义

| 参数 | 作用 | 备注 |
|---|---|---|
| `max_ms` | 这一发必须在多少毫秒内走完 | 60 fps 取 10 ms；显式时长不再被 `mr` 地板抬高 |
| `maxStepCounts` | 单帧修正上限 | 防误检甩飞；160 counts ≈ 200 px |
| `dead_min` | 切比雪夫残差 ≤ 它即"到位"（结果码 4） | 与 `deadzonePx` 同源 |
| `flags.bit0` | 会话累计 > 4000 counts 拒绝 | 防连续误检；被拒 → `last_result=6` |
| `flags.bit1` | 极速（每报告顶到 120 counts） | 一般不用 |

## 4. 目标选择

1. 类目过滤（默认 `head,body`）；
2. `head` 按"落在 body 上部 60% 且覆盖率 ≥45%"挂到 body，一个敌人一个候选；
3. 距准心最近者优先，`headShot` 有 12 px 加权优势；
4. 连续跟踪帧数 ≥ `stableFrames`（默认 2）才动手。

瞄准点：head 中心 →（无 head）body 中心，再叠加 `aimOffsetX/Y`（像素，默认 0）。

## 5. 热键

| 项 | 值 |
|---|---|
| 默认 | **右键 `mask=0x02`，按下切换**（holdMode=false），**穿透**（consume=0，PC 照常收到该键）；侧后 0x08 / 侧前 0x10 可切换 |
| 订阅 | `0x39 EVT_CTL(enable=1, mask, push=1, consume)`；`consume` 由开关决定，默认 0=穿透 |
| 事件 | `0xE1`：`payload[6]=mask`、`payload[7]=edge` |

## 9. 验收

1. 布防后日志出现 `← AIM_STATE`（没有则是旧固件）；
2. 按住热键：`rounds`/`死区` 上涨，`dur ≤ max_ms+2`；
3. PC 收不到侧前键（`EVT_STAT.flags` bit3=1、`last_fwd=0x00`）；
4. 单帧位移 ≈ `counts × 1.25 px`（±10%）；
5. 会话钳位生效时人为大位移 → `last_result=6`、光标不动；
6. 采集 59 fps、推理 6 ms 不受影响。

## 10. 已知限制

- 无光标绝对位置反馈，Windows 缩放变化后需重标 `pxPerCount`；
- 瞄准期间真实鼠标 X/Y 被盒子丢弃（按键/滚轮透传）；
- 只在采集帧覆盖的屏幕区域内有效；
- 前馈对突然变向的目标会短暂过冲，靠 EMA 与限幅缓解。

## 11. 会话钳位为什么默认关（2026-11-11）

固件 `makcu_sumv_aim()` 里 `SUMV_AIM_LIMIT = 4000`，判定用 `s_aim_total_dx/dy` 的**累计值**，而这个累计
只在 `makcu_sumv_aim_reset()` 里清零 —— 该函数在固件里**没有任何调用点**。于是：

- 钳位开着时，累计一旦越过 4000 counts（≈5000 px），之后**每一发都回 `result=6 超限`**，直到盒子重启；
- `s_last_result` 是粘滞的，空闲时界面读到的还是上一次的结果，所以看起来像"一直在超限"。

对策：App 侧默认关闭 `flags.bit0`（`session_clamp=false`），并把它做成开关；界面在非瞄准态显示
「空闲 · rounds N · … · 上次 X」而不是把旧结果当状态。

> 可选固件两行修（需要再刷一次机）：在 `makcu_sumv_aim()` 里当 `flags & SUMV_AIM_FLAG_LIMIT == 0` 时把
> `s_aim_total_dx/dy` 清零，这样重新打开钳位时不会立刻被历史累计拒绝。

## 12. 线程约定（崩溃修复 2026-11-11）

串口读线程（`control-port-rx`）会直接回调 `ControlPort.dispatch → EvtListener`。任何从这里往下的路径
**不能碰 View**。现在已经做的三处隔离：

1. `HotkeyWatcher.onEvt` 一律 `mHandler.post` 到主线程后再处理（学习、边沿都走这条）；
2. `AimConfig.save()` 的 listener 通知改为主线程 post；
3. `AimFragment.onAimConfigChanged` 只做轻量赋值，渲染走主线程。

之前「学习按键」必崩的原因就是：`finishLearn → AimConfig.save → AimFragment.renderBudget → setText`
跑在读线程，抛 `CalledFromWrongThreadException`。
## 13. 停止帧只在轨迹在飞时发（2026-11-11）

瞄准中若**没有目标**，早期实现会每帧调一次 `0x37 SUMV_STOP`（60 帧/秒刷屏，把串口和日志都占满）。
现在用 `mTrajectoryActive` 记住"有没有一发在飞"：

- 发过 `AIM` → 置 true；
- 丢目标 / 进死区 / 松手 → 只在 true 时发一次 `SUMV_STOP` 并清位；
- 布防时复位。

实测：瞄准 3 秒无目标 → `SUMV_STOP` 0 条；松手 → 恰好 1 条。
## 14. 热键去抖（2026-11-11）

现象：右键切换自瞄时，偶尔一次点击会「开→立刻关」，PC 侧也像是收到了两次右键。

排查结论：固件 `btn_evt_filter()` 每份报告都无条件更新 `s_prev_watched`，只在真跳变时 `ring_push` + push 一次，
不存在重复推送 —— 所以两个 `down` 边沿来自**鼠标右键自身的机械抖动/重发**。穿透模式下这份抖动同时也转发给
PC，这就是"PC 好像收到两次"的原因。

处置：新增 `HotkeyGate`（150 ms 窗口）

- 切换模式的 `down` 边沿在 150 ms 内重复到达一律丢弃，并在状态里提示"已忽略右键抖动（累计 N 次）"；
- 按住模式不去抖（需要每一次松开）；
- 布防时 `reset()`；
- 单测 `HotkeyGateTest` 5 项：单次通过、抖动被吞、200 ms 后二次点击照常、边界值、reset。

> 如果连 PC 也不该看到这两次点击，只能二选一：把「热键照常传给 PC」关掉（吃掉模式），
> 或在固件里对转发报告做 5–10 ms 去抖（会给所有点击加延迟，不建议默认开）。
## 15. 左键“松手后一直射击”（固件 bug + App 安全网，2026-11-11）

现象：瞄准中松开左键，PC 侧仍持续开火（触发被粘住）。

根因在固件 `app_main.c` 的屏蔽层：引擎注入的每条报告都带着全局 `s_buttons`，而屏蔽层
（`makcu_sumv_active()` 为真时）只在“按键相对 `s_mute_btn` 有变化”时才 `makcu_mouse_forward`。
`s_mute_btn` 原先**只在屏蔽路径里更新**，正常路径从不写它。于是：

1. 左键在“瞄准窗口之外”按下 → 走正常路径，PC 收到按下，`s_buttons=1`，但 `s_mute_btn` 仍为 0；
2. 松开恰好落在“瞄准窗口之内” → 屏蔽层比较 `0 != 0` 判为“没变化”，**直接丢弃**；
3. `s_buttons` 停在 1，引擎 1 kHz 注入的每条报告都带着“按下” → PC 永远在开火。

**固件修（已写在源码里，待刷机）**：正常路径也同步 `s_mute_btn = fwd[0] & 0x1F;`（放在转发去抖之后），
让屏蔽层看到的就是“PC 实际看到的按键状态”。

**App 侧安全网（已装，无需刷机即可缓解）**：每收到一次 `EVT_STAT`，若 `cur == 0x00`（真实鼠标一个键都没按），
就发一帧 `0x32 BUTTON 0x00` 强制补一条“全松开”报告。因为 `cur==0` 时不可能误伤真实按住，所以这是无条件安全的；
实测日志：`→ BUTTON 0x00（安全释放：真实鼠标无按键，PC 可能卡在按下）`，`cur=0x00 last_fwd=0x00`。

> 注意：安全网只在“手已经全松开”后 1 秒内生效；如果松开瞬间还在扫射，最坏会多打 1 秒。
> 要彻底消除，刷上固件补丁。
## 16. 标定 px/count 的 DPI 陷阱（2026-11-11 复核）

刷完固件后用脚本量增益：`AIM(300,0)` 让光标在 `GetCursorPos()` 里只走了 300，看着像 1.00 px/count，
而文档标的是 1.25。原因不是固件，是**测量进程被 DPI 虚拟化**：

```
物理面板 2560×1600，系统缩放 125%  →  DPI-unaware 进程看到 2048×1280
GetCursorPos() 返回的是"逻辑像素"，真机物理位移 = 逻辑值 × 1.25
→ 300 逻辑 = 375 物理 = 300 counts × 1.25 ✓
```

所以 App 里的 `pxPerCount = 1.25` 是对的（它面对的是 1920×1080 采集帧的物理像素）。
**标定工具必须 DPI-aware**（manifest 声明 per-monitor v2，或 `SetProcessDpiAwareness(2)`），
否则会得到偏小 25% 的结果，进而把闭环增益调错。
## 17. 按键优先级（固件，2026-11-11 13:2x 已刷）

现象：瞄准过程中偶发“右键双发”/开镜闪断，游戏里像点了一下又点了一下。

根因：**注入报告与真实报告的竞态**。转发路径 `makcu_mouse_forward()` 会加锁、写 `s_buttons`、再 `emit`；
但引擎 1 kHz 的 `makcu_mouse_emit_now()` 不加锁，`emit()` 里读 `s_buttons` 时可能还是上一刻的旧值：

```
转发：take → s_buttons=按下 → emit(按下) → give
引擎：emit(旧字节=松开)          ← 插在中间
结果：按下 → 松开 → 按下   ＝ 游戏里的双击
```

只有引擎在跑（瞄准/移动中）才有这份竞争，所以症状只在瞄准时出现。

固件改法：

1. `s_lock` 改为**递归互斥**（`xSemaphoreCreateRecursiveMutex`），原有 take/give 全换递归版本；
2. `makcu_mouse_emit_now()` 也进锁 → 注入与转发不再交错；
3. 新增 `makcu_mouse_button_priority(buttons)`：置位 + 立即 `emit(0,0,0)`，绕过 pending 合并与转发去抖；
4. 屏蔽层改为“按键变化一律走 priority，滚轮/pan 才走 forward”。

验证（刷后，PC 直连 COM3）：

| 项 | 结果 |
|---|---|
| 版本 | `km.MAKCU` |
| 混合压力 300×AIM + 200×BUTTON / 9.7 s | 无死锁，版本仍应答 |
| 压力后按键残留 | `左键=False` |
| `AIM(300,0)` 单发 | 光标位移与计数一致（DPI 换算后 1.25 px/count） |
## 18. 换 Tab 就“不瞄了”（2026-11-11 修）

现象：状态显示「瞄准中」，盒子 `rounds` 却一直不涨，准心不跟人；换回预览页又正常。

根因：检测结果只在 `PreviewFragment.onFrame(ByteBuffer…)` 里喂给 `AimController`，而
`onHiddenChanged(hidden=true)` 会把 `setRawFrameListener(null)` 摘掉 —— 只要不在「预览」Tab，
瞄准闭环就断粮。状态机在进程单例里，所以它仍然显示“瞄准中”，形成“状态在、动作无”。

修法：隐藏时只摘 Surface（画面不必显示），**保留 raw 帧监听**，检测与瞄准继续跑。
`onStop()`（App 退到后台）仍然全部摘掉。

诊断日志（新增，都在瞄准页底部日志里）：

| 行 | 含义 |
|---|---|
| `→ AIM dx,dy counts · 残差 N px · head 0.91 …` | 闭环在发命令（≤4 条/秒打印一次） |
| `瞄准中 · 框内无目标（候选 N）` | 有检测但都不在瞄准框/类目里 |
| `已发 N 条 AIM，但 rounds/死区都没涨` | 命令在发但盒子没执行（拒绝/超限） |
| `热键边沿 mask=… edge=…` / `热键切换 → 瞄准 ON/OFF` | 每次按键与状态翻转 |
## 19. 按键报告插队槽（固件，2026-11-11 13:4x 已刷）

现象：大幅甩鼠标时偶发右键“被冲掉”（游戏里没吃到，或慢半拍）。

根因在 `components/makcu_hiddev/src/makcu_hiddev.c` 的注入队列：

```c
if (next == s_rep_tail) {          /* full: drop the oldest to stay current */
    s_rep_tail = ...; s_rep_dropped_q++;
}
```

队列 32 深、从完成回调里每 1 ms 发一条（端点容量 1000 条/s），而瞄准时引擎注入约 1000 条/s、
真实鼠标移动又 500–1000 条/s → 队列长期满载：按键报告要么排在 32 条运动报告后面（+20–30 ms），
要么正好撞上溢出被丢掉。左键“粘住”的另一种成因也是这里（松开那条被丢）。

固件改法：**按键字节变化的报告不进 FIFO，走单槽并抢先发送**

```c
if (btn != s_last_btn) {           /* 插队槽 */
    if (s_urg_valid && s_urg[0] != data[0]) rep_push_fifo(s_urg, s_urg_len); // 前一条先落地

}
```

## 21. 过冲三层防护（2026-11-11 16:0x）

现象：已经瞄上目标，收尾还会冲过去一下再回来。

根因：`pxPerCount = 1.25` 是**桌面光标**标定值，而游戏用 raw input，`counts → 视角旋转` 由游戏灵敏度与
倍镜决定。真实响应可能是假设的 1.5–2 倍，于是"走 60%"实际走成 90–120%，收尾必冲。叠加目标点在
head/body 间跳变（假检出）与 AIM 的 1.7% 侧向弧，就是"瞄上了还甩一下"。

### A 自校准增益（`AimMath.measureResponse / gainForResponse`）

```
上一帧残差 e0（请求了 e0 的 f 份额）→ 本帧残差 e1
投影 ratio = dot(e1, e0) / |e0|²    →  真实响应 k = (1 - ratio) / f
目标增益 = min(1, 0.85 / k)         →  EMA(α=0.3) 平滑到 mGainAdapt
下发增益 = min(config.gain, mGainAdapt)
```

- 只用**同一目标连续两帧**、且上帧确实发过枪（`mPrevShotSent`）时取样；
- 残差小于 ~2 px 时投影不可信，直接丢弃样本；
- `k` 落在 [0.05, 3] 之外视为异常，不更新；
- 换目标、松手、重新布防都会重置取样状态，但**保留已学到的增益**（机器/游戏属性）。

### B 目标粘滞与假目标抑制

- 锁定某跟踪 id 后，只要它还在框内且距准心 < 1.5×框宽，就继续用它（避免两个敌人靠近时来回换人）；
- `TargetTracker` 单帧位移 > **40 px** 不再匹配旧轨迹，直接当新目标（跳变/假检测不会继承稳定帧）；
- head 归属收紧：覆盖率 45%→**50%**、上部 60%→**55%**；
- `stable_frames` 默认 2→**3**。

### C 单发相对限幅

```
cap = 残差(px) × countsPerPx × 0.8
counts = limitToError(counts, 残差, countsPerPx)   // 超过 cap 按比例压回去
maxStepCounts 默认 400 → 200（≈250 px）
```

### 界面（同时适配新文档）

```
触发 12 次 · 误差 3.1 px · head 0.91
按键 184/184 · 等待 9µs · 溢出 0 · 审计 126/126 多发 0     ← 异常自动变红
自校准增益 0.72（实测响应 1.18）                          ← 正在自校准/已收敛
AIM 到位 · gen 19 · rounds 2304 · 死区 255
```

`0x3E` 第四字段 = `btn_overflow`；`0x3F BTN_AUDIT` 的 `in_chg/out_chg/extra` 判据 `extra == 0`。

## 25. 瞄头改版：瞄点落下巴 + 居中优先（2026-11-11 18:3x）

用户拍板：方案 B（瞄头部框的"居中 + 最下面"），下沿=下巴（bias **1.0**），居中容差 **±3% 画面宽**（2026-11-11 20:2x 由 schema 8 收紧到 **±1%**，见 §26.1）。

### 瞄点（`AimPick.anchorY`）

```
ay = head.top + (head.bottom - head.top) × headAnchorBias     // 默认 1.0 = 下沿（下巴）
ax = (head.left + head.right) / 2                              // 水平居中（不变）
```

- `TargetTracker` 用 `setHeadAnchorBias(bias)` 接收；body 回退仍取框中心；
- 聚类自检也必须用同一 bias 计算锚点，否则"已聚类的 head"会被当成新目标重复计数（本次踩到，已修）。

### 选择（`AimPick.pick`，替换原 `score = distance + non-head 12`）

```
tol = preferCenteredHead ? centerTolerance × frameW : 0
① 在 head 候选里挑 |ax − 准心x| ≤ tol 的"居中"者
② 其中取 y 最大者（最下面 = 最近敌人）
③ 没有居中的 head → 退回"离准心最近"（head 有 12 px 加成）
```

- 粘滞（`mStickId`）仍然优先：目标还在框内就继续用，不被"更居中/更下面"抢走；
- `centerTolerance = 0` 等价于关掉居中规则。

### 配置与界面

| 项 | 默认 | 位置 |
|---|---|---|
| `head_anchor_bias` | 1.0 | 高级区「头部锚点 1=下巴」 |
| `prefer_centered_head` | true | 高级区「居中优先：居中且最下面（最近）优先」 |
| `center_tolerance` | 0.01 | 高级区「居中容差 %」 |
| schema | **8** | 老配置自动升级 |

### 验证

- 单测 **90 项全绿**，新增 `AimPickTest` 10 例（下巴锚点、容差边界、居中优先、居中取最低、无居中回退最近、容差为 0 退化、空输入）
- `TargetTrackerTest` 改为断言"默认瞄点在框下沿"，并新增 bias=0.5 → 框中心一例
- 设备实测迁移：`aim_schema=7`、`head_anchor_bias=1.0`、`prefer_centered_head=true`、`center_tolerance=0.03`

### 25.1 居中容差收紧到 ±1%（2026-11-11 20:2x，schema **8**）

用户认为 ±3% 太宽，改为 **±1% 画面宽**。判定窗口（1080p）从 **±57.6 px → ±19.2 px**，通过率约为原来的 1/3。

改动：

| 文件 | 改动 |
|---|---|
| `AimConfig` | 字段默认 `0.03f → 0.01f`、`getFloat` 兜底 `0.01f`、新增 `schema < 8` 迁移强制覆写 `0.01f`、`aim_schema` 写 **8** |
| `AimFragment` | 「居中容差 %」空值兜底 `3f → 1f` |
| `strings.xml` | `aim_center_tol` 文案「默认 3」→「默认 1」 |
| `AimPickTest` | 新增 3 例：±1% 窗口边界、3%→1% 的选择分歧、1% 下仍回退最近 |

行为影响（重要，别再当成"更准脚锁头"）：

- 收紧后**居中集合更容易为空**，`pick()` 更频繁落到 `nearest` 分支（`headBonus` 只有 12 px，在几百 px 距离差里几乎无权重）→ 实际排序向「**最近优先**」倾斜；

### 25.2 选近优先：框大（更近）优先（2026-11-11 20:3x，schema **9**）

**动机**：`y` 只代表"屏幕上靠下"，俯视/高台/斜坡地形里近敌的 y 可能更小，会锁错人。透视投影下 `框高 ∝ 1/距离`，所以框大小才是真实距离的单调代理。

**新判据（`AimPick.pick`，多了一个 `sizes` 参数）**：

```
tol = preferCenteredHead ? centerTolerance × frameW : 0
① 在 head 候选里挑 |ax − 准心x| ≤ tol 的"居中"者
② 其中取 sizes[i] 最大（等效体高最大 = 最近）
   尺寸差 ≤ 1% 视为并列 → 退回 y 最大（最下面）
③ 没有居中的 head → 退回"离准心最近"（尺寸不参与，head 有 12 px 加成）
```

`sizes == null`（旧签名）等价于旧的「y 最大」，老调用与老测试零改动。

**等效体高 `sizeProxy`（`TargetTracker` 新增字段）**：

| 候选类型 | sizeProxy |
|---|---|
| body（含头附着在身体上的） | `body.bottom − body.top`（归一化体高） |
| head-only（模型只输出头） | `(head.bottom − head.top) × HEAD_TO_BODY`，`HEAD_TO_BODY = 5.0` |

- 归一化 → 采集分辨率切换（1080p↔2K）不失真；
- 与 `boxW/boxH` **分开**：后两个仍是真实框尺寸，overlay 画框不受影响；
- `HEAD_TO_BODY` 是常量，换模型后在 `TargetTracker` 里标定。

**换人门槛（`AimController.pick`）**：

```
允许抢锁 = best == null || best.id == mStickId
        || !pickSizeFirst
        || best.sizeProxy ≥ stick.sizeProxy × sizeGate        // 默认 1.08
```

两个尺寸接近的敌人不会每帧翻转锁定；`mStickHits` 只在"继续粘住"时 +1，`mStickSwitches` 只在"真的换人"时 +1（顺带修掉旧计数把"被否决的候选"也算成换人的问题）。

**配置与界面**：

| 项 | 默认 | 位置 |
|---|---|---|
| `pick_size_first` | true | 高级区「选近优先：框更大（更近）优先」 |
| `size_gate` | 1.08 | 高级区「换人门槛 %（默认 8）」 |
| schema | **9** | 老配置自动升级 |

界面上同时把目标读数加了等效体高：`head 0.87 · 420 px/s · h0.24`，实战可直接观察"h 大的就是近的"。

**已知取舍**：趴/蹲/侧身会让框变矮，近敌可能被远处站立者抢；贴边裁剪已通过"用高度而非面积"规避大部分。缩放抖动由 `sizeGate` 吸收。

恢复「y 最大」旧行为：关掉「选近优先」开关即可，无需回退代码。

### 25.3 头框并列 → 比身体框（2026-11-11 20:4x）

**问题**：25.2 只用 `sizeProxy`（等效体高）做第二判据，而 head 附着在 body 上时 `sizeProxy` 就是**体高**——"头框大小"这个更直接的距离信号被丢掉了。头框一样大（典型情况：两人距离相近）时，谁更近看不出区别。

**改动**：把尺寸拆成两把尺子，选敌变成三层判据。

`TargetTracker.Candidate` 新增两个字段（归一化框高）：

| 字段 | 含义 |
|---|---|
| `headSize` | 头框高；无头框 = 0 |
| `bodySize` | 身体框高；模型只给头 = 0 |
| `sizeProxy` | 保留：`bodySize > 0 ? bodySize : headSize × 5`，只给**粘滞门槛**用 |

`AimPick.pick` 新签名（`sizes` = 头框高，`bodySizes` = 身体框高）：

```
tol = preferCenteredHead ? centerTolerance × frameW : 0
① 居中 head 集合（|ax − 准心x| ≤ tol）
② 集合内比 sizes（头框）：大者胜
③ 头框差 ≤ 1% 视为并列 → 比 bodySizes（身体框）：大者胜
④ 身体框也并列 → 取 y 最大（旧行为），保证不出现"谁都不选"的空档
⑤ 没有居中 head → 距离最近（尺寸不参与）
```

要点：

- 头框和身体框**量纲一致**（都是归一化框高），所以三层比较不需要任何折算；
- head-only 候选 `bodySize = 0`，在 ③ 会输给"有身体框"的候选（合理：能看见身体说明更完整/更近）；
- 旧的两级重载（`sizes` 单参 / 完全旧签名）都保留，行为不变，`pickSizeFirst` 关闭时走旧签名等价路径；
- 粘滞门槛仍用 `sizeProxy`（等效体高），与选敌三层判据**解耦**：门槛回答"值不值得换人"，`pick` 回答"换谁"。

**测试**：`AimPickTest` 19→24（头并列→体大者胜、头明显更大仍压过体大、体也并列→最下面、head-only 输给有体、边界无缝隙回归）；`TargetTrackerTest` 在原 3 例上补断言（body 候选 / head-only / 头附着体 的 `headSize`、`bodySize`、`sizeProxy` 三值各自正确）。

**顺带修掉的一个真缺陷**：旧写法用 `size × (1 + tie)` 判"更大"、用相对差判"并列"，两者在浮点边界上留缝——`0.050` vs `0.0505`（相对差 1.0002%）既不算更大也不算并列，候选被静默忽略、选错人。现在统一成 `best ± best × tie` 带宽，两个分支严丝合缝，并加了回归用例 `boundaryBetweenBiggerAndTieHasNoGap`。

### 25.4 框大优先（横向偏离降为"可达范围"）（2026-11-11 20:5x，schema **10**）

**用户场景**：画面里一个近敌（框大、横向偏 60 px），另外两个远敌几乎居中（框小、头框只有一半大）——旧规则把近敌当"不居中"踢出集合，锁了远的小框。

**根因**：`isCentred(±1% 画面宽)` 是**资格线**，尺寸只是资格线内的排序键；`y` / `hypot` 还分别出现在第三层和回退分支。所以 x/y 在结构上优先于尺寸。

**改动**：横向偏离从资格线降级为**可达范围**，判据顺序整体翻转。

```
reach = sizeReach × frameW            // 默认 ±15% 画面宽（1080p = ±288 px）
① rect.contains()                     // 瞄准框仍是搜索区域
② 资格：|ax − 准心x| ≤ reach          // 范围内含大框，范围外不参与
③ headSize 最大（并列带 1%）
④ 并列 → bodySize 最大（并列带 1%）
⑤ 并列 → 横向偏离最小（原"居中"降级成排序键）
⑥ 并列 → y 最大
⑦ 范围内无 head → 距离最近
```

- `reach = 0` 或关掉「选近优先」→ 逐项等价于 schema 9 的行为（`better()` 的"最正"层只在 `reachPx > 0` 时启用，旧三层顺序原样保留）；
- `reach` 的作用是防"准心被屏幕边上的大框拽走"，替代原来的一票否决；
- 粘滞门槛统一到 `headSize`（此前用 `sizeProxy`，有身体时是**体高**，与 `pick` 主键不是一把尺子，会出现"pick 选了大的 B 却仍粘 A"）。

**配置与界面**：

| 项 | 默认 | 位置 |
|---|---|---|
| `size_reach` | 0.15 | 高级区「选敌横向范围 %（默认 15，0=只认居中）」 |
| `size_gate` | 1.08 | 「换人门槛 %」——现在比的是 `headSize` |
| schema | **10** | 老配置自动升级 |

目标读数同时显示两个框高：`head 0.87 · 420 px/s · h0.09 b0.30`（头框 / 身体框），实战可直接确认新判据在起作用。

**测试**：`AimPickTest` 24→29（近大框压过两个居中远小框、超范围被排除、范围内头并列比身体、全并列挑最正、范围内无 head 回退最近；并验证 `reach = 0` 回到旧行为）。

### 25.5 治「两个近敌抢鼠标」（2026-11-11 21:0x，schema **11**）

**现象**：两个距离相近的敌人时，准心在两人之间来回弹，鼠标"被抢"。

**根因**（三层缓冲全缺，只有一层且挡不住抖动）：

| 缺口 | 说明 |
|---|---|
| 尺寸无平滑 | `headSize` 直接取单帧 YOLO 框高，逐帧抖 ±5~10% |
| 门槛只有相对 | `best.headSize ≥ stick.headSize × 1.08`。近距离 `h ∝ 1/d`，两人差 0.3 m 就差 10.7%，**门槛天然被击穿**；再叠加两个目标各自 ±6.7% 的抖动，相对差可摆动 ±13% |
| 无换人确认 | 单帧判定即换人，而 AIM 是 REPLACE 语义 → 一帧反向就发一条反向修正 |

**三件套改动**：

1. **尺寸 EMA**（`TargetTracker.setSizeFilter`，默认 α=0.30）：每 track 平滑 `headSize`/`bodySize`，首帧直通，之后 `新 = α·观测 + (1−α)·旧`。选敌主键从此不再逐帧跳水。
2. **抢锁双门槛**（`AimPick.shouldTakeOver`）：相对 `sizeGate = 1.12` **且** 绝对 `sizeDelta = 0.01`（归一化框高 ≈ 11 px @1080p）。只有一档时，两个都很近的目标（框高 0.09 上下）差 12% 只需 0.011 就能被抖动凑出；双门槛把"大一点点"挡在门外。绝对门槛留 `1e-6` 容差（`0.06f − 0.05f` 在浮点里是 `0.009999998`，正好卡在 `0.01f` 门外）。
3. **换人确认帧**（`switchFrames`，默认 3）：连续 3 帧都判"该换"才真换（`mPendingStickId` + `mSwitchStreak`）。观察期继续锁旧目标并计入"粘住"，所以状态行的粘滞率会变高（正常）。

`sizeGate` 同时从 8% 放宽到 **12%**：平滑之后主键变稳，门槛要略放宽，否则真近的那个抢不过来。

**配置与界面**（高级区，选近优先下方）：

| 项 | 默认 | 控件 |
|---|---|---|
| `size_gate` | 1.12 | 换人门槛 %（显示 12） |
| `size_delta` | 0.01 | 换人最小差 %（默认 1，防抖） |
| `switch_frames` | 3 | 换人确认帧（默认 3） |
| `size_ema` | 0.30 | 尺寸平滑 %（默认 30，越大越灵敏） |
| schema | **11** | 老配置自动升级 |

**测试**：`AimPickTest` 29→31（双门槛：相对够/绝对不够 → 拒；都够 → 允；绝对够/相对不够 → 拒；尺寸为 0 → 拒），`TargetTrackerTest` 10→12（EMA 吸收跳变 0.05→0.09 得 0.062、α=1.0 关闭平滑）。

**调参指引**：还抢 → `换人门槛` 提到 15~18 或 `确认帧` 提到 5；反过来"该换不换" → `换人最小差` 降到 0.5%、`尺寸平滑` 提到 50。

## 26. 按键「假洪泛」修复（2026-11-11 18:4x，固件 c8501c7）

**现象**：布防后状态行 `按键 824/824 · 等待 50093µs · 审计 30/14 多发 16`。

**根因**：按键字节有两个真源——

```
① 正常透传：真实报告直接交给 hiddev 发出，完全不更新 s_buttons
② 引擎注入：emit() 把 s_buttons 盖进每条报告
③ hiddev：byte0 与 s_last_btn 不同 → 判为"按键变化" → 插队
```

① 与 ② 的字节一旦不同，hiddev 在**每一条**报告上都判成变化 → 824 条假按键挤占 1 ms 端点时隙 →
按键延迟 50 ms、引擎掉帧；同时 mouse 层审计的 `s_btn_last_sent` 只在 `emit()` 更新，看不见 ①，
于是把透传变化误算成「多发」。

**修法**
| 项 | 内容 |
|---|---|
| S1 真源统一 | 透传路径调用 `makcu_mouse_sync_buttons()`（只同步、不发送、不计 `in_chg`）|
| S2 审计上线级 | `out_chg` 由 hiddev 统计真正发出字节的变化；`extra = max(0, out − in)` |
| S3 防洪泛 | 按键队列 1 ms 同值去重；1 s 内变化 > 50 次计 `flood`（`0x3E` 扩到 10 B）|
| S4 可观测 | `0x42 LAST_HID` 扩到 18 B，带最近 8 条上线报告的按键字节 |

**台架验证**

```
纯 1 kHz 引擎 8 s（不按键）→ btn in=0 sent=0 wait=0 overflow=0 flood=0     ← 洪泛消失
注入一次按下+松开           → in_chg=2 out_chg=2 extra=0                  ← 审计自洽
LAST_HID 按钮=0x00 历史=00 00 00 00 00 00 00 00
```

App 状态行同步升级：`按键 sent/in · 等待 µs · 溢出 · 洪泛 · 审计 out/in 多发`，
`洪泛>0` 或 `等待>5 ms` 时整行标红。
